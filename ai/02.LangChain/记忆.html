记忆 ​

概念 ​

记忆是 Agent 能“想得起来”的东西：它决定了一次对话里 AI 记不记得你上一句说了什么，也决定了换一个会话之后它还认不认识你。

按生命周期只分两类：

  • 短期记忆：当前任务或会话的上下文，会话结束就没了，也叫会话记忆。
  • 长期记忆：跨任务、跨会话的经验与知识，落到数据库之后一直都在。

两个实现载体先记住：短期记忆靠 Checkpointer（按 thread_id 存会话快照），长期记忆靠 Store（按 namespace 存键值数据）。

短期记忆长期记忆
生命周期当前会话（短暂）跨任务、跨会话（永久）
内容当前任务状态、会话历史知识、经验、用户偏好
是否跨任务❌✅
存储Redis/内存/DBDB/Vector DB
实现载体CheckpointerStore

有什么用 ​

没有记忆的 Agent 是这样的：第二轮就忘了第一轮说的话，换个会话又要用户把背景重讲一遍，长任务断在中途只能从头再来。它每一轮都像一个刚入职的新人。

记忆解决的正是这几件事：

场景解决什么
多轮对话本次会话说过的内容记得住，指代、“刚才那个”都接得上
个性化记住用户的身份与偏好，下次不用重复介绍
长任务续跑任务状态与中间结果留在会话里，断点能捡回来
知识沉淀跨会话的经验、结论、用户档案存进长期记忆，越用越懂你
节省上下文稳定信息放长期记忆，不必每轮都塞进 prompt

所以：短期记忆决定“这次聊得顺不顺”，长期记忆决定“下次还认不认识你”。

短期记忆 ​

短期记忆的生命周期只有当前会话，所以也叫会话记忆。一个 Agent 的会话记忆通常包含三部分：

  • 对话历史
  • 查询结果（工具返回的内容）
  • 任务状态

对简单的 Agent 来说，只考虑对话历史就够了。后面再学怎么给复杂 Agent 自定义会话记忆。

管理方案 ​

  • LangChain 把会话记忆（也就是 Messages 列表）记录在 AgentState 中：

  • 每一次与 AI 的交互都会生成一个快照，记为一个 AgentStateSnapshot，记录当前会话的状态。把同一会话的所有快照串起来，就是完整的会话历史。

  • 为了区分不同会话，每个会话要有自己的 thread_id；同一会话始终使用同一个 thread_id。

  • 发起会话时必须带上 thread_id，才能唤起对应的会话记忆。

所有 AgentStateSnapshot 都由 Checkpointer 对象保存，它有多套实现：

实现存储适用
InMemorySaver进程内存开发调试，重启即丢
SqliteSaverSQLite 文件单机小项目，并发写有锁竞争
PostgresSaverPostgreSQL生产环境

    config,

    {"messages": [HumanMessage(content="我喜欢什么？")]},
    config,

长期记忆 ​

短期记忆的生命周期只有一条 thread，thread_id 一换，Agent 就等于换了个“失忆的新人”。长期记忆要解决的就是这件事：让 Agent 记住跨会话的信息——用户是谁、喜欢什么、上次做到哪一步。

LangChain 里的长期记忆不靠 checkpointer，而是靠 Store（LangGraph Store）。它存的不是会话状态，就是普通键值数据，用两个维度定位：

  • namespace：字符串元组，相当于“文件夹”，用来区分数据属于谁，常用 ("user_id", "memories")
  • key：namespace 内唯一的标识，相当于“文件名”，一条记忆一个 key
  • value：字典，真正存的内容（偏好、事实、结论都行）

一句话区分：checkpointer 按 thread 存状态，Store 按 namespace 存数据，跟 thread 无关。

管理方案 ​

  • 两者可以同时用：checkpointer 管“这次聊了什么”，store 管“这个人是谁”
  • 写入：store.put(namespace, key, value)
  • 读取单条：store.get(namespace, key)，返回对象用 .value 取内容
  • 列出 / 检索：store.search(namespace) 返回该 namespace 下所有记忆，带 query 则是语义检索
  • 由谁写：通常给 Agent 一个“保存用户信息”的 tool，让它自己决定记什么
  • 隔离靠 namespace：想按用户分开，就必须把 user_id 放进 namespace，否则所有用户共用一份

Store 的实现和 Checkpointer 一个路子，都继承 BaseStore：

实现存储位置适用
InMemoryStore进程内存开发调试，重启即丢
PostgresStorePostgreSQL生产环境，已经在用 PG
RedisStoreRedis追求低延迟，已有 Redis
MongoDBStoreMongoDB已有 Mongo

工具里通过 runtime.store 拿到 store，通过 runtime.context 拿到当前用户：

python
from dataclasses import dataclass
from typing import TypedDict
from langchain.tools import ToolRuntime, tool


@dataclass
class Context:
    user_id: str          # 当前用户，用来拼 namespace


class UserInfo(TypedDict):
    name: str
    like: str


@tool
def save_user_info(user_info: UserInfo, runtime: ToolRuntime[Context]) -> str:
    """保存用户信息，跨会话有效。"""
    user_id = runtime.context.user_id
    runtime.store.put((user_id, "memories"), "profile", dict(user_info))
    return "已记住"

完整示例 ​

python
from dataclasses import dataclass
from typing import TypedDict

from dotenv import load_dotenv
from langchain.agents import create_agent
from langchain.chat_models import init_chat_model
from langchain.tools import ToolRuntime, tool
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore

# 1.准备和加载环境变量
load_dotenv()

# 2.初始化模型
model = init_chat_model(
    "deepseek-v4-flash",
    extra_body={"thinking": {"type": "disabled"}},
)


# 3.定义context与记忆工具
@dataclass
class Context:
    user_id: str


class UserInfo(TypedDict):
    name: str
    like: str


@tool
def save_user_info(user_info: UserInfo, runtime: ToolRuntime[Context]) -> str:
    """保存用户信息，跨会话有效。"""
    user_id = runtime.context.user_id
    runtime.store.put((user_id, "memories"), "profile", dict(user_info))
    return "已记住"


@tool
def get_user_info(runtime: ToolRuntime[Context]) -> str:
    """读取用户信息，跨会话有效。"""
    item = runtime.store.get((runtime.context.user_id, "memories"), "profile")
    return str(item.value) if item else "还不认识你"


# 4.创建Agent：checkpointer管会话，store管跨会话
agent = create_agent(
    model=model,
    tools=[save_user_info, get_user_info],
    checkpointer=InMemorySaver(),
    store=InMemoryStore(),
    context_schema=Context,
)

# 5.会话1：让它记住我
agent.invoke(
    {"messages": [{"role": "user", "content": "我叫望屿，喜欢迪迦，帮我记住"}]},
    {"configurable": {"thread_id": "t1"}},
    context=Context(user_id="u1"),
)

# 6.会话2：换thread，记忆仍在
response = agent.invoke(
    {"messages": [{"role": "user", "content": "我叫什么？喜欢什么？"}]},
    {"configurable": {"thread_id": "t2"}},
    context=Context(user_id="u1"),
)
print(response["messages"][-1].content)

记忆持久化存储 ​

前面两节的 InMemorySaver / InMemoryStore 数据只活在进程里：服务重启、换台机器、多开一个副本，记忆就都丢了。要落到数据库，就得换成持久化实现。

这里容易误解的一点是：会话记忆和长期记忆是两套东西，持久化也要换两个组件——checkpointer 换实现、store 换实现，但它们可以共用同一个数据库实例。

组件对照 ​

用途内存版（开发调试）持久化版（生产）
会话记忆InMemorySaverSqliteSaver、PostgresSaver
长期记忆InMemoryStorePostgresStore、RedisStore、MongoDBStore

两者分别继承 BaseCheckpointSaver 和 BaseStore，所以换实现只改初始化那一行，写记忆的业务代码不用动。

from langchain.agents import create_agent
from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.store.postgres import PostgresStore

DB_URI = "postgresql://postgres:postgres@localhost:5432/langmem?sslmode=disable"

# 两者都是上下文管理器，退出时自动关闭连接
with PostgresSaver.from_conn_string(DB_URI) as checkpointer, \
     PostgresStore.from_conn_string(DB_URI) as store:
    checkpointer.setup()   # 建 checkpoint 相关表，幂等
    store.setup()          # 建 store 表，幂等

    agent = create_agent(
        model="deepseek-v4-flash",
        tools=[save_user_info, get_user_info],
        checkpointer=checkpointer,
        store=store,
        context_schema=Context,
    )

异步与连接池 ​

  • 异步接口用 AsyncPostgresSaver / AsyncSqliteSaver，方法加 a 前缀（aput、asearch、aget）
  • 每个请求新建一次连接，很快会把 PG 的连接数打满，生产要用连接池，启动时创建、全局复用
  • setup() 只在启动阶段跑一次，别塞进请求路径
python
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver
from langgraph.store.postgres.aio import AsyncPostgresStore
from psycopg_pool import AsyncConnectionPool

pool = AsyncConnectionPool(DB_URI, max_size=10, open=False)

async with pool:
    async with AsyncPostgresSaver(pool) as checkpointer, \
               AsyncPostgresStore(pool) as store:
        await checkpointer.setup()
        await store.setup()
        agent = create_agent(
            model="deepseek-v4-flash",
            tools=[save_user_info, get_user_info],
            checkpointer=checkpointer,
            store=store,
            context_schema=Context,
        )

注意事项 ​

  1. namespace 里不带 user_id —— 现象：换个账号登录，还能看到别人的偏好。原因：所有用户写进了同一个 namespace。解法：namespace 至少带上 user_id，多租户再加一层 tenant。
  2. 以为 store 能替代 checkpointer —— 现象：去掉 checkpointer 后，同一个 thread 里 AI 也不记得上一句。原因：store 只存你显式放进去的键值，不记对话历史。解法：两个一起用，checkpointer 管会话，store 管长期。
  3. search(query=...) 报语义检索未启用 —— 现象：传 query 报错，或结果跟关键词毫不相干。原因：构造 store 时没配索引。解法：要语义检索就给 store 配 index={"embed": ..., "dims": ...}，否则只用 search(namespace) 列出来自己筛。
  4. 生产用了 InMemoryStore —— 现象：服务一重启，所有人的记忆全没了。原因：数据只在进程内存里。解法：换成 PostgresStore / RedisStore，启动时先执行一次 setup() 建表。
  5. 跳过 setup() —— 现象：第一次查询报 relation "checkpoints" does not exist。原因：表还没建。解法：启动阶段对 checkpointer 和 store 各调一次 setup()，它是幂等的，重复执行没关系。
  6. 装了 psycopg2 —— 现象：ModuleNotFoundError: No module named 'psycopg'。原因：LangGraph 的 PG 实现要的是 psycopg 3，不是 psycopg2。解法：pip install "psycopg[binary]"，两个包不要混装。
  7. 在 with 之外用 agent —— 现象：请求时报 the connection is closed。原因：from_conn_string 是上下文管理器，退出 with 就把连接关了，而 agent 还在引用它。解法：让 agent 的生命周期留在 with 内部，或改用连接池（池不随单次请求关闭）。
  8. 用 docker compose down -v 重启环境 —— 现象：重启后所有人的记忆全没了，以为是代码问题。原因：-v 会把数据卷一起删掉，PG 的数据就在卷里。解法：日常重启只 down；要清库时先 pg_dump 备份。

总结 ​

  • 短期记忆 = 会话内，靠 checkpointer + thread_id，存的是 AgentStateSnapshot。
  • 长期记忆 = 跨会话，靠 Store + namespace/key，存的是你自己放进去的字典。
  • 两者不冲突，一起用才对：一个记“聊了什么”，一个记“这个人是谁”。
  • 想按用户隔离，user_id 必须进 namespace；生产环境别用 InMemoryStore。
  • 持久化就是把 InMemorySaver / InMemoryStore 换成 PG 实现，两个组件共用一个库，启动时跑一次 setup()。
  • 记不清该用哪个时，问一句：这条信息在下一个会话还需要吗？需要就是长期记忆，不需要就是短期记忆。
