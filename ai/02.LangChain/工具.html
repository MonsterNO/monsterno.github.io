工具（Tools） ​

概念 ​

一个完整的 Agent 至少包含两个关键部分：

  • 模型：Agent 的大脑，负责推理、分析、规划任务步骤；
  • 工具：Agent 的手脚，负责执行任务、与外界交互。

所谓工具（Tool），本质就是一个可调用的函数——但这个函数不是我们调用，而是给模型调用。所以光把函数写出来不够，还得把“这是什么工具、怎么用”讲清楚，模型才知道什么时候该调、参数怎么填。需要提供三样信息：

信息模型拿它干什么
工具名指认“我要调哪一个”
作用描述判断“这次该不该调这个工具”
参数 schema按结构组织参数，知道每个字段填什么

在 LangChain 里，只要在函数上加 @tool 装饰器，它就会自动从函数信息里提取这三样，不用自己组装。提取来源有三种：装饰器参数、函数文档注释、Pydantic 的 BaseModel。

注意

作为工具的函数有两个保留参数名，自定义参数不能与之重名：

  • config：用来传递运行时配置。
  • runtime：用来传递运行时上下文。

有什么用 ​

模型自己只会“说”，不会“做”：它能告诉你该查哪个城市的天气，但没法真的去查；能写出 SQL，但连不上库。

工具就是把“做”的能力接给模型：

场景解决什么
实时信息查天气、查汇率、查库存——模型知识停在训练时，工具能拿到此刻的数据
动手操作读写文件、发请求、建工单、发邮件
私有数据查业务库、查内部文档，这些模型本身看不到
精确计算大数运算、单位换算，交给代码算比让模型“估”可靠
串联流程多个工具接力，一次对话里完成“查—改—确认”

所以：模型负责决定做什么，工具负责把它做出来。

描述工具的三种方式 ​

三种方式只影响“工具名 / 描述 / 参数”从哪来，函数本体不用改。可以同时用，也可以只用一种。

方式一：基于 @tool 装饰器参数 ​

直接在装饰器上把名字和描述写好：

python
from langchain.tools import tool

# 方式一：用装饰器参数描述工具
@tool("square_root", description="Calculate the square root of a number")
def tool1(x: float) -> float:
    return x ** 0.5

@tool 常用的几个参数：

参数说明
name工具名，省略则取函数名
description工具描述，省略则取 docstring
args_schema入参模型，省略则从函数签名推导
return_direct为 True 时，工具结果直接作为最终回答，不再回到模型
parse_docstring为 True 时解析 docstring 的 Args 段作为参数描述

方式二：基于函数的文档注释（推荐） ​

如果装饰器没给工具名和描述，LangChain 会这样兜底：

  • 工具名：默认就是函数名
  • 工具参数：默认就是函数的参数列表
  • 工具描述：默认就是函数的文档注释（必须有，否则报错）
python
from langchain.tools import tool

# 方式二：用文档注释描述工具
@tool
def get_weather(location: str, units: str = "celsius", include_forecast: bool = False) -> str:
    """Get current weather and optional forecast.

    Args:
        location: city name or coordinates
        units: unit of degrees
        include_forecast: does it include the weather forecast
    """
    temp = 22 if units == "celsius" else 72
    result = f"Current weather in {location}: {temp} degrees {units[0].upper()}"
    if include_forecast:
        result += "\nNext 5 days: Sunny"
    return result

一个容易忽略的点：parse_docstring 默认是 False，此时整段 docstring 只作为工具描述，Args 里的逐参数说明不会传给模型。想让模型看到每个参数的含义，得写成 @tool(parse_docstring=True)。

方式三：基于 BaseModel 作为 schema ​

参数比较多、类型比较讲究（枚举、默认值、校验规则）时，用 Pydantic 模型描述入参最清楚：

python
from typing import Literal

from pydantic import BaseModel, Field
from langchain.tools import tool


# 方式三：用 BaseModel 描述工具参数
class WeatherInput(BaseModel):
    """查询天气的输入参数."""

    location: str = Field(description="City name or coordinates")
    units: Literal["celsius", "fahrenheit"] = Field(
        default="celsius",
        description="Temperature unit preference"
    )
    include_forecast: bool = Field(
        default=False,
        description="Include 5-day forecast"
    )


@tool(args_schema=WeatherInput)
def get_weather(location: str, units: str = "celsius", include_forecast: bool = False) -> str:
    """Get current weather and optional forecast."""
    temp = 22 if units == "celsius" else 72
    result = f"Current weather in {location}: {temp} degrees {units[0].upper()}"
    if include_forecast:
        result += "\nNext 5 days: Sunny"
    return result

Literal 这种枚举会让模型只能在给定取值里选，比自己写一句“units 只能是摄氏度或华氏度”可靠得多。

三种方式怎么选 ​

方式适合注意
装饰器参数临时改个工具名，或描述很短参数说明还是靠函数签名
文档注释绝大多数场景，推荐要 parse_docstring=True 才有参数说明
BaseModel参数多、有枚举 / 嵌套 / 校验多写一个类，换来精确的入参 schema

所以：日常用方式二；参数复杂了升级到方式三；方式一只在需要临时改名时用。

工具是怎么被调用的 ​

写好的工具函数不会自己跑起来，是 Agent 在对话循环里替你调：

  • 模型返回的 AIMessage 里带 tool_calls：工具名、参数、tool_call_id；
  • 运行时按 name 找到对应工具，校验参数并执行函数；
  • 结果包装成 ToolMessage，带上同一个 tool_call_id 追加进消息列表；
  • 模型拿到结果继续推理，直到不再产生 tool_calls，输出最终回答。

create_agent 会自动跑这个循环，所以只需要把 tools=[...] 传进去。一次回复里出现多个 tool_calls 时，它们会逐个执行、一起回填。

在工具里拿运行时信息 ​

工具经常需要一些“模型不该看到、但执行时需要”的信息：当前用户是谁、之前存过什么、这次会话的 id。这类信息通过那两个保留参数拿：

python
from dataclasses import dataclass

from langchain.tools import ToolRuntime, tool


@dataclass
class Context:
    user_id: str


@tool
def who_am_i(runtime: ToolRuntime[Context]) -> str:
    """返回当前用户 ID。"""
    return runtime.context.user_id

这两个参数不会出现在给模型看的 schema 里，模型既看不到也填不了，只是运行时自动注入。

注意事项 ​

  1. 只写 @tool 不写 docstring —— 现象：定义时就报错，提示函数必须有 docstring。原因：方式二靠 docstring 当描述。解法：补一段 docstring，或用方式一在装饰器里给 description。
  2. 参数名用了 config 或 runtime —— 现象：模型死活不传这个参数，或者传了也拿不到值。原因：这两个名字是保留参数，被运行时注入占用了。解法：业务参数换个名字，比如 cfg、ctx。
  3. parse_docstring 没开 —— 现象：模型经常把参数填错、漏填，明明 Args 里写了说明。原因：默认 False，逐参数说明没进 schema。解法：@tool(parse_docstring=True)。
  4. 描述写得太模糊 —— 现象：模型该调时不调，或者调了别的工具。原因：判断依据只有工具名和描述，“处理数据”这种描述等于没说。解法：写清“对什么、做什么、返回什么”，必要时把使用条件也写上。
  5. 工具里吞掉异常，返回“查询失败” —— 现象：模型把失败当成功，继续基于错误信息往下编。原因：正常字符串跟成功结果没有区别。解法：该抛异常就抛，运行时会把它作为失败的工具结果回给模型，模型有机会换参数重试。
  6. 把 IO、重试、业务判断全塞进工具 —— 现象：工具没法单测，出问题只能连模型一起调试。原因：一个函数干了太多事。解法：工具只做“取参数 → 调业务函数 → 转成字符串”，业务逻辑放可单测的普通函数里。

实战案例 ​

目标：写一个带 BaseModel schema 的汇率换算工具，先脱离模型单测，再交给 Agent 真正调用，顺便验证 schema 有没有生效。

  1. 定义工具
python
from typing import Literal

from pydantic import BaseModel, Field
from langchain.tools import tool


class ConvertInput(BaseModel):
    """汇率换算入参。"""

    amount: float = Field(description="要换算的金额", gt=0)
    source: Literal["CNY", "USD", "JPY"] = Field(description="原币种")
    target: Literal["CNY", "USD", "JPY"] = Field(description="目标币种")


RATES = {
    ("CNY", "USD"): 0.14,
    ("USD", "CNY"): 7.20,
    ("CNY", "JPY"): 21.50,
    ("JPY", "CNY"): 0.047,
}


@tool(args_schema=ConvertInput)
def convert_currency(amount: float, source: str, target: str) -> str:
    """把一种货币换算成另一种，返回两位小数的结果。"""
    if source == target:
        return f"{amount:.2f} {target}"

    rate = RATES.get((source, target))
    if rate is None:
        raise ValueError(f"暂不支持 {source} 兑换 {target}")

    return f"{amount * rate:.2f} {target}"

  1. 交给 Agent
python
import asyncio

from dotenv import load_dotenv
from langchain.agents import create_agent
from langchain.chat_models import init_chat_model
from langchain.messages import HumanMessage

load_dotenv()


async def main():
    model = init_chat_model(
        "deepseek-v4-flash",
        extra_body={"thinking": {"type": "disabled"}},
    )
    agent = create_agent(model=model, tools=[convert_currency])

    result = await agent.ainvoke(
        {"messages": [HumanMessage("100 块人民币能换多少美元？")]}
    )
    for msg in result["messages"]:
        print(f"\n【{msg.type}】: {msg.content}")


if __name__ == "__main__":
    asyncio.run(main())

总结 ​

  • 工具是给模型调用的函数，三要素缺一不可：名字、描述、参数 schema。
  • 描述优先用 docstring（方式二）；参数复杂就上 BaseModel（方式三）；装饰器参数（方式一）只在改名时用。
  • 记得 parse_docstring=True，否则 Args 里的参数说明根本到不了模型。
  • 参数名别用 config / runtime，这两个位置留给运行时注入。
  • 工具只负责“取参 → 调业务 → 转字符串”，业务逻辑放在能单测的普通函数里。
  • 调试时先 tool.invoke({...}) 单测，再放进 Agent，能把“工具本身的问题”和“模型选错工具”分开。
