智能体评测，别只盯最终答案

约 910 字大约 3 分钟

AI智能体模型评测Evals

2026-08-10

摘要： 智能体会行动，评测也要检查它怎么行动，不能只比最后一句话。

问智能体“客户上个月为什么退款变多”，它最后给出了正确数字。表面看，这次任务已经通过。往过程里翻，才发现它先查了错误的数据表，又调用了一个没有权限说明的导出工具，最后碰巧从缓存里拿到了正确结果。

只检查答案，这次会得到满分。放到真实系统里，这条路径却让人不太放心。

智能体多了一条行动轨迹

普通问答评测常看正确性、相关性和表达。智能体还会选工具、传参数、修改环境，并根据中间结果改变计划。最终答案只是最后一帧。

Anthropic 在智能体评测文章里把环境、工具和多轮执行都放进评测任务。Google 的 Agent Evaluation 也区分最终响应和轨迹。这个变化很合理：一个退款智能体答对原因固然重要，它有没有读取不该看的数据同样重要。

测试样例可以多保存一点信息：

{
  "input": "解释 7 月退款率上升的原因",
  "expectedOutcome": ["指出移动端支付失败", "引用已审核数据"],
  "requiredTools": ["query_metrics", "read_incident"],
  "forbiddenTools": ["export_customer_pii"],
  "maxToolCalls": 6
}

这里没有规定唯一的思考路线，但给出了不能越过的边界。

别把理想步骤写得太死

轨迹评测也有个坑：把人工写的步骤当成唯一答案。智能体可能用另一条更短的路径完成任务，结果被判错。Google 提供的轨迹指标里，既有精确顺序，也有只看必要动作是否出现的方式，就是为了适应不同任务。

涉及财务提交、生产发布时，步骤顺序可以很严格。做资料研究时，只要来源可靠、关键证据齐全，不必要求每次以同样顺序打开网页。

我会把评测分成几层。硬规则先由程序判断，例如是否调用禁用工具、参数是否越权、测试是否通过。答案质量再交给人工标准或模型评分。失败案例最好保留完整轨迹，方便看问题究竟出在模型、工具描述，还是环境本身。

def hard_checks(run):
    assert not set(run.tools) & FORBIDDEN_TOOLS
    assert run.tool_calls <= 6
    assert run.environment.tests_passed

简单断言通常比一段长评分提示词更稳定。

先收集真实的难题

团队刚做评测时，容易写一批过于干净的题。真实用户不会总给完整订单号，内部文档也会有冲突。可以从客服升级记录、人工接管点和生产失败轨迹里挑样例，清理敏感信息后放进评测集。

评测集还要慢慢长。一次线上故障如果只修提示词，下次仍可能以另一种形式回来；把它变成回归用例，系统才真的记住这次教训。

智能体评测不必一开始就做成庞大平台。先挑十个重要任务，同时记下答案、工具调用和环境结果。你会很快看到，有些“答错”只是措辞不同，有些“答对”才值得认真追一下。
