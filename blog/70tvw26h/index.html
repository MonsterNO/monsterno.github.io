给AI装个USB口-MCP协议实战

约 2353 字大约 8 分钟

AI智能体

2026-09-01

MCP正在成为AI Agent的工具调用标准。本文从实际踩坑出发，用Python手把手搭一个可运行的MCP Server，并聊聊它到底解决了什么。

去年做一个内部客服Agent的时候，我干过一件现在想起来挺蠢的事。

需求很简单：用户问"我的订单到哪了"，Agent要去查数据库，然后把物流信息返回给用户。最开始我用的是LangChain的Tool，写了个query_order函数，把SQL逻辑塞进去，再用bind_tools绑到模型上。跑通那天还挺开心，觉得Agent也不过如此。

然后问题就来了。

运营说想加一个"查用户积分"的功能，我又写了个query_points。过了一周，产品说要接第三方物流API，我又写了个get_logistics。每个工具都是独立的函数，参数格式全靠我手写JSON Schema，描述写得稍微含糊一点，模型就开始乱传参。最离谱的一次，它把用户ID传成了订单号，查出来一堆空结果，我排查了半天才发现是工具描述里写了个"用户标识"这种模糊词。

更烦的是，这些工具只能在我这个LangChain项目里用。后来另一个团队想用同样的订单查询能力接他们的Agent，我只能把代码复制过去，改改参数名。两边维护一份几乎一样的逻辑，改个字段都要同步两次。

那段时间我就在想，要是AI调用工具有个统一标准就好了——就像USB接口，不管你是U盘还是鼠标，插上去就能用，不用每个设备都写一套驱动。

后来MCP就出现了。

MCP到底是什么

MCP全称Model Context Protocol，是Anthropic在2024年底提出来的一个开放协议。说人话就是：它定义了一套大模型和外部工具之间的"对话规则"。

你写一个MCP Server，把你的工具、数据源、提示词模板注册进去。任何支持MCP的客户端（Claude Desktop、Cursor、各种Agent框架）连上这个Server，就能自动发现里面有什么工具、每个工具要什么参数，然后直接调用。不用再手写JSON Schema，不用再适配不同框架的Tool格式。

它的核心概念就三个：

  • Tools（工具）：模型可以主动调用的动作，比如查数据库、发邮件、调API。类似POST请求。
  • Resources（资源）：模型可以读取的数据，比如文件内容、系统状态。类似GET请求，是只读的。
  • Prompts（提示模板）：预定义好的交互模板，比如"代码审查"模板，模型可以直接套用。

听起来好像也没什么革命性的？关键在于标准化。之前每个框架都有自己的工具定义方式，LangChain是一套，LlamaIndex是一套，AutoGPT又是一套。MCP相当于在中间加了一层协议，只要你的工具符合MCP规范，任何支持MCP的客户端都能用。这才是它真正的价值——不是技术上有多难，而是结束了"各自为政"的局面。

动手搭一个MCP Server

说再多不如写代码。我们用Python的FastMCP库来搭一个实用的MCP Server，包含两个工具：一个查天气，一个查数据库里的用户订单。

先装依赖：

pip install fastmcp requests

然后创建server.py：

from fastmcp import FastMCP
import requests
import sqlite3

# 创建MCP Server实例，name是标识符，instructions会告诉模型这个Server能干什么
mcp = FastMCP(
    name="customer-service-tools",
    instructions="提供订单查询和天气查询能力，用于客服场景"
)

# 工具1：查天气
@mcp.tool()
def get_weather(city: str) -> str:
    """查询指定城市的当前天气

    Args:
        city: 城市名称，支持中文，如"广州"、"北京"
    """
    # 这里用wttr.in这个免费API，实际项目可以换成和风天气等
    try:
        resp = requests.get(f"https://wttr.in/{city}?format=%C+%t+%h", timeout=5)
        if resp.status_code == 200:
            return f"{city}：{resp.text.strip()}"
        return f"查询{city}天气失败"
    except Exception as e:
        return f"天气查询出错：{str(e)}"

# 工具2：查用户订单
@mcp.tool()
def query_user_orders(user_id: str, limit: int = 5) -> str:
    """查询指定用户的最近订单记录

    Args:
        user_id: 用户ID，格式为U开头加数字，如"U10086"
        limit: 返回订单数量，最多20条
    """
    if limit > 20:
        limit = 20

    conn = sqlite3.connect("shop.db")
    cursor = conn.cursor()

    try:
        cursor.execute(
            "SELECT order_id, product, amount, status, created_at FROM orders WHERE user_id = ? ORDER BY created_at DESC LIMIT ?",
            (user_id, limit)
        )
        rows = cursor.fetchall()

        if not rows:
            return f"用户{user_id}暂无订单记录"

        result = f"用户{user_id}的最近{len(rows)}条订单：\n"
        for row in rows:
            result += f"- 订单号：{row[0]}，商品：{row[1]}，金额：¥{row[2]}，状态：{row[3]}，下单时间：{row[4]}\n"
        return result
    finally:
        conn.close()

# 启动Server
if __name__ == "__main__":
    mcp.run()

就这么多。不到60行代码，两个工具就注册好了。FastMCP会自动根据函数签名和docstring生成工具描述，不用你手写JSON Schema——这正是我之前最烦的部分。

运行一下：

python server.py

Server会通过标准输入输出（stdio）和客户端通信。这是MCP最常用的传输方式，简单直接，不需要起HTTP服务。

接进Claude Desktop

写好Server之后，怎么让大模型用上它？以Claude Desktop为例，打开设置里的Developer页，编辑claude_desktop_config.json：

{
  "mcpServers": {
    "customer-service": {
      "command": "python",
      "args": ["/path/to/your/server.py"]
    }
  }
}

重启Claude Desktop，然后在对话框里输入"帮我查一下用户U10086的最近订单"，你会看到Claude自动调用了query_user_orders工具，拿到结果后用自然语言回复你。整个过程你不需要告诉它有什么工具、怎么调——它自己发现的。

Cursor的接入方式类似，在设置里找到MCP配置，加上同样的命令就行。接好之后，你在Cursor里写代码时，AI就能直接调用你这个Server里的工具了。

一些踩过的坑

写了几个MCP Server之后，有几个实际经验值得记一下：

工具描述一定要写清楚。 别觉得这是废话。MCP虽然自动生成Schema，但工具的行为全靠docstring描述。我有个工具叫search_product，描述只写了"搜索商品"，结果模型经常把用户说的"有没有红色的裙子"直接当关键词传进去，搜出来一堆不相关的。后来我把描述改成"根据关键词搜索商品，支持颜色、尺码等属性过滤，多个关键词用空格分隔"，准确率立刻上去了。描述写得越具体，模型调用越准。

返回结果尽量用纯文本，别返回复杂JSON。 模型处理结构化数据的能力不如你想象的好。我试过返回一个嵌套的dict，模型经常漏掉某些字段。后来改成格式化好的字符串，比如"订单号：xxx，状态：xxx"，它理解起来反而更稳。

注意安全边界。 MCP工具是真实执行代码的，模型传什么参数你就执行什么，这有风险。比如上面的query_user_orders，我限制了limit最多20条，就是防止模型传个10000把数据库查崩。涉及写操作的工具更要小心，最好加一层人工确认。

我的一些思考

用了一段时间MCP之后，我觉得它最有意思的地方不是技术本身，而是它暗示了一种新的开发范式。

以前我们写软件，是"人写代码，代码执行"。现在有了MCP，变成了"人写工具，AI选择并调用工具"。工具的使用者从人变成了AI，这意味着工具的设计原则要变——以前我们设计API，考虑的是开发者怎么用，要文档清晰、参数规范；现在设计MCP工具，考虑的是AI怎么理解，要描述自然、语义明确、容错性好。

这也是为什么我觉得工具描述比代码实现还重要。代码决定了工具能做什么，描述决定了AI会不会用、用得对不对。一个功能强大但描述含糊的工具，在AI眼里等于不存在。

当然MCP也不是银弹。它现在还比较早期，生态在快速变化，不同客户端的支持程度参差不齐。而且标准化带来的另一面是灵活性受限——有些复杂的交互场景，MCP的Tools/Resources/Prompts三分法不一定够用。但方向是对的，就像当年HTTP统一了Web服务的通信方式一样，MCP很可能会统一AI Agent的工具调用方式。

如果你也在做AI Agent相关的东西，建议花一个下午试试MCP。不用搞复杂的，就写一个你日常工作中最常用的小工具——比如查内网文档、跑个脚本、查个数据——接进Cursor或Claude里用几天。用过之后你大概就明白，为什么这么多人说MCP是AI时代的USB接口了。

它不是什么高深的技术，但它让"AI能用你的工具"这件事，从手写一堆适配代码，变成了写一个函数、加一个装饰器。这种降低门槛的东西，往往才是真正能改变生态的。
