长任务智能体，断线后怎么继续

约 830 字大约 3 分钟

AI智能体Agent RuntimeAI开发平台

2026-08-10

摘要： 长任务要从一次 HTTP 请求里拆出来，留下可以查询和恢复的任务状态。

让智能体分析五百份合同，前端转了十五分钟，浏览器一刷新，页面只剩“任务不存在”。后端其实还在跑，只是最初那条连接已经断了。用户不知道该继续等，还是重新提交一次。

短对话里，这种情况不多。任务开始跑半小时、几个小时以后，连接和任务绑在一起就很脆。

请求结束，任务可以继续

近一年的智能体平台都在补后台执行。Google 的 Managed Agents 支持 background: true，Agent Executor 强调持久化执行和恢复；MCP 新版也为长任务提供任务句柄。实现方式不同，思路很接近：先接受任务，马上返回一个 ID，后面单独查进度。

{
  "taskId": "contract-review-8f32",
  "status": "queued",
  "pollAfterMs": 2000,
  "createdAt": "2026-08-10T08:00:00Z"
}

客户端拿到 taskId 后可以轮询，也可以订阅事件。断线重连时不重新创建任务，只查询原任务。

状态别只放在执行器内存里

如果任务状态只存在某个进程里，进程挂了，taskId 也只是一个空壳。至少要把任务输入摘要、当前步骤、产物位置和最后心跳存进共享存储。执行器领取任务时使用租约，租约过期后才允许其他实例接管。

const lease = await taskStore.claim(taskId, {
  workerId,
  ttlMs: 30_000,
});

if (!lease.acquired) return;

await runNextStep(taskId);
await taskStore.renew(taskId, workerId);

续租失败时，旧执行器要停下来，避免两个实例同时写同一份结果。这类细节有点像普通队列系统，只是智能体任务通常更长，中间还会等人确认。

等用户时别占着工作线程

合同里出现特殊赔偿条款，智能体可能需要法务确认。任务状态可以切到 input_required，保存问题和恢复位置，然后释放计算资源。用户第二天回答，执行器再从检查点继续。

取消也要认真做。前端把状态改成 cancelled 不等于后台真的停了。执行器每完成一小段工作都检查取消标记，下游 API 如果支持取消，也把信号传下去。已经生成的临时文件要有清理时间，不然运行一阵后存储里全是半成品。

我更关心的验收方式，是把故障主动加进去。处理到第 200 份合同时杀掉执行器，等租约过期，再看新实例能否从第 201 份继续。接着刷新浏览器，确认页面仍能找到同一个任务。这样的测试比让进度条顺利走完一次有说服力。

长任务运行时听起来像新东西，底层很多问题还是队列、租约、幂等和状态机。把这些老办法用扎实，智能体才不会因为一次断线就失忆。
