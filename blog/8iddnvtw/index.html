大模型推理优化-五招把响应时间砍到三分之一

约 2538 字大约 8 分钟

大模型

2026-09-01

大模型应用上线后，用户抱怨响应慢？本文从模型选型、量化加速、KV缓存、批处理到流式输出，分享五招经过验证的推理优化方法，亲测有效。

我们的AI客服系统上线第一周，用户投诉最多的不是回答不准，而是"太慢了"。

有用户截图给我们看：问一个问题，转圈转了8秒才出答案。还有更夸张的，复杂问题要等15秒。领导把我叫过去说："回答不准可以慢慢优化，但响应慢是硬伤，用户等不及的。一周之内，把响应时间降到3秒以内。"

当时我们用的是GPT-4o，API调用本身就要3-5秒，加上我们自己的RAG检索和处理，总延迟经常超过8秒。要降到3秒以内，看起来是不可能的任务。

但一周之后，我们真的做到了——平均响应时间1.2秒，P99 2.8秒。今天就把我们用的五招分享出来。

第一招：选对模型，比什么优化都重要

这是最有效但也最容易被忽视的一招。很多人一上来就用最强的模型（GPT-4o、Claude 3 Opus），但实际上80%的场景根本不需要这么强的模型。

我们做了一个测试：把客服系统里的1000个真实问题，分别用GPT-4o和GPT-4o-mini回答，然后人工评估答案的合格率。

结果是：GPT-4o的合格率是94%，GPT-4o-mini的合格率是89%。只差5个百分点，但速度差了3倍，价格差了10倍。

对于客服场景来说，89%的合格率完全够用——剩下11%可以转人工。于是我们把主模型从GPT-4o换成了GPT-4o-mini，平均响应时间直接从4秒降到了1.5秒。

但不是所有场景都能用小模型。我们的策略是模型分级：

def select_model(query_type):
    """根据问题类型选择合适的模型"""
    if query_type == "简单问答":
        return "gpt-4o-mini"      # 快、便宜，80%的问题用这个
    elif query_type == "复杂推理":
        return "gpt-4o"            # 复杂问题用强模型
    elif query_type == "代码生成":
        return "gpt-4o"            # 代码需要强模型
    else:
        return "gpt-4o-mini"       # 默认用小模型

我们还加了一个"兜底机制"：如果小模型的回答置信度低（比如答案含糊、有不确定的表述），自动用大模型重新回答一次。这样既保证了速度，又保证了质量。

模型分级之后，我们85%的请求走小模型，15%走大模型，整体平均响应时间降了60%，成本降了70%。

第二招：量化加速

如果你是自己部署模型（不是调API），量化是最直接的加速手段。

量化的原理很简单：大模型的参数通常是FP16（16位浮点数）存储的，量化就是把它变成INT8（8位整数）甚至INT4（4位整数），这样模型体积变小，计算速度变快，而精度损失很小。

我们用vLLM部署开源模型的时候，加了量化参数，速度直接提升了一倍：

# 用vLLM部署，开启AWQ量化
python -m vllm.entrypoints.openai.api_server \
    --model Qwen/Qwen2.5-72B-Instruct-AWQ \
    --quantization awq \
    --gpu-memory-utilization 0.9 \
    --max-model-len 8192 \
    --tensor-parallel-size 2

量化的效果：

  • 模型体积：FP16的72B模型需要144GB显存，AWQ量化后只需要72GB
  • 推理速度：量化后吞吐量提升约80-100%
  • 精度损失：AWQ量化的精度损失通常在1-2%以内，大多数场景感知不到

量化的选择：

  • AWQ：目前最推荐的量化方法，精度损失小，兼容性好
  • GPTQ：老牌量化方法，精度也不错
  • INT4：极致压缩，适合显存紧张的场景，但精度损失稍大

我的建议是：如果显存够，用INT8量化；显存紧张，用AWQ的INT4量化。不要用比INT4更低的量化，精度损失会很明显。

第三招：KV缓存优化

大模型推理的时候，每生成一个token，都要把之前所有token的Key和Value存下来（这就是KV缓存）。KV缓存占的显存非常大，而且如果缓存管理不好，会严重影响推理速度。

我们做了两个KV缓存的优化：

优化1：Prefix Caching（前缀缓存）

很多请求的开头是一样的——比如系统提示词、RAG检索到的上下文。如果每次都重新计算这些前缀的KV，就浪费了。

Prefix Caching的思路是：把相同前缀的KV缓存起来，下次请求如果前缀相同，直接复用缓存，不用重新计算。

vLLM默认开启了Prefix Caching：

# 开启前缀缓存
python -m vllm.entrypoints.openai.api_server \
    --model Qwen/Qwen2.5-72B-Instruct-AWQ \
    --enable-prefix-caching \
    --prefix-caching-max-length 4096

我们的RAG场景下，很多请求的系统提示词和检索上下文是相同的，Prefix Caching让我们的首token延迟降低了约30%。

优化2：限制上下文长度

很多人不管什么请求，都把最大上下文设成32K甚至128K。但实际上，KV缓存的大小和上下文长度成正比——上下文越长，KV缓存越大，推理越慢。

我们根据场景限制了上下文长度：

# 不同场景的上下文限制
MAX_TOKENS = {
    "简单问答": 1024,      # 简单问题不需要长上下文
    "文档总结": 8192,      # 总结文档需要较长上下文
    "代码审查": 4096,      # 代码审查中等长度
    "复杂推理": 8192,      # 复杂推理需要较长上下文
}

限制上下文长度之后，KV缓存的占用降了一半，推理速度提升了约25%。

第四招：批处理（Continuous Batching）

如果你自己部署模型，批处理是提升吞吐量最有效的手段。

传统的批处理是"静态批处理"：凑够一批请求一起处理，处理完了再处理下一批。问题是，如果一批里有一个请求特别长，其他请求都要等它。

vLLM用的是"连续批处理"（Continuous Batching）：每个请求生成一个token之后，如果它还没结束，就继续留在批里；如果结束了，就立刻把它移出批，加入新的请求。这样GPU永远不会闲着，吞吐量大幅提升。

# vLLM默认开启连续批处理
# 关键参数
python -m vllm.entrypoints.openai.api_server \
    --model Qwen/Qwen2.5-72B-Instruct-AWQ \
    --max-num-seqs 256 \          # 最大并发序列数
    --max-num-batched-tokens 8192  # 每批最大token数

连续批处理的效果非常惊人：我们的吞吐量从每秒15个请求提升到了每秒80个请求，提升了5倍多。而且平均延迟反而降低了，因为请求不用等"凑批"。

第五招：流式输出

最后一招，也是用户感知最明显的一招：流式输出。

不用流式输出的话，用户要等模型把完整答案生成完才能看到内容，可能要等5-10秒。用流式输出的话，模型生成一个字就显示一个字，用户几乎立刻就能看到内容，感知上的速度提升非常明显。

虽然实际上总生成时间没变，但用户的等待感大大降低了。我们做过用户调研：流式输出开启后，用户对"响应速度"的满意度从3分提升到了4.5分（满分5分），尽管实际总时间只快了一点点。

流式输出的实现很简单：

from openai import OpenAI

client = OpenAI()

def chat_stream(query):
    """流式输出"""
    stream = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": query}],
        stream=True  # 开启流式
    )
    
    for chunk in stream:
        if chunk.choices[0].delta.content:
            yield chunk.choices[0].delta.content  # 逐字返回给前端

前端用EventSource接收，逐字显示就行。

我的一些思考

做推理优化这件事，我最大的感受是：不要一上来就抠底层优化，先从顶层决策开始。

很多人一想到推理优化，就去研究算子融合、CUDA内核、模型压缩这些底层技术。但实际上，最有效的优化往往是顶层的：选对模型（第一招）、限制上下文（第三招）、流式输出（第五招）。这些不需要什么高深的技术，但效果比底层优化好得多。

我们的优化顺序是：先做模型分级（省60%时间），再做流式输出（用户感知提升），然后做量化和KV缓存（再省30%），最后做批处理（提升吞吐量）。按这个顺序，每一步都能看到明显的效果，而且不需要一开始就投入大量精力。

另一个感受是：推理优化是一个持续的过程，不是一次性的。 模型在更新、场景在变化、用户量在增长，今天的最优配置明天可能就不是了。我们现在每个月都会做一次性能review，看看有没有新的优化空间。

最后说一句：不要为了优化而优化。优化的目标是用户体验，不是跑分。如果一个优化让速度快了10%，但答案质量降了5%，那可能不值得。永远在速度和质量之间找平衡，而不是一味追求快。

大模型推理优化这条路没有尽头，但只要方向对了，每一步都能看到效果。希望这五招能帮你把响应时间砍下来。
