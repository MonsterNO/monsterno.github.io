文档RAG漏掉表格，答案就会偏

约 841 字大约 3 分钟

RAG多模态大模型

2026-08-10

摘要： 文档里最关键的数据常在表格和图中，普通文本抽取会悄悄漏掉它们。

问财报助手“海外收入增长多少”，它引用了一段很流畅的管理层总结，数字却错了。正确答案就在下一页表格里。PDF 文本抽取把列顺序打散，检索系统没找到那一行。

这种错误挺隐蔽。回答有来源，也有数字，看起来比纯幻觉更可信。

PDF 不是一长串文字

真实企业文档里有多栏排版、表格、脚注、扫描图片和流程图。把所有内容转成纯文本再按 500 字切块，会丢掉空间关系。表头和数值分开后，单独检索任何一块都说不清含义。

多模态 RAG 的第一步，是保留文档结构。解析时记录页码、区块类型和位置。表格既可以存结构化数据，也保留页面截图，方便视觉模型复核。

{
  "document": "annual-report-2025.pdf",
  "page": 42,
  "type": "table",
  "caption": "按地区划分的收入",
  "cells": [["地区", "2025", "2024"], ["海外", "18.2", "15.7"]],
  "imageRef": "page-42-table-1.png"
}

检索结果带着这些字段，答案就能引用到具体页和表格，而不是只说“根据财报”。

检索时让不同内容走不同路线

文本段落适合向量检索和关键词检索，表格问题还需要识别列名、时间和单位。图表可以先生成描述，再在命中后把原图交给视觉模型。所有内容硬塞进一种 Embedding，效果往往不稳定。

NVIDIA 2026 年的多模态 RAG 资料把文本、表格、图表和扫描页都列为企业知识系统需要处理的对象。这不是为了让架构显得高级，是因为漏掉任一类，答案都会有盲区。

if query.looks_numeric:
    candidates = hybrid_search(text_index, table_index, query)
else:
    candidates = semantic_search(all_blocks, query)

真实系统会更复杂，但“数值问题优先找表格”已经比完全不区分强。

评测要有专门的表格题

很多 RAG 测试集几乎全是正文问答，于是系统上线前看着分数不错。可以单独准备跨行、跨页、单位换算和图表趋势题。除了比对答案文本，还要核对引用页、表头和年份。

OCR 也要留置信度。扫描模糊时，数字 8 和 3 很容易认错。低置信度的关键金额进入人工复核，比让模型根据上下文猜一个更稳。

我会拿一份公司里最难读的 PDF 做起点，而不是先找排版整齐的示例文档。把里面的表格和图表问通，再扩到整个知识库。第一份文档可能处理得很慢，但它会把解析链路里真正薄弱的地方暴露出来。

RAG 的问题有时不在模型，也不在检索算法。资料从 PDF 进入系统的那一刻，答案已经少了一半。先把文档看完整，后面的智能才有地方落脚。
