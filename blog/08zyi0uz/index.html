向量数据库深度解析-HNSW索引原理与工程实践

约 4700 字大约 16 分钟

向量数据库深度解析

2026-09-01

RAG是AI应用的核心技术，而向量数据库是RAG的基石。本文从最基础的相似度搜索讲起，深度拆解向量数据库的核心索引算法——HNSW（分层可导航小世界图），讲清它的原理、参数调优、工程实现，并对比主流向量数据库的选型。

一、为什么需要向量数据库

传统的数据库（MySQL、PostgreSQL）擅长精确匹配——你给一个条件，它返回完全匹配的记录。但在AI应用中，我们经常需要做"语义搜索"——找和查询"意思相近"的内容，而不是"完全一样"的内容。

比如用户问"怎么退款"，知识库里的文章标题是"退货退款流程说明"。用传统的关键词搜索，"退款"能匹配上，但如果用户问"东西不想要了怎么办"，关键词搜索就匹配不上了——因为"不想要"和"退款"字面上不一样，但意思是一样的。

向量数据库解决的就是这个问题：把文本转换成向量（一串数字），语义相近的文本，向量的距离也近。通过计算向量之间的距离，就能找到语义相似的内容。

这个过程叫相似度搜索（Similarity Search）或最近邻搜索（Nearest Neighbor Search）。向量数据库就是专门做这个的数据库。

二、向量搜索的基础

2.1 文本转向量（Embedding）

第一步是把文本转换成向量。这个过程叫Embedding（嵌入），用Embedding模型来做。

Embedding模型的输入是一段文本，输出是一个高维向量（通常是768维、1024维、1536维）。这个向量代表了文本的"语义"——语义相近的文本，向量在高维空间中的距离也近。

比如：

  • "怎么退款" → [0.12, -0.34, 0.56, ...]
  • "退货流程" → [0.15, -0.31, 0.52, ...]（和上面的距离近）
  • "今天天气真好" → [-0.45, 0.67, -0.12, ...]（和上面的距离远）

常用的Embedding模型：OpenAI text-embedding-3、BGE、GTE、E5、Cohere Embed等。

2.2 相似度度量

有了向量，怎么衡量两个向量的"距离"？常用的相似度度量有三种：

1. 余弦相似度（Cosine Similarity）：计算两个向量夹角的余弦值。值域[-1, 1]，值越大越相似。余弦相似度只关心向量的方向，不关心长度。这是最常用的相似度度量。

cosine(A,B)=A⋅B∥A∥∥B∥\text{cosine}(A, B) = \frac{A \cdot B}{\|A\| \|B\|} cosine(A,B)=∥A∥∥B∥A⋅B​

2. 欧氏距离（Euclidean Distance）：计算两个向量在高维空间中的直线距离。值越小越相似。欧氏距离既关心方向也关心长度。

euclidean(A,B)=∑i=1n(Ai−Bi)2\text{euclidean}(A, B) = \sqrt{\sum_{i=1}^{n}(A_i - B_i)^2} euclidean(A,B)=i=1∑n​(Ai​−Bi​)2​

3. 点积（Dot Product）：计算两个向量的内积。值越大越相似。点积和向量的长度有关——长度大的向量点积也大。

dot(A,B)=∑i=1nAiBi\text{dot}(A, B) = \sum_{i=1}^{n} A_i B_i dot(A,B)=i=1∑n​Ai​Bi​

如果向量都做了归一化（长度为1），那么余弦相似度和点积是等价的。大多数Embedding模型输出的向量已经做了归一化，所以用点积和余弦相似度效果一样。

2.3 暴力搜索 vs 近似最近邻

最简单的相似度搜索方法是暴力搜索（Brute Force）：把查询向量和库里的所有向量逐一计算距离，返回距离最近的K个。

暴力搜索的优点是精确（能找到真正的最近邻），缺点是慢——如果库里有100万条向量，每条1024维，一次查询就要计算100万次距离，每次距离计算要做1024次乘法。这在高并发下根本扛不住。

所以实际应用中用的是近似最近邻（Approximate Nearest Neighbor, ANN）：牺牲一点点精度（比如95%的召回率），换取几十倍甚至几百倍的速度提升。

ANN的核心是索引（Index）——提前对向量做一些预处理（建索引），查询的时候不用遍历所有向量，只需要检查一部分候选向量，就能找到近似最近邻。

主流的ANN索引算法包括：

  • HNSW（Hierarchical Navigable Small World，分层可导航小世界图）：目前最主流、效果最好的算法
  • IVF（Inverted File，倒排文件）：基于聚类的索引
  • PQ（Product Quantization，乘积量化）：基于压缩的索引
  • LSH（Locality Sensitive Hashing，局部敏感哈希）：基于哈希的索引

其中HNSW是目前的绝对主流，几乎所有向量数据库都支持HNSW索引。下面重点拆解HNSW的原理。

三、HNSW索引原理

HNSW（Hierarchical Navigable Small World，分层可导航小世界图）是2018年由Yury Malkov和Dmitry Yashunin提出的ANN算法。它结合了图搜索和分层思想，在速度和精度上都达到了最优水平。

3.1 从NSW到HNSW

HNSW的前身是NSW（Navigable Small World，可导航小世界图）。NSW的核心思想是：把所有向量构建成一个图，每个向量是图中的一个节点，和它最近的几个节点相连。查询的时候，从一个入口节点出发，沿着图"走"——每次走到当前节点的邻居中距离查询最近的那个，直到走不动为止。

这个过程类似于"贪心搜索"——每次都往更近的方向走。但贪心搜索有个问题：可能会陷入局部最优——走到一个节点，它的所有邻居都比它远，但全局最近邻还在很远的地方，没走到。

NSW通过"长程连接"来解决这个问题——在构建图的时候，不仅连最近的邻居，还随机连一些远距离的节点（"长程边"）。这样查询的时候，能通过长程边快速跳到离目标近的区域，然后再用短程边精确定位。这就是"小世界"特性——任意两个节点之间的路径长度很短。

NSW的问题是：所有节点都在同一层，入口节点是随机选的，如果入口节点离目标很远，需要走很多步才能到。HNSW通过"分层"来解决这个问题。

3.2 HNSW的分层结构

HNSW的核心创新是分层——把图分成多层，最上层是"稀疏图"（节点少、连接少），最下层是"稠密图"（所有节点、连接多）。

Layer 2:    ○───○          (稀疏，只有少数节点)
              \ /
Layer 1:    ○───○───○       (中等，部分节点)
            / \ / \ /
Layer 0:  ○───○───○───○───○ (稠密，所有节点)

分层的思想类似于"高速公路"：

  • 上层（Layer 2）是"高速公路"——节点少，能快速从一个区域跳到另一个区域（粗定位）
  • 下层（Layer 0）是"普通道路"——节点多，能在局部区域精确定位（细搜索）

每个节点在每一层是否存在，是随机决定的——用指数分布随机决定节点的最大层数。大多数节点只在最下层（Layer 0），少数节点能到上层。越往上，节点越少。

3.3 HNSW的查询过程

HNSW的查询过程是"从上到下逐层搜索"：

1. 从最上层的入口节点开始
2. 在当前层做贪心搜索：从入口节点出发，每次走到邻居中距离查询最近的节点，直到找不到更近的
3. 把当前层找到的最近节点作为下一层的入口
4. 下降到下一层，重复步骤2-3
5. 直到最下层（Layer 0），找到的最近节点就是最终结果

这个过程的直觉是：先用上层的稀疏图快速定位到目标所在的区域（粗定位），然后在下层的稠密图里精确定位（细搜索）。这样比在稠密图里从随机入口开始搜索要快得多——因为上层节点少，几步就能跳到目标区域。

3.4 HNSW的构建过程

HNSW的构建过程是逐个插入节点：

1. 为新节点随机决定最大层数（用指数分布）
2. 从最上层开始，找到该层中离新节点最近的节点
3. 下降到下一层，在该层做贪心搜索，找到最近的M个邻居
4. 把新节点和这M个邻居互相连接
5. 重复步骤3-4，直到新节点的最大层数
6. 如果是第一个节点，作为各层的入口

构建的时候有个重要的机制：连接的"修剪"。每个节点的最大连接数是有限的（参数M），如果新节点要连到一个已经有M个连接的节点，需要"修剪"——把那个节点最远的连接删掉，给新节点腾位置。这样保证图的连接数不会无限增长。

3.5 HNSW的关键参数

HNSW有几个关键参数，影响搜索速度和精度：

1. M（每个节点的最大连接数）

  • 含义：每个节点在图中的最大邻居数
  • 影响：M越大，图越稠密，搜索精度越高，但内存占用越大，构建越慢
  • 典型值：16-64。常用M=16或M=32

2. ef_construction（构建时的搜索宽度）

  • 含义：构建索引时，每层贪心搜索保留的候选节点数
  • 影响：ef_construction越大，构建的图质量越高（连接更合理），但构建越慢
  • 典型值：100-500。常用ef_construction=200

3. ef_search（查询时的搜索宽度）

  • 含义：查询时，每层贪心搜索保留的候选节点数
  • 影响：ef_search越大，搜索精度越高（召回率越高），但查询越慢
  • 典型值：50-500。可以在查询时动态调整——对精度要求高就设大，对速度要求高就设小

这三个参数的调优原则：

  • M和ef_construction在建索引时确定，建完就不能改了（要改就得重建索引）
  • ef_search可以在查询时动态调整，根据需求平衡速度和精度
  • 数据量越大、维度越高，M和ef_construction需要设得越大

四、HNSW的工程实现

4.1 内存优化

HNSW的内存占用主要来自两部分：

  1. 向量数据：每个向量的原始数据。100万条1024维FP32向量 = 100万 × 1024 × 4字节 = 4GB
  2. 图结构：每个节点的连接信息。每个节点最多M个连接，每个连接存一个节点ID（4字节）。100万条 × M=16 × 4字节 = 64MB

向量数据占了绝大部分内存。为了降低内存占用，可以用量化（Quantization）：

  • 标量量化（Scalar Quantization）：把FP32转成INT8，内存减到1/4，精度损失很小
  • 乘积量化（Product Quantization, PQ）：把向量分成若干段，每段用聚类中心编码，内存能减到1/16甚至更少，精度损失稍大
  • HNSW + PQ：HNSW的图结构用原始向量（保证搜索质量），叶子节点用PQ压缩（降低内存）。这是Faiss等库常用的优化方式

4.2 持久化

HNSW索引构建好之后，需要持久化到磁盘，避免重启后重新构建（重建很耗时）。

持久化的方式：

  • 全量快照：把整个索引（向量数据+图结构）序列化成文件，保存到磁盘。重启时加载。简单但加载慢（大索引可能需要几分钟）
  • 增量持久化：每次插入/删除节点时，实时写入磁盘。类似数据库的WAL（Write-Ahead Log）。恢复快，但实现复杂
  • 内存映射（mmap）：把索引文件映射到内存，操作系统自动管理换入换出。不需要把整个索引加载到内存，适合索引比内存大的场景。这是大多数向量数据库的做法

4.3 动态更新

HNSW支持动态插入和删除节点：

  • 插入：和构建过程一样，逐个插入。插入的复杂度是O(log n)（因为分层搜索），很快
  • 删除：HNSW的删除比较 tricky——直接删掉节点会破坏图的连通性。常用的做法是"软删除"——标记节点为已删除，查询时跳过，后台定期清理重建。或者用"墓碑"机制

动态更新是向量数据库的重要能力——知识库的内容会不断新增、修改、删除，需要索引能实时更新。

五、其他ANN索引算法简介

虽然HNSW是主流，但了解其他算法有助于理解不同场景的选型：

5.1 IVF（倒排文件）

IVF的思路是聚类：先用K-Means把所有向量聚成N个簇，每个簇有一个中心。查询时，先找到离查询最近的几个簇中心，然后只在这几个簇里做暴力搜索。

  • 优点：构建快、内存小、适合大规模数据
  • 缺点：精度比HNSW低，需要调参（簇的数量、搜索的簇数）
  • 适合：数据量特别大（亿级）、对精度要求不极高的场景

5.2 PQ（乘积量化）

PQ的思路是压缩：把高维向量分成若干段，每段单独做K-Means聚类，用聚类中心的ID代替原始向量。这样一个1024维的FP32向量（4KB），可以压缩成几十字节。

  • 优点：内存极小，适合超大规模数据
  • 缺点：精度损失较大，需要配合IVF或HNSW使用
  • 适合：内存有限、数据量极大、能接受一定精度损失的场景

5.3 LSH（局部敏感哈希）

LSH的思路是哈希：设计一组哈希函数，让相似的向量有更大概率哈希到同一个桶里。查询时，只需要检查和查询在同一个桶里的向量。

  • 优点：理论优美，构建快
  • 缺点：实际效果不如HNSW，内存大，精度低
  • 现状：用得越来越少，基本被HNSW取代

5.4 算法对比

算法速度精度内存构建速度适用场景
HNSW快高中中通用场景，最主流
IVF中中小快超大规模，精度要求不高
IVF+PQ快中低极小快内存有限，超大规模
LSH中低大快基本被淘汰
暴力搜索慢最高大-数据量小（<10万），需要100%精度

六、主流向量数据库对比

目前主流的向量数据库有很多，各有特点：

数据库开源索引算法特点适用场景
Milvus是HNSW、IVF、PQ等功能最全，分布式，云原生企业级，大规模
Qdrant是HNSWRust实现，性能好，API友好中小规模，快速上手
Weaviate是HNSW自带向量化，GraphQL API知识图谱，语义搜索
Pinecone否自研全托管，开箱即用，性能好不想自己运维
Chroma是HNSW轻量，Python友好，适合原型原型开发，小规模
FAISS是多种库，不是数据库，需要自己管理自定义程度高，研究
pgvector是HNSW、IVFPostgreSQL扩展，和关系数据共存已有PG，数据量不大

选型建议：

  • 快速原型/小规模：Chroma或pgvector（如果已经用PostgreSQL）
  • 中小规模生产：Qdrant（性能好，运维简单）
  • 大规模/企业级：Milvus（功能全，分布式，支持亿级数据）
  • 不想运维：Pinecone（全托管，但贵）
  • 自定义程度高/研究：FAISS（库，自己管理存储和索引）

七、RAG中的向量检索最佳实践

向量数据库在RAG（检索增强生成）中使用时，有一些最佳实践：

7.1 文档切分（Chunking）

文档切分是RAG的第一步，也是最影响检索质量的步骤。切分原则：

  • 大小适中：太小语义不完整，太大噪声多。通常200-500个Token
  • 语义完整：尽量在段落、章节边界切分，不要把一个完整的意思切开
  • 重叠（Overlap）：相邻chunk之间留一些重叠（10-20%），避免关键信息在切分边界丢失
  • 元数据：每个chunk带上文档标题、章节、页码等元数据，便于过滤和溯源

7.2 混合检索（Hybrid Search）

纯向量检索有时候会漏掉关键词匹配的结果（比如专有名词、产品型号、错误代码）。混合检索 = 向量检索 + 关键词检索（BM25），然后用RRF（Reciprocal Rank Fusion）等方法融合结果。

混合检索通常能比纯向量检索提升5-10%的召回率，是生产级RAG的标配。

7.3 重排序（Reranking）

向量检索返回的Top-K结果，排序不一定准确——向量相似度不等于"对回答这个问题最有用"。重排序用一个更精确的模型（比如Cohere Rerank、BGE Reranker）对Top-K结果重新排序，取Top-N给LLM。

通常检索返回20-50条，重排序后取3-5条给LLM。重排序能显著提升回答质量。

7.4 查询改写（Query Rewriting）

用户的查询有时候太简短或太模糊，直接检索效果不好。查询改写用LLM把用户的查询改写成更适合检索的形式——比如扩展关键词、分解成多个子查询、提取关键实体。

查询改写能提升检索的召回率，尤其是对模糊查询。

八、总结

向量数据库是AI应用（尤其是RAG）的基础设施，HNSW是目前最主流的向量索引算法。

核心要点回顾：

  1. 向量搜索的本质：把文本转换成向量，通过计算向量距离找到语义相似的内容
  2. HNSW的核心思想：分层图搜索——上层稀疏图粗定位，下层稠密图细搜索
  3. HNSW的关键参数：M（连接数）、ef_construction（构建宽度）、ef_search（查询宽度），平衡速度和精度
  4. 工程优化：量化降低内存、mmap持久化、动态更新支持
  5. RAG最佳实践：合理切分、混合检索、重排序、查询改写

几个判断：

  • HNSW在可预见的未来仍是主流：它的速度和精度平衡最好，工程实现成熟，新的算法（如DiskANN、SPANN）还在发展中
  • 向量数据库和关系数据库会融合：pgvector等扩展让PostgreSQL也能做向量搜索，未来"向量+关系+全文"的统一数据库会越来越多
  • 检索质量比数据库选型更重要：RAG的效果，80%取决于文档切分、检索策略、重排序，只有20%取决于用哪个向量数据库。不要本末倒置
