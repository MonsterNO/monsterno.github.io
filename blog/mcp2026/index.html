MCP 2026升级后，远程服务怎么迁

约 2665 字大约 9 分钟

AI智能体MCPAI开发平台模型工具

2026-08-10

摘要： 写给远程 MCP 服务开发者：看懂无状态、长任务和鉴权变化，少踩迁移坑。

你写了一个生成周报的 MCP 服务。本机用 stdio 调用，创建工作区、读取数据、导出文件，一路都挺顺。等它搬到服务器上，后面挂了三个实例，问题就来了：第一次请求落在 A，第二次被分到 B，B 不认识刚才那段会话。

日志里每个接口好像都成功了，周报却接不上。为了先把服务救回来，你可能会开粘性会话，也可能把 Session 塞进 Redis。功能是能用了，只是部署越来越不像一个普通的 HTTP 服务。

MCP 在 2026 年 7 月 28 日发布的新规范，处理的正是这类问题。它去掉初始化会话，引入更明确的长任务、缓存和鉴权规则。听上去都是协议词，落到项目里，其实就是一件事：远程 MCP 服务怎么少记一点连接历史，又不把业务状态弄丢。

如果你的工具只在自己电脑上跑，这次不用急着改。如果已经放到远程环境，尤其是多实例服务，下面这些变化值得看一遍。

本地没感觉，远程先疼

旧版 MCP 的调用通常从 initialize 开始，服务端再发回 Mcp-Session-Id。后面的请求带着这个 ID，服务端便知道它们属于同一段会话。

这种方式在本机很好理解，因为客户端和服务端基本不会走散。到了远程环境，Session 会慢慢变成一个运维问题。负载均衡器要记住请求原来落在哪台机器；某个实例挂掉以后，新实例还得找到之前的上下文；客户端一旦断线，服务端主动发起的请求也不好继续。

我刚看到“移除初始化”时，第一反应只是少发一次请求，似乎不算大事。把周报服务的调用顺着走一遍，区别才明显。以前，一条请求能不能处理，多少要看此前发生过什么。现在，协议希望每个请求自己把必要信息带齐。

这不代表服务端从此不能保存任何数据。用户上传的文件、生成到一半的报告、租户权限，这些状态还在。变化在于它们不该只藏在某段连接里。

一条请求，现在要能自己说明白

新版移除了 initialize/initialized 交换，也不再依赖 Mcp-Session-Id。协议版本、客户端信息和能力跟着请求走。客户端如果想先了解服务端，可以调用可选的 server/discover，但工具调用不用等这次握手完成。

先不管 SDK，直接看一条简化过的请求，会更容易理解：

export async function callTool(
  endpoint: string,
  token: string,
  name: string,
  args: Record<string, unknown>,
) {
  const body = {
    jsonrpc: "2.0",
    id: crypto.randomUUID(),
    method: "tools/call",
    params: {
      name,
      arguments: args,
      _meta: {
        "io.modelcontextprotocol/clientInfo": {
          name: "weekly-report-web",
          version: "1.4.0",
        },
      },
    },
  };

  const response = await fetch(endpoint, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${token}`,
      "MCP-Protocol-Version": "2026-07-28",
      "Mcp-Method": "tools/call",
      "Mcp-Name": name,
    },
    body: JSON.stringify(body),
  });

  if (!response.ok) {
    throw new Error(`MCP 调用失败：${response.status}`);
  }

  return response.json();
}

这里省略了超时、重试和完整的 OAuth 流程，只留下这次变化里最关键的字段。服务端拿到一条请求，已经知道客户端版本、要调用的方法以及工具名，不必先去会话存储里翻前情。

周报生成到一半的状态怎么处理？可以在创建工作区时返回一个业务句柄，例如 workspaceHandle，后面的调用再明确传回来。

{
  "name": "render_report",
  "arguments": {
    "workspaceHandle": "ws_7f3a",
    "template": "weekly"
  }
}

这个办法不花哨，甚至显得有点笨，但排错时很省心。日志里能看见句柄，重试时也知道要恢复哪份数据。只要三个实例都能根据 ws_7f3a 找到同一个工作区，请求落到谁那里都能继续。

要注意，句柄不能直接等于数据库主键。它最好有过期时间，能撤销，并且绑定用户或租户。协议不再管理会话，不等于这些边界可以省掉。

把一份周报跑完，会经过什么

继续沿用前面的例子。用户先调用 create_workspace，拿到工作区句柄。接着调用 render_report。如果报告几秒就能生成，服务端照常返回结果；如果它要读取很多数据，可能需要跑十几分钟，就返回一个 taskId。

客户端随后通过 tasks/get 查询进度。任务需要补充信息时，可以用 tasks/update 继续；用户不想等了，再调用 tasks/cancel。这些能力属于 io.modelcontextprotocol/tasks 扩展，客户端和服务端要先确认彼此都支持，不能只看服务端版本号就默认可用。

控制流大概是这样：

let task = await startReport("ws_7f3a");

while (task.status === "working") {
  await delay(task.pollIntervalMs ?? 2000);
  task = await getTask(task.taskId);
}

if (task.status === "input_required") {
  // 把问题展示给用户，拿到回答后再用 tasks/update 继续
  return showQuestions(task.inputRequests);
}

if (task.status !== "completed") {
  throw new Error(`报告生成结束，状态：${task.status}`);
}

return task.result;

轮询看起来没有长连接那么“实时”，可它的恢复路径比较直白。浏览器关了，客户端重启了，只要 taskId 还有效，就能回来查进度。对一个十几分钟的任务，我会选任务句柄，心里踏实一些。一条长连接能撑多久，实在不好说。

如果工具准备覆盖旧报告，服务端还可以用 MRTR 返回 input_required，把确认问题和不透明的 requestState 一起交给客户端。用户点确认后，客户端重新发送原调用，并把回答与 requestState 原样带回。这里有个很实际的坑：覆盖、扣费、删除之类的操作一定要有幂等键。否则服务端其实已经执行成功，只是响应在路上丢了，客户端一重试就可能做两遍。

新版还给 Streamable HTTP 增加了 Mcp-Method 和 Mcp-Name 请求头。网关不用先解析整段 JSON，就能看出这是 tools/list，还是在调用 delete_report。不过请求头也是客户端传来的，网关必须核对它和正文是否一致，再结合令牌身份和 OAuth 作用域做判断。把高风险工具只拦在前端按钮上，还是不够。

工具目录也多了 ttlMs 和 cacheScope。这对周报服务同样有用：普通工具列表可以短暂缓存，和个人权限有关的列表则应放进私有缓存。cacheScope: "public" 只是缓存提示，不能拿它证明数据真的适合公开。我看到这个字段时，更担心权限隔离。缓存快一点固然好，别把甲公司的工具目录发给乙公司才是底线。

真要迁，先找藏起来的状态

我不建议上来就升级 SDK。依赖版本改起来很快，麻烦通常藏在那些已经没人说得清的状态里。

可以先在代码和网关配置里搜几个词：Mcp-Session-Id、initialize、内存里的 Session 对象，还有维持回调的 SSE 连接。再看实例缓存中放了什么。有些数据只是为了协议握手存在，可以直接拿掉；有些其实是工作区、任务进度或用户授权，需要换成显式句柄，不能一起删。

状态理清后，再选一个测试环境接入支持新规范的 SDK。TypeScript、Python、Go 和 C# 的 Tier 1 SDK 已经跟上这版规范，不过宿主应用是否兼容仍要单独确认。旧版和新版可以留一小段并行观测期，别在一次发布里同时改协议、鉴权和所有业务工具。

网关这边要检查请求头与 JSON-RPC 正文是否一致。缓存键里应包含身份和租户边界。OAuth 则要校验授权服务器返回的 iss，客户端凭据不能跨发行方混用。动态客户端注册 DCR 已进入弃用路径，新接入可以开始看 CIMD。

Roots、Sampling、Logging 以及旧 HTTP+SSE 传输也进入了弃用阶段，官方给出的迁移窗口至少是 12 个月。现有项目不用今晚就删，但新功能最好别继续往这些旧能力上堆。

到了验证环节，我会先做几个有点“故意找麻烦”的测试：报告生成到一半时关掉一个实例；让用户隔十分钟再确认；把同一个覆盖请求重试两次。相比只看接口有没有返回 200，这几次测试更容易暴露状态丢失、重复执行和权限串用。

目前我没有真实压测数据，所以不想写“性能提升了多少”这种结论。真要比较，可以给旧版和新版各放三个实例，记录 P95 延迟、Session 存储读写、随机停掉实例后的完成率，再看看私有工具目录有没有被错误共享。新版少了协议会话，也仍然要读取业务状态，数字未必每一项都更漂亮。把成本测出来，比先写一个好看的结论更有用。

可以先做一个很小的动作

这次升级让我觉得有用，是因为它把远程服务里的麻烦摆到了明面上。实例可能突然退出，用户也可能隔半天才点确认。偏偏这时客户端又重试了。现在协议给这些情况留了恢复办法，MCP 也更像一套能长期维护的服务接口。

本地 stdio 工具可以继续用，不必为了追版本马上重构。远程、多实例、多租户，或者带有写操作的 MCP 服务，情况就不一样了。今天可以先做一个很小的动作：在项目里搜一下 Mcp-Session-Id，顺着它看看有哪些数据只存在某台机器的内存里。

如果搜出来的东西很多，也不用急着全改。先把“协议状态”和“业务状态”分开，迁移顺序自然就会清楚。等真正动手时，建议把最难恢复的那条调用链先拿出来测试。它通常比一份很长的升级清单更能说明问题。
