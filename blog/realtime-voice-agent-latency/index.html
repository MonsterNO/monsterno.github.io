实时语音智能体，延迟藏在哪

约 802 字大约 3 分钟

语音智能体Realtime APIAI助手

2026-08-10

摘要： 语音对话慢半拍，问题可能出在模型之前，也可能卡在工具之后。

语音助手回答文字问题只要一秒，实际通话却总让人觉得慢。用户说完以后，它停两秒才开口；用户想插话，它又把上一句读完。单看模型接口耗时并不高，体验还是僵。

语音交互对停顿很敏感。文字聊天多等一秒不明显，电话里的一秒会让人怀疑对方是不是掉线了。

先把一轮对话拆开计时

一轮语音通常经过采集、语音端点判断、上行网络、模型处理、工具调用和音频播放。只记录“请求总耗时”，很难知道该优化哪里。

{
  "speechEndDetectedMs": 420,
  "uplinkMs": 85,
  "modelFirstAudioMs": 310,
  "toolCallMs": 760,
  "playbackBufferMs": 90
}

这里最慢的是工具调用，换一个更快的语音模型帮助有限。要是 speechEndDetectedMs 很高，用户每次说完都会先等一段安静。

OpenAI 在 2026 年推出 GPT-Realtime-2 等新语音模型，重点已经从“能说话”往推理、翻译和边说边处理走。模型变强以后，整条链路的细节会更显眼。

流式音频还要处理打断

自然对话不会严格一问一答。用户说“等等”时，客户端应该立刻停止播放，并通知服务端取消未播放的音频。否则模型后面的话还在缓存里，下一轮会错位。

player.on("user_speaking", async () => {
  player.clearBuffer();
  await realtime.cancelResponse(currentResponseId);
});

端点检测也不能一味追求快。阈值太短，用户正常停顿就被当成说完；阈值太长，助手总慢半拍。客服、外语练习和车载场景的说话节奏不同，参数最好按场景测试。

工具结果不用全念出来

语音智能体查订单时，工具可能返回一大段 JSON。先筛出状态、时间和下一步，再生成口语回答。接口出错时，可以先说“我正在重新查询”，别让电话里长时间没有声音。

安全提示也要适合听。付款确认不能读一段很长的条款后让用户说“好”。金额、收款方和动作讲清楚，再要求明确确认。

NVIDIA 的语音 RAG 示例把识别、检索、安全和语音输出拆成多个组件。这种模块化会增加链路，却方便分别测延迟和质量。实际项目里，不一定每层都用不同模型，但计时方式值得借鉴。

准备优化时，可以先录十段真实对话，把“用户说完”到“第一段可听声音”的时间画出来，再标记工具调用。听感是主观的，链路数据能告诉你应该从哪一段开始。语音助手自然不自然，很多时候就藏在这几百毫秒里。
