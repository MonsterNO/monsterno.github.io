用AI写代码一年的8个高效习惯

约 2580 字大约 9 分钟

AI编程

2026-09-01

AI编程工具不是装上就有用，用得好是神器，用不好是累赘。本文分享我用AI写代码一年总结的8个实用习惯，每个都经过真实项目验证。

一年前团队开始全面用AI写代码的时候，我是最积极的那个。当时觉得有了AI，写代码还不是分分钟的事？结果第一周就被打脸了：AI生成的代码bug满天飞，我改bug的时间比自己写还长。

后来慢慢摸索，才发现AI编程和自己写代码完全是两种技能。自己写代码是"想清楚再写"，用AI写代码是"说清楚再让它写"——你表达需求的能力，直接决定了AI输出的质量。

这一年下来，我总结了8个真正有用的习惯，今天分享出来。

习惯一：先写注释，再让AI写代码

这是我最常用、也最有效的一个技巧。

以前我直接跟AI说"帮我写一个用户登录接口"，它写出来的东西总是差那么点意思——参数校验不全、错误处理粗糙、返回格式不统一。后来我改成先写注释：

# 用户登录接口
# 输入：手机号+密码（JSON body）
# 流程：
#   1. 校验手机号格式（11位数字）和密码长度（6-20位）
#   2. 根据手机号查用户，不存在返回404
#   3. 比对密码（bcrypt加密），错误返回401，累计5次锁定账户
#   4. 生成JWT token（有效期7天），返回token和用户基本信息
# 注意：密码错误次数存在Redis，key为login_fail:{phone}，TTL 30分钟
def login(request):
    pass  # 让AI来实现

把注释写得越详细，AI写出来的代码越符合预期。因为注释本质上就是"需求文档"，你把需求说清楚了，AI才能写对。

而且这种方式还有一个好处：注释是给人看的，AI写完代码后，注释还在，代码的可维护性也高了。

习惯二：把大任务拆成小任务

不要让AI一次实现一个完整的功能模块。比如"帮我做一个用户管理系统"，这种需求AI写出来的东西一定是半成品——它不知道你的表结构、不知道你的框架约定、不知道你的错误处理规范。

正确的做法是拆成小任务：

  1. "帮我设计用户表的SQL schema，包含字段：id、手机号、密码hash、昵称、头像、状态、创建时间、更新时间"
  2. "基于上面的schema，用SQLAlchemy写User模型"
  3. "写用户注册接口，参数校验参考项目里现有的register_validator"
  4. "写用户登录接口，密码用bcrypt校验，token用项目里的jwt_util生成"
  5. "写用户信息查询和修改接口"

每个小任务AI都能写得比较准确，而且你可以在每一步检查和修正，避免最后出来一个大半成品。

习惯三：给AI看你的代码规范

AI不知道你的项目用什么命名规范、什么错误处理方式、什么代码风格。如果你不告诉它，它就会用"通用风格"写，结果就是和你的项目格格不入。

我的做法是，在项目根目录放一个AI_GUIDELINES.md文件，里面写清楚项目的代码规范：

# 项目代码规范（供AI参考）

## 命名
- 函数和变量用snake_case
- 类名用PascalCase
- 常量用UPPER_SNAKE_CASE

## 错误处理
- 所有接口返回统一格式：{"code": 0, "message": "success", "data": {...}}
- 业务异常抛BusinessException，由全局异常处理器捕获
- 不要用try-except吞异常，除非有明确的处理逻辑

## 数据库
- 用SQLAlchemy ORM，不要写裸SQL
- 所有表必须有created_at和updated_at字段
- 查询用db.session.query，不要用text()

## 注释
- 公共函数必须有docstring，说明参数、返回值、异常
- 复杂逻辑必须加行内注释

然后每次让AI写代码之前，把这个文件的内容贴给它（或者用Cursor的@功能引用这个文件）。这样AI写出来的代码风格就和你的项目一致了，不用再花时间改格式。

习惯四：让AI写测试，而不是只写实现

很多人用AI只写业务代码，测试还是自己写。这其实是浪费——AI写测试的能力比写实现还强，因为测试的逻辑更直接。

我的做法是：让AI同时写实现和测试。比如：

"帮我写一个校验手机号格式的函数，同时写对应的单元测试，覆盖：正常手机号、不足11位、超过11位、包含非数字字符、空字符串、None这几种情况。"

这样AI写完实现，测试也一起写好了，你跑一下测试就知道实现对不对。而且AI写的测试往往比你自己写的覆盖更全——它会想到一些你没想到的边界情况。

习惯五：用AI做代码审查，而不是只写代码

AI不只能写代码，还能审查代码。我现在的习惯是：写完代码（不管是自己写的还是AI写的），都让AI做一遍审查。

"帮我审查这段代码，重点看：有没有安全漏洞、有没有性能问题、有没有边界情况没处理、有没有可以简化的地方。"

AI审查代码有一个人类没有的优势：它不会有"自己写的代码舍不得改"的心理。它会客观地指出问题，哪怕这段代码是它自己写的。

有好几次，AI写的代码我觉得没问题，但让它自己审查，它发现了一个边界情况没处理。这种"自己写自己审"的模式，比单纯写代码质量高很多。

习惯六：不要盲目接受AI的补全

这是一个教训。刚开始用AI补全的时候，我看到提示就按Tab，觉得"AI写的应该没问题"。结果有一次AI补全了一个SQL查询，里面有个条件写反了，我没看就接受了，上线后导致数据统计错误，查了半天才发现。

从那以后我养成了一个习惯：AI补全的每一行代码，我都至少看一眼再按Tab。 尤其是涉及条件判断、数值计算、数据库操作的代码，必须仔细看。

AI补全的错误率其实不低，大概每10次补全就有1次有问题。如果你盲目接受，这些小错误积累起来就是大问题。

习惯七：建立自己的Prompt模板库

用AI写代码久了，你会发现很多需求是重复的：写接口、写模型、写测试、写工具函数……每次都重新组织语言描述需求，既慢又容易遗漏细节。

我的做法是建立一个Prompt模板库，把常用的需求描述存下来，用的时候直接套用：

# 写RESTful接口模板
请用{框架}写一个{资源}的{操作}接口：
- 路由：{路由路径}
- 请求参数：{参数列表，包含类型和校验规则}
- 业务逻辑：{具体要做什么}
- 返回格式：{成功和失败的返回格式}
- 参考项目中的{现有文件}的写法

# 写单元测试模板
请为{函数名}写单元测试，覆盖以下情况：
- 正常输入：{描述}
- 边界情况：{描述}
- 异常输入：{描述}
- 依赖mock：{需要mock的依赖}
使用{测试框架}，参考项目中{现有测试文件}的写法。

有了模板库，你描述需求的速度和质量都会大幅提升。而且模板是可以不断优化的——每次发现AI输出有问题，就回去改进模板，下次就不会再犯。

习惯八：知道什么时候不用AI

最后一个习惯，也是最重要的：不是所有代码都该让AI写。

有些场景，自己写比让AI写更快更好：

  • 非常简单的代码：比如一个三行的工具函数，自己写10秒，让AI写要描述需求30秒，还不一定对。
  • 核心业务逻辑：涉及钱、权限、安全的核心逻辑，一定要自己写或者至少逐行审查。AI在这些地方犯错的代价太大。
  • 你正在学习的技术：如果你在学一个新技术，不要让AI帮你写。自己写一遍才能真正理解，AI写的你永远只是"看懂了"而不是"学会了"。
  • 需要深度思考的架构设计：AI能帮你实现细节，但架构设计需要你对业务有深刻理解，这是AI替代不了的。

AI是工具，不是主人。知道什么时候用、什么时候不用，才是真正的高效。

写在最后

这8个习惯，说起来都不复杂，但真正坚持下来的人不多。很多人用AI写代码，还停留在"让它写，然后改bug"的阶段，效率自然上不去。

我觉得AI编程的核心能力，不是写代码的能力，而是表达需求的能力和判断质量的能力。你能把需求说得多清楚，AI就能写得多准确；你能多快判断AI写的代码对不对，你就能多高效地使用AI。

这两个能力都需要练习。刚开始可能觉得"还不如自己写快"，但坚持一两个月，你会发现效率真的能翻几倍。我现在写代码的速度，大概是一年前的三倍，而且代码质量也更高——因为AI帮我处理了大量重复劳动，我可以把精力放在真正重要的架构设计和业务逻辑上。

如果你也在用AI写代码，试试这8个习惯。不用全改，先挑一两个你觉得最有用的开始。用一段时间，你会回来感谢我的。
