提示词缓存省钱，前缀别总变

约 822 字大约 3 分钟

大模型提示词缓存AI开发平台

2026-08-10

摘要： 缓存不只看内容是否相同，也看共同前缀有没有被随手打乱。

知识助手每次回答都带着三万 Token 的产品手册。一天几千次请求，大部分手册内容完全相同，账单却还是往上涨。开了提示词缓存后，命中率只有十几个点。

查了一圈，问题不在手册。应用每次都把当前时间、随机请求号和用户昵称写在最前面，共同前缀从第一个 Token 就分叉了。

稳定内容放前面

许多模型服务会复用重复的输入前缀。系统规则、产品手册和固定工具定义相对稳定，适合排在前面。当前问题、用户状态和时间信息变化频繁，放到后面。

const input = [
  systemRules,
  productManual,
  stableToolDefinitions,
  userPermissionContext,
  currentQuestion,
];

Google Gemini 的缓存文档也建议把大段共同内容放在提示词开头，并保持相似前缀。使用隐式缓存时，还可以从响应里的缓存 Token 统计确认是否命中。

别为了缓存把权限混在一起

缓存最容易犯的错，是看到命中率上涨就忘了隔离。公司公共手册可以共享，包含用户订单、内部权限或私人对话的上下文不能跨用户复用。服务商如何隔离缓存要查清楚，应用自己的检索缓存也要把租户放进键里。

cache-key = model + prompt-version + tenant + knowledge-version

如果知识库更新，knowledge-version 跟着变。旧内容就算还能命中，也不该继续使用。

另一个小问题是工具顺序。工具列表来自数据库，查询没有稳定排序时，同一批定义每次顺序不同，前缀自然变化。给工具按名称固定排序，往往就能改善命中率。

先算每个任务的真实成本

提示词缓存只减少可复用的输入成本，模型输出、工具调用和检索仍会计费。一个 Agent 反复调用十轮，每轮又塞入新的大结果，优化最初前缀可能只省下一部分。

可以按任务记录四个数字：总输入 Token、缓存命中 Token、输出 Token、完成率。完成率很重要。为了省一点上下文把关键规则删掉，导致任务重试两次，账单反而更高。

我喜欢先拿一条请求展开看，给每段上下文标上“稳定”或“变化”。这种手工检查很朴素，却经常能发现时间戳、随机 ID、无序列表这些小东西。调整以后再看缓存指标，不用猜。

提示词缓存不是一个神奇开关。它更像整理仓库：经常使用、长期不变的东西放在固定位置，临时物品别每次都堵在门口。顺序理清了，成本和延迟通常都会安静一点。
