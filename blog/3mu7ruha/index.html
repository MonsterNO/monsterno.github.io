AI网关技术深度解析-限流熔断模型路由的工程实践

约 4925 字大约 16 分钟

AI网关技术深度解析

2026-09-01

一个生产级的AI应用，为什么需要AI网关？本文系统拆解AI网关的核心功能——模型路由、负载均衡、故障转移、限流熔断、缓存、成本控制、安全防护，并给出可落地的工程实现方案。

一、为什么需要AI网关

传统的微服务架构中，API网关是标配——所有请求的统一入口，负责认证、限流、路由、日志。但在AI应用中，网关的作用更加重要，因为AI应用有一些特殊的挑战：

1. 多模型管理：一个AI应用可能同时接入多个LLM（OpenAI、Anthropic、通义、DeepSeek、本地模型），每个模型的API格式、认证方式、计费方式都不一样。如果每个服务都自己对接这些模型，代码会非常混乱。需要一个统一的网关来管理所有模型的接入。

2. 成本控制：LLM调用是按Token计费的，成本很高。需要在网关层做统一的成本控制——预算限制、用量统计、模型分级（简单任务用便宜模型）、缓存。如果没有网关，每个服务自己做成本控制，很难统一管理。

3. 稳定性保障：LLM API是外部服务，可能会故障、限流、延迟波动。需要在网关层做故障转移（一个模型挂了自动切到另一个）、熔断（故障率高了暂时不用）、重试（瞬时故障自动重试）。如果没有网关，每个服务自己处理这些，容易出问题。

4. 安全防护：LLM API Key是敏感信息，不能散落在各个服务里。需要在网关层统一管理API Key，下游服务不需要知道Key。同时还要做输入过滤（防止Prompt注入）、输出过滤（防止有害内容）、速率限制（防止滥用）。

5. 可观测性：所有LLM调用都经过网关，可以在网关层统一记录Trace、Metric、Log，不需要每个服务都自己接一遍。

因为这些原因，AI网关（也叫LLM Gateway、AI Proxy）成为了生产级AI应用的标配组件。

三、模型路由与负载均衡

3.1 模型路由

模型路由是AI网关最基础的功能——根据请求的特征，选择合适的模型来处理。

常见的路由策略：

1. 按任务类型路由：不同类型的任务用不同的模型。

  • 简单问答、摘要：用便宜的小模型（GPT-4o-mini、Qwen-Turbo）
  • 复杂推理、代码生成：用强的大模型（GPT-4o、Claude 3 Opus、Qwen-Max）
  • 长文本处理：用长上下文模型（Claude 3、GPT-4-128K）
class ModelRouter:
    def route(self, request):
        task_type = classify_task(request.prompt)
        
        if task_type == "simple_qa":
            return "gpt-4o-mini"
        elif task_type == "complex_reasoning":
            return "gpt-4o"
        elif task_type == "code_generation":
            return "claude-3-opus"
        elif task_type == "long_text":
            return "claude-3-sonnet-200k"
        else:
            return "gpt-4o-mini"  # 默认用便宜的

2. 按用户等级路由：不同等级的用户用不同的模型。

  • 免费用户：用便宜的模型，有限速
  • 付费用户：用好的模型，限速宽松
  • 企业用户：用指定的模型，有SLA保障

3. 按成本预算路由：根据当前的成本使用情况，动态选择模型。

  • 预算充足时：用好的模型
  • 预算快用完时：自动降级到便宜的模型

4. 按延迟要求路由：根据请求的延迟要求，选择模型。

  • 实时对话（要求低延迟）：用快的模型
  • 离线任务（不要求延迟）：用慢但质量高的模型

3.2 负载均衡

同一个模型可能有多个接入点（多个API Key、多个区域、多个供应商），需要做负载均衡。

常见的负载均衡策略：

1. 轮询（Round Robin）：依次分配给各个接入点。简单公平，但不考虑各个接入点的负载和性能差异。

2. 加权轮询（Weighted Round Robin）：根据各个接入点的性能分配权重。性能好的分配更多请求。

3. 最少连接（Least Connections）：分配给当前连接数最少的接入点。适合请求处理时间差异大的场景。

4. 延迟感知（Latency-Aware）：实时监控各个接入点的延迟，优先分配给延迟最低的接入点。这是AI网关最常用的策略，因为LLM API的延迟波动很大。

class LatencyAwareLoadBalancer:
    def __init__(self, endpoints):
        self.endpoints = endpoints  # 接入点列表
        self.latency_stats = {ep: [] for ep in endpoints}  # 每个接入点的延迟统计
    
    def select(self):
        """选择延迟最低的接入点"""
        avg_latencies = {}
        for ep in self.endpoints:
            if self.latency_stats[ep]:
                avg_latencies[ep] = sum(self.latency_stats[ep][-20:]) / len(self.latency_stats[ep][-20:])
            else:
                avg_latencies[ep] = 0  # 没数据的优先试
        
        return min(avg_latencies, key=avg_latencies.get)
    
    def record_latency(self, endpoint, latency):
        """记录接入点的延迟"""
        self.latency_stats[endpoint].append(latency)
        if len(self.latency_stats[endpoint]) > 100:
            self.latency_stats[endpoint] = self.latency_stats[endpoint][-100:]

四、故障转移与熔断重试

4.1 故障转移（Failover）

LLM API是外部服务，可能会故障。故障转移就是：当一个模型/接入点故障时，自动切换到另一个可用的模型/接入点。

故障转移的策略：

1. 主备模式：有一个主模型和一个备用模型。主模型正常时用主模型，主模型故障时自动切到备用模型。主模型恢复后自动切回。

2. 多活模式：多个模型同时在线，负载均衡。一个故障了，流量自动分到其他健康的模型上。

3. 降级模式：主模型故障时，不是切到同等的备用模型，而是降级到更便宜/更快的模型。比如GPT-4o故障时，降级到GPT-4o-mini。保证服务可用，虽然质量下降了。

故障转移的触发条件：

  • HTTP 5xx错误（服务端错误）
  • 超时（超过阈值没有响应）
  • 限流（429错误，配额用完）
  • 连接失败（网络问题）
class FailoverRouter:
    def __init__(self, primary, fallback, downgrade=None):
        self.primary = primary
        self.fallback = fallback
        self.downgrade = downgrade  # 降级模型
    
    def route(self, request):
        # 先试主模型
        try:
            return self.call_model(self.primary, request)
        except (ServerError, TimeoutError, RateLimitError) as e:
            logger.warning(f"Primary model failed: {e}, trying fallback")
            
            # 主模型失败，试备用模型
            try:
                return self.call_model(self.fallback, request)
            except Exception as e2:
                logger.warning(f"Fallback model failed: {e2}, trying downgrade")
                
                # 备用模型也失败，降级到更便宜的模型
                if self.downgrade:
                    return self.call_model(self.downgrade, request)
                raise  # 都失败了，抛出异常

4.2 熔断（Circuit Breaker）

故障转移是"单次请求失败就切换"，但如果一个模型持续故障，每次请求都先试主模型再试备用，会浪费时间（每次都要等主模型超时）。熔断就是解决这个问题：当一个模型的故障率超过阈值时，暂时"熔断"它，直接不用，过一段时间再尝试恢复。

熔断器的三个状态：

  • CLOSED（关闭）：正常状态，请求正常发送到该模型
  • OPEN（打开）：熔断状态，请求不发送到该模型，直接失败或走备用
  • HALF_OPEN（半开）：恢复试探状态，放少量请求过去，如果成功就恢复CLOSED，如果失败就回到OPEN
class CircuitBreaker:
    def __init__(self, failure_threshold=0.5, recovery_timeout=30, window_size=20):
        self.failure_threshold = failure_threshold  # 失败率阈值
        self.recovery_timeout = recovery_timeout    # 熔断恢复时间（秒）
        self.window_size = window_size               # 统计窗口大小
        
        self.state = "CLOSED"
        self.failure_count = 0
        self.total_count = 0
        self.last_failure_time = None
    
    def call(self, func, *args, **kwargs):
        # 检查熔断器状态
        if self.state == "OPEN":
            # 检查是否到了恢复时间
            if time.time() - self.last_failure_time > self.recovery_timeout:
                self.state = "HALF_OPEN"
            else:
                raise CircuitBreakerOpenError("Circuit breaker is OPEN")
        
        try:
            result = func(*args, **kwargs)
            self._on_success()
            return result
        except Exception as e:
            self._on_failure()
            raise
    
    def _on_success(self):
        self.total_count += 1
        if self.state == "HALF_OPEN":
            # 半开状态下成功，恢复正常
            self.state = "CLOSED"
            self._reset_stats()
    
    def _on_failure(self):
        self.failure_count += 1
        self.total_count += 1
        self.last_failure_time = time.time()
        
        if self.state == "HALF_OPEN":
            # 半开状态下失败，重新熔断
            self.state = "OPEN"
            return
        
        # 统计窗口满了，计算失败率
        if self.total_count >= self.window_size:
            failure_rate = self.failure_count / self.total_count
            if failure_rate >= self.failure_threshold:
                self.state = "OPEN"
            self._reset_stats()
    
    def _reset_stats(self):
        self.failure_count = 0
        self.total_count = 0

4.3 重试（Retry）

对于瞬时故障（网络抖动、临时超时），重试一下就能成功。重试策略需要考虑：

1. 哪些错误可以重试：

  • 可以重试：超时、5xx错误、连接失败、限流（等一会儿再试）
  • 不可以重试：4xx错误（参数错误，重试也没用）、业务逻辑错误

2. 重试次数：通常2-3次，太多了会增加延迟和成本。

3. 重试间隔：用指数退避（Exponential Backoff）+ 随机抖动（Jitter），避免所有请求同时重试导致"重试风暴"。

import time
import random

def call_with_retry(func, max_retries=3, base_delay=1.0):
    for attempt in range(max_retries):
        try:
            return func()
        except RetryableError as e:
            if attempt == max_retries - 1:
                raise  # 最后一次重试失败，抛出异常
            
            # 指数退避 + 随机抖动
            delay = base_delay * (2 ** attempt) + random.uniform(0, 0.5)
            logger.warning(f"Attempt {attempt+1} failed: {e}, retrying in {delay:.2f}s")
            time.sleep(delay)

4. 重试的成本考虑：LLM调用是按Token计费的，重试意味着重复消耗Token。对于已经发送了部分输出的流式请求，重试的成本更高。需要在重试策略中考虑成本，比如只对"还没开始生成就失败"的请求重试，已经生成了一部分的就不重试了。

五、限流与缓存

5.1 限流（Rate Limiting）

限流是AI网关的重要功能，防止滥用和过载。

常见的限流维度：

  • 按用户：每个用户每分钟/每天的请求数和Token数限制
  • 按API Key：每个Key的请求数限制
  • 按IP：每个IP的请求数限制（防止恶意攻击）
  • 按模型：每个模型的总请求数限制（防止某个模型被打爆）
  • 按功能：每个功能模块的请求数限制

限流算法：

  • 令牌桶（Token Bucket）：固定速率往桶里放令牌，请求消耗令牌，桶满了就丢弃。允许突发流量。
  • 漏桶（Leaky Bucket）：请求进入桶里，固定速率流出。流量平滑，不允许突发。
  • 滑动窗口（Sliding Window）：统计滑动时间窗口内的请求数。比固定窗口更精确。
class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate = rate          # 令牌生成速率（每秒）
        self.capacity = capacity  # 桶容量
        self.tokens = capacity    # 当前令牌数
        self.last_time = time.time()
    
    def acquire(self, tokens=1):
        """获取令牌，返回是否成功"""
        now = time.time()
        # 补充令牌
        self.tokens = min(
            self.capacity,
            self.tokens + (now - self.last_time) * self.rate
        )
        self.last_time = now
        
        if self.tokens >= tokens:
            self.tokens -= tokens
            return True
        return False

分布式限流用Redis实现，保证多实例之间的限流数据共享。

5.2 缓存（Caching）

缓存是降低AI应用成本和延迟的最有效手段之一。LLM调用很贵很慢，如果相同的请求能命中缓存，直接返回缓存结果，能省很多钱和时间。

1. 精确缓存：完全相同的Prompt和参数，命中缓存。实现简单，但命中率低（因为用户的输入很少完全一样）。

2. 语义缓存（Semantic Cache）：不是精确匹配，而是语义相似就命中。用向量相似度判断两个请求是否语义相似。命中率比精确缓存高很多。

class SemanticCache:
    def __init__(self, embedding_model, threshold=0.95):
        self.embedding_model = embedding_model
        self.threshold = threshold  # 相似度阈值
        self.cache = {}  # key: embedding, value: response
        self.vectors = []  # 缓存的向量列表
    
    def get(self, prompt):
        """查询缓存，语义相似就命中"""
        embedding = self.embedding_model.encode(prompt)
        
        # 计算和所有缓存条目的相似度
        for cached_embedding, response in self.vectors:
            similarity = cosine_similarity(embedding, cached_embedding)
            if similarity >= self.threshold:
                return response  # 命中缓存
        
        return None  # 未命中
    
    def set(self, prompt, response):
        """写入缓存"""
        embedding = self.embedding_model.encode(prompt)
        self.vectors.append((embedding, response))

语义缓存的注意事项：

  • 相似度阈值要调好——太高命中率低，太低可能返回不相关的结果
  • 对于有"随机性"的请求（temperature>0），缓存的结果可能和新生成的不一样，需要考虑是否接受
  • 缓存要有过期时间，避免返回过时的信息
  • 对于涉及实时数据的请求（天气、股价），不应该缓存

3. 缓存层级：

  • L1：内存缓存（最快，但容量小，实例重启就没了）
  • L2：Redis缓存（较快，容量较大，分布式共享）
  • L3：向量数据库缓存（容量大，适合语义缓存）

六、成本控制与用量统计

6.1 用量统计

所有LLM调用都经过网关，可以在网关层统一统计用量：

  • 每个用户/每个API Key/每个功能的Token消耗量
  • 输入Token、输出Token分别统计
  • 每个模型的调用量和Token量
  • 缓存命中率（命中缓存能省多少Token）

用量数据存在时序数据库（Prometheus、InfluxDB）或数据仓库（BigQuery、ClickHouse），方便后续分析和报表。

6.2 成本估算

根据Token消耗量和各模型的单价，实时估算费用：

# 模型单价（每1K Token的价格，单位：美元）
MODEL_PRICING = {
    "gpt-4o": {"input": 0.005, "output": 0.015},
    "gpt-4o-mini": {"input": 0.00015, "output": 0.0006},
    "claude-3-opus": {"input": 0.015, "output": 0.075},
    "claude-3-sonnet": {"input": 0.003, "output": 0.015},
}

def estimate_cost(model, input_tokens, output_tokens):
    """估算LLM调用费用"""
    pricing = MODEL_PRICING.get(model)
    if not pricing:
        return 0
    
    input_cost = (input_tokens / 1000) * pricing["input"]
    output_cost = (output_tokens / 1000) * pricing["output"]
    return input_cost + output_cost

6.3 预算控制

设置预算限制，防止费用超支：

  • 每个用户/每个Key/每个功能的月度/日度预算
  • 预算使用率达到阈值（比如80%）时告警
  • 预算用完时，自动降级到更便宜的模型，或者限制请求

七、安全防护

7.1 密钥管理

LLM API Key统一存在网关里，下游服务不需要知道Key。网关转发请求时自动加上对应的Key。这样：

  • Key不会散落在各个服务里，减少泄露风险
  • Key轮换时只需要在网关里改，不需要改各个服务
  • 可以按功能/用户分配不同的Key，便于用量统计和权限隔离

密钥存在密钥管理服务（AWS KMS、HashiCorp Vault）里，不要硬编码在配置文件里。

7.2 输入过滤（Prompt注入防护）

Prompt注入是AI应用的特有安全问题——用户在输入中嵌入恶意指令，试图让模型忽略系统提示词，执行恶意操作。

网关层可以做输入过滤：

  • 检测输入中是否包含常见的Prompt注入模式（比如"忽略之前的指令"、"你现在是..."）
  • 对可疑输入做告警或拒绝
  • 对用户输入做转义或隔离（用特殊标记包裹用户输入，让模型区分系统指令和用户输入）

7.3 输出过滤

防止模型生成有害内容：

  • 检测输出中是否包含暴力、色情、违法、敏感信息
  • 对可疑输出做过滤、替换或拒绝
  • 可以用专门的内容安全API（OpenAI Moderation、阿里云内容安全）来检测

7.4 认证鉴权

网关作为统一入口，负责认证和鉴权：

  • 验证用户身份（JWT、API Key、OAuth2）
  • 检查用户是否有权限访问某个模型/功能
  • 记录每个请求的用户身份，用于审计和用量统计

八、协议转换与格式统一

不同LLM供应商的API格式不一样：

  • OpenAI用/v1/chat/completions，请求体有model、messages、temperature等字段
  • Anthropic用/v1/messages，请求体有model、messages、max_tokens等字段
  • 国内模型（通义、文心、智谱）的格式又各有不同

AI网关的一个重要功能是协议转换和格式统一：下游服务只需要用一种格式（比如OpenAI格式）调用网关，网关自动转换成对应模型的格式。这样下游服务不需要关心各个模型的API差异，切换模型也不需要改代码。

class ProtocolConverter:
    def convert_request(self, unified_request, target_model):
        """把统一格式的请求转换成目标模型的格式"""
        if target_model.startswith("gpt"):
            return self._to_openai_format(unified_request)
        elif target_model.startswith("claude"):
            return self._to_anthropic_format(unified_request)
        elif target_model.startswith("qwen"):
            return self._to_qwen_format(unified_request)
        else:
            raise ValueError(f"Unsupported model: {target_model}")
    
    def convert_response(self, raw_response, source_model):
        """把目标模型的响应转换成统一格式"""
        # 统一转换成OpenAI格式的响应
        return {
            "id": raw_response.get("id"),
            "model": source_model,
            "choices": [{
                "message": {
                    "role": "assistant",
                    "content": self._extract_content(raw_response, source_model)
                }
            }],
            "usage": self._extract_usage(raw_response, source_model)
        }

流式响应（Streaming）的协议转换更复杂，因为需要实时转换每个chunk的格式。但原理是一样的——把每个chunk从源模型格式转换成统一格式，再转发给客户端。

九、开源AI网关推荐

目前有一些开源的AI网关项目，可以直接使用或参考：

1. LiteLLM Proxy：最流行的开源LLM网关，支持100+模型的统一接口，支持负载均衡、故障转移、限流、缓存、成本跟踪。Python实现，部署简单。

2. Portkey：开源的AI网关，支持模型路由、负载均衡、缓存、可观测性、Prompt管理。有云服务和自托管版本。

3. Helicone：开源的LLM可观测性平台，也有网关功能。重点在可观测性——Trace、Metric、Log、成本分析。

4. One API：国内开发者做的开源LLM API管理系统，支持多种模型的统一接口，支持渠道管理、用量统计、令牌管理。适合国内模型的接入。

5. FastGPT Gateway：FastGPT团队开源的AI网关，支持模型路由、负载均衡、限流、缓存。和FastGPT集成好。

如果需求简单，可以直接用这些开源项目；如果有特殊需求，可以基于这些项目二次开发，或者自己实现一个轻量的网关。

十、总结

AI网关是生产级AI应用的标配组件，它解决了多模型管理、成本控制、稳定性保障、安全防护、可观测性等核心问题。

核心功能总结：

功能类别核心功能解决的问题
流量管理模型路由、负载均衡多模型统一管理，智能分配流量
稳定性故障转移、熔断、重试外部服务故障时保障可用
性能优化限流、缓存防止过载，降低延迟和成本
成本控制用量统计、成本估算、预算控制防止费用超支，优化成本
安全防护密钥管理、输入/输出过滤、认证鉴权保护API Key，防止恶意输入和有害输出
协议适配协议转换、格式统一、流式转发下游服务用统一接口，屏蔽模型差异
可观测性Trace、Metric、Log统一监控和排查问题

落地建议：

  1. 不要一上来就自己写网关：先用开源项目（LiteLLM、One API），满足基本需求。等有特殊需求了再二次开发或自己写。
  2. 先做核心功能：模型路由+统一格式+故障转移，这三个是最核心的，先做好。限流、缓存、成本控制等可以后续加。
  3. 可观测性先行：网关是所有LLM调用的入口，一定要在网关层做好Trace、Metric、Log，这对后续的排查和优化至关重要。
  4. 安全不能忽视：API Key统一管理、输入输出过滤、认证鉴权，这些安全功能要尽早做。
  5. 渐进式演进：从简单的代理开始，逐步增加路由、负载均衡、熔断、缓存等功能。不要一开始就追求大而全。

AI网关不是"锦上添花"，而是生产级AI应用的"必需品"。没有网关，AI应用的管理会非常混乱，成本、稳定性、安全都无法保障。尽早接入AI网关，能让你的AI应用更稳定、更省钱、更安全。
