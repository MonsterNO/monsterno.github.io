AI编程的上下文工程-让AI真正理解你的代码库

约 3397 字大约 11 分钟

AI编程

2026-09-01

AI写代码的质量，80%取决于它能看到什么。本文系统拆解AI编程中的上下文工程——上下文窗口的限制、代码检索策略、符号级理解、分层上下文设计、动态上下文管理，并给出可落地的实现方案。

一、为什么上下文工程是AI编程的核心问题

用AI编程工具的人都有这种体验：简单的函数补全，AI做得很好；但一旦涉及跨文件的修改、项目级的重构、理解整个代码库的架构，AI就开始"犯糊涂"——它会用错API、记错变量名、忽略依赖关系，生成的代码看起来对但跑不通。

问题的根源不是AI不够聪明，而是它看不到完整的代码库。

大模型的上下文窗口是有限的。即使是128K的窗口，也只能装下大概几万行代码——而一个中等规模的项目，代码量可能是几十万甚至上百万行。AI不可能把整个项目都"看"一遍。

这就是上下文工程要解决的问题：在有限的上下文窗口里，放入最相关、最有用的信息，让AI能准确理解你的代码库。

上下文工程做得好，AI生成的代码准确率能提升50%以上；做得不好，再强的模型也只能"瞎猜"。

二、上下文窗口的物理限制

在讲怎么优化之前，先理解上下文窗口的限制到底是什么。

2.1 Token和代码行数的换算

上下文窗口的单位是Token，不是行数。一般来说：

  • 1个Token ≈ 4个英文字符 ≈ 0.75个英文单词
  • 代码因为有大量符号和缩进，Token密度更高，1行代码大概需要2-3个Token

换算一下：

  • 4K窗口 ≈ 1500-2000行代码
  • 32K窗口 ≈ 12000-16000行代码
  • 128K窗口 ≈ 50000-65000行代码
  • 1M窗口 ≈ 400000-500000行代码

看起来128K窗口能装5万行代码，好像不少了。但实际上，你不能把整个窗口都用来放代码——还要放系统提示词、用户需求、对话历史、AI的思考过程。真正能用来放代码的，可能只有窗口的50-70%。

而且5万行代码听起来多，但一个中等规模的项目（比如一个Web应用的后端），代码量很容易就超过10万行。128K窗口连一个中等项目都装不下。

2.2 长上下文的"Lost in the Middle"问题

上下文窗口不是越长越好。研究发现，当上下文很长的时候，模型对放在中间的信息的注意力会下降——它能很好地记住开头和结尾的内容，但中间的内容容易被忽略。

这就是"Lost in the Middle"现象。它意味着，即使你能把5万行代码都塞进上下文，模型也不一定能"看到"所有内容——放在中间的代码可能被忽略。

这就要求我们在设计上下文的时候，不仅要考虑"放什么"，还要考虑"怎么排列"——把最重要的信息放在开头和结尾，次要的放在中间。

2.3 推理成本和延迟

上下文越长，推理成本越高，延迟越大。Transformer的自注意力计算复杂度是O(n²)，上下文从4K扩到128K，计算量增加了1000倍。这意味着：

  • 更长的上下文 = 更贵的API调用费用
  • 更长的上下文 = 更慢的响应速度

在实际使用中，你需要在"上下文完整性"和"成本/速度"之间找平衡。不是上下文越长越好，而是"刚好够用"最好。

三、代码检索策略：找到最相关的代码

上下文窗口有限，不可能放所有代码。那放哪些？答案是：放和当前任务最相关的代码。这就需要代码检索。

代码检索有几种主流策略：

3.1 语义检索（向量检索）

语义检索的思路是：把代码库中的每个文件/函数/类都转成向量，存到向量数据库里。用户提出需求后，把需求也转成向量，然后检索最相似的代码片段。

# 语义检索的简化实现
from sentence_transformers import SentenceTransformer
import chromadb

class CodeSemanticRetriever:
    def __init__(self, codebase_path):
        self.model = SentenceTransformer('BAAI/bge-large-code')
        self.client = chromadb.PersistentClient(path="./code_index")
        self.collection = self.client.get_or_create_collection("code_functions")
        self._index_codebase(codebase_path)
    
    def _index_codebase(self, path):
        """遍历代码库，提取函数/类，向量化后存储"""
        for file_path in traverse_code_files(path):
            functions = extract_functions(file_path)  # 提取函数定义
            for func in functions:
                embedding = self.model.encode(func['content'])
                self.collection.add(
                    ids=[f"{file_path}:{func['name']}"],
                    embeddings=[embedding.tolist()],
                    documents=[func['content']],
                    metadatas=[{"file": file_path, "function": func['name']}]
                )
    
    def retrieve(self, query, top_k=10):
        """根据用户需求检索相关代码"""
        query_embedding = self.model.encode(query)
        results = self.collection.query(
            query_embeddings=[query_embedding.tolist()],
            n_results=top_k
        )
        return results['documents'][0]

语义检索的优点是能理解"语义相似性"——比如用户说"用户登录"，它能检索到authenticate_user、login_handler等函数，即使名字不完全一样。

缺点是对精确的符号匹配（比如变量名、函数名）效果不好，而且检索的粒度不好控制——太粗了（整个文件）不精准，太细了（单行代码）没上下文。

3.2 符号检索（结构检索）

符号检索的思路是：利用代码的结构信息（AST、符号表），根据符号名称、类型、依赖关系来检索。

比如用户提到"用户登录"，符号检索会：

  1. 找到名称包含"login"或"auth"的函数/类
  2. 找到这些函数/类的定义和调用关系
  3. 找到相关的类型定义和导入

符号检索的优点是精确——能准确找到特定的函数、类、变量。缺点是只能按名称匹配，如果用户用的词和代码里的名称不一样，就检索不到。

3.3 混合检索

实际应用中，最好的策略是语义检索 + 符号检索的混合检索。

class HybridCodeRetriever:
    def __init__(self, semantic_retriever, symbol_retriever):
        self.semantic = semantic_retriever
        self.symbol = symbol_retriever
    
    def retrieve(self, query, top_k=15):
        # 1. 语义检索
        semantic_results = self.semantic.retrieve(query, top_k=10)
        
        # 2. 符号检索（从query中提取关键词）
        keywords = extract_code_keywords(query)
        symbol_results = self.symbol.retrieve(keywords, top_k=10)
        
        # 3. 合并去重，按相关性排序
        merged = merge_and_rank(semantic_results, symbol_results)
        return merged[:top_k]

混合检索能兼顾语义理解和符号精确，是目前效果最好的检索策略。Cursor等AI编程工具的代码检索，本质上就是混合检索。

四、分层上下文设计

检索到相关代码之后，怎么组织这些代码放进上下文？不是简单地堆在一起，而是需要分层设计。

4.1 三层上下文结构

我推荐的分层上下文结构是三层：

第一层：项目概览（Project Overview）

  • 项目的目录结构（目录树）
  • 技术栈和框架说明
  • 核心模块的简介
  • 代码规范和约定

这一层放在上下文的最开头，让AI对项目有整体的认识。内容不需要多，大概几百行就够了。

第二层：相关代码（Relevant Code）

  • 检索到的相关文件的完整内容
  • 相关的类型定义、接口定义
  • 相关的配置文件

这一层是上下文的核心，放在中间。内容根据任务复杂度调整，简单任务放几个文件，复杂任务放十几个文件。

第三层：当前任务（Current Task）

  • 用户的具体需求
  • 当前正在编辑的文件
  • 之前的对话历史
  • AI需要输出的格式要求

这一层放在上下文的最后，因为"Lost in the Middle"现象告诉我们，结尾的内容模型注意力最高。把当前任务放在最后，能确保AI聚焦在当前要做的事情上。

4.2 代码摘要：不相关但需要知道的文件

有些文件，AI不需要看完整内容，但需要知道它的存在和结构。比如：

  • 工具函数库：AI不需要看每个工具函数的实现，但需要知道有哪些可用的工具
  • 数据模型：AI不需要看每个字段的定义，但需要知道有哪些表/模型
  • API接口：AI不需要看每个接口的实现，但需要知道有哪些接口

对于这些文件，可以用代码摘要代替完整内容。代码摘要就是提取文件的核心结构（函数签名、类定义、文档字符串），去掉具体实现。

def generate_code_summary(file_path):
    """生成代码文件的摘要（只保留结构，去掉实现）"""
    ast_tree = parse_code(file_path)
    summary = []
    
    for node in ast_tree.body:
        if isinstance(node, FunctionDef):
            # 只保留函数签名和docstring，去掉函数体
            summary.append(f"def {node.name}({get_args(node)}):")
            if node.docstring:
                summary.append(f'    """{node.docstring}"""')
            summary.append("    ...")
        elif isinstance(node, ClassDef):
            summary.append(f"class {node.name}:")
            for item in node.body:
                if isinstance(item, FunctionDef):
                    summary.append(f"    def {item.name}({get_args(item)}): ...")
    
    return "\n".join(summary)

代码摘要能把一个几百行的文件压缩到几十行，同时保留核心结构信息。这样AI既能知道这个文件里有什么，又不会占用太多上下文空间。

五、动态上下文管理

上下文不是一成不变的，应该根据任务的进展动态调整。

5.1 任务阶段感知

不同的任务阶段，需要的上下文不一样：

理解阶段：AI需要理解需求和代码结构，这时候需要更多的项目概览和相关代码。 实现阶段：AI需要写具体代码，这时候需要更多的当前文件内容和相关的API定义。 调试阶段：AI需要定位bug，这时候需要更多的错误信息、日志、相关的调用链。

动态上下文管理会根据当前阶段，自动调整上下文的内容和比例。

5.2 上下文压缩

随着对话进行，上下文会越来越长（历史对话越来越多）。这时候需要做上下文压缩——把旧的对话历史压缩成摘要，腾出空间给新的内容。

def compress_conversation_history(history, max_turns=10):
    """压缩对话历史，保留最近N轮，更早的压缩成摘要"""
    if len(history) <= max_turns:
        return history
    
    # 更早的对话压缩成摘要
    old_history = history[:-max_turns]
    summary = summarize_conversation(old_history)  # 用AI生成摘要
    
    # 最近的对话保留完整
    recent_history = history[-max_turns:]
    
    return [{"role": "system", "content": f"之前的对话摘要：{summary}"}] + recent_history

上下文压缩能在有限的窗口里保留更多的有效信息，避免因为对话太长而"忘记"早期的需求。

六、工程实现：构建一个上下文管理器

把上面的策略组合起来，一个完整的上下文管理器大概长这样：

class ContextManager:
    def __init__(self, codebase_path, llm):
        self.codebase_path = codebase_path
        self.llm = llm
        self.retriever = HybridCodeRetriever(
            semantic_retriever=CodeSemanticRetriever(codebase_path),
            symbol_retriever=CodeSymbolRetriever(codebase_path)
        )
        self.project_overview = self._build_project_overview()
        self.conversation_history = []
    
    def build_context(self, user_query, current_file=None, task_phase="implementation"):
        """构建完整的上下文"""
        context_parts = []
        
        # 1. 系统提示词
        context_parts.append(self._build_system_prompt())
        
        # 2. 项目概览（第一层）
        context_parts.append(f"## 项目概览\n{self.project_overview}")
        
        # 3. 相关代码（第二层）
        relevant_code = self._get_relevant_code(user_query, current_file, task_phase)
        context_parts.append(f"## 相关代码\n{relevant_code}")
        
        # 4. 对话历史（压缩后的）
        compressed_history = compress_conversation_history(self.conversation_history)
        context_parts.append(f"## 对话历史\n{compressed_history}")
        
        # 5. 当前任务（第三层，放在最后）
        current_task = self._build_current_task(user_query, current_file)
        context_parts.append(f"## 当前任务\n{current_task}")
        
        # 6. 检查总长度，如果超了就进一步压缩
        full_context = "\n\n".join(context_parts)
        if count_tokens(full_context) > MAX_CONTEXT_TOKENS:
            full_context = self._aggressive_compress(full_context)
        
        return full_context
    
    def _get_relevant_code(self, query, current_file, task_phase):
        """获取相关代码"""
        # 检索相关文件
        relevant_files = self.retriever.retrieve(query, top_k=15)
        
        # 根据任务阶段调整：理解阶段放更多文件，实现阶段放更少但更完整
        if task_phase == "understanding":
            # 理解阶段：放摘要，能放更多文件
            return "\n\n".join([generate_code_summary(f) for f in relevant_files])
        else:
            # 实现阶段：放完整内容，但只放最相关的几个文件
            top_files = relevant_files[:5]
            if current_file and current_file not in top_files:
                top_files.insert(0, current_file)
            return "\n\n".join([read_file(f) for f in top_files])

这个上下文管理器综合了：分层上下文、混合检索、代码摘要、动态阶段感知、上下文压缩。实际使用中，能显著提升AI生成代码的准确率。

七、总结

AI编程的上下文工程，核心是在有限的上下文窗口里，放入最相关、最有用的信息。几个关键原则：

  1. 检索是基础：用混合检索（语义+符号）找到最相关的代码
  2. 分层是关键：项目概览→相关代码→当前任务，三层结构，重要信息放开头和结尾
  3. 摘要是手段：不相关但需要知道的文件用摘要，节省上下文空间
  4. 动态是进阶：根据任务阶段和对话进展，动态调整上下文内容
  5. 压缩是保障：对话历史太长时及时压缩，避免"忘记"早期需求

上下文工程是AI编程中最有价值的投入之一。把上下文做好了，即使是中等水平的模型，也能生成高质量的代码；上下文做不好，再强的模型也只能"瞎猜"。

未来随着上下文窗口越来越大，上下文工程的重要性会不会下降？我认为不会。窗口越大，能放的信息越多，但"放什么、怎么放"的问题反而更重要——你不可能把整个互联网都塞进上下文，选择和组织永远是必要的。上下文工程不是过渡技术，而是AI编程的核心能力。
