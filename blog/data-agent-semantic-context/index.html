数据智能体，先补好语义上下文

约 883 字大约 3 分钟

数据智能体AI助手数据分析

2026-08-10

摘要： 数据智能体要先理解公司怎样定义指标，随后才轮到生成 SQL。

业务问“本月新增客户多少”，数据智能体很快写出 SQL，结果比财务报表高出一倍。它把试用账号算成客户，也没排除内部测试组织。查询语法没错，回答还是错了。

很多数据智能体 Demo 先展示自然语言转 SQL。真的放进公司以后，SQL 写出来并不难，麻烦常常出在“客户”这个词没人讲清楚。

表结构不等于业务含义

数据库能告诉模型字段叫 created_at，却不会解释退款发生后收入是否回溯，或者“活跃客户”按登录还是付费计算。这些定义通常散在 BI 指标、代码、文档和分析师经验里。

OpenAI 在介绍内部数据智能体时，把上下文分成表使用信息、人工注释、代码含义、机构知识、记忆和运行时上下文。这个设计很有启发：模型先拿到可信的语义，再决定查什么。

metric: new_paying_customers
definition: 首次完成有效付款的外部组织数
exclude:
  - internal_org = true
  - payment_status != succeeded
timeField: first_successful_payment_at
owner: revenue-analytics

比起在提示词里写一句“请按公司口径计算”，这份定义更容易维护，也能被评测程序读取。

给表和指标加上来源

语义上下文也会过期。指标定义需要负责人、更新时间和适用范围。数据智能体引用口径时，把来源一起返回。出现冲突时，优先使用经过审核的语义层，不要自己把两份定义揉成一份。

SQL 执行前还可以做静态检查：是否带租户过滤，是否扫描超大分区，是否访问敏感列。只读账号是基本配置，导出明细和修改数据需要另外的工具与审批。

def validate_query(query, user):
    require_read_only(query)
    require_tenant_filter(query, user.tenant_id)
    block_columns(query, ["id_card", "phone", "email"])

这几行规则不会理解业务，却能拦下一些很实际的问题。

让智能体承认口径不够

数据问题最怕一个数字顺滑地出现。查不到正式定义时，智能体应把疑问说出来，例如“新增客户是注册还是首次付费”。追问一次，比返回一张漂亮但口径错误的图便宜。

评测也要用真实歧义。准备一些同名指标、跨时区、退款回溯和权限受限的问题，检查智能体有没有选对定义、引用来源，并在信息不足时停下来。

我会从分析师最常被重复问的十个指标开始，先整理定义，再接数据库。顺序慢一点，但第一个答案就有机会对齐现有报表。直接让模型探索几百张表看起来很聪明，最后往往还得回头补这层语义。

数据智能体能省下写 SQL 的时间，也能把公司已有的指标知识变成可以查询、引用和维护的上下文。这个地基稳了，模型换一代也不至于从头猜。
