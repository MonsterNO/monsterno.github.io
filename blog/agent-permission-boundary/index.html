AI智能体权限，别只靠确认弹窗

约 929 字大约 3 分钟

AI智能体AI安全权限治理

2026-08-10

摘要： 权限弹窗只能处理最后一步，前面的沙箱和工具边界更重要。

一个智能体连续弹出十次确认：读取配置、运行测试、访问网络、写入文件。前两次还会认真看，后面多半只想赶紧点完。这不是用户不重视安全，是确认太频繁以后，弹窗本身已经失去信息量。

现在的智能体能读仓库、跑命令、操作浏览器，也能连接公司里的各种工具。权限设计如果仍停在“每次都问一下”，体验会很累，安全也未必更好。

先把活动范围缩小

确认适合处理少量、清楚、不可逆的动作，例如发布生产版本或删除云资源。日常读文件、运行本地测试，不该每一步都把判断推给用户。

更基础的一层是沙箱。智能体只能看到任务需要的目录，网络默认关闭或使用域名白名单，密钥也不要直接出现在模型上下文里。这样即使模型判断错了，影响范围仍有限。

可以把权限策略写成配置，而不是散落在提示词中：

workspace:
  read: ["src/**", "tests/**", "package.json"]
  write: ["src/**", "tests/**"]
network:
  default: deny
  allow:
    - registry.npmjs.org
commands:
  allow: ["npm test", "npm run lint"]
  requireApproval: ["npm publish", "git push"]

提示词里的“请小心操作”没有强制力，这份策略却能在命令真正执行前拦住它。

弹窗里只放值得人判断的事

一个好确认应该说清楚准备做什么、影响什么，以及有没有退路。“是否允许执行命令”太笼统；“是否把 v2.3.0 发布到公开 npm 仓库，发布后无法覆盖同版本”就具体得多。

OpenAI 和 Anthropic 在各自的智能体安全实践里，都把边界、审批和遥测放在一起看。原因很实际：只限制权限，会让正常工作处处受阻；只记录日志，出事时已经晚了；只弹确认，人又很容易疲劳。

我的理解是，低风险动作交给确定性规则，高风险动作留给人。中间那一段可以看工具、目标环境和数据敏感度，再决定是否自动放行。

function needsApproval(action: Action) {
  if (action.environment === "production") return true;
  if (action.kind === "delete" || action.kind === "publish") return true;
  return action.riskScore >= 70;
}

这不是一条放之四海皆准的分数线。重点是让审批条件可读、可测试，也能在事故复盘后修改。

日志要能还原当时的权限

智能体出错以后，只看到它运行了 deploy 还不够。还要知道当时使用了哪个身份、拿到哪些工具、谁批准了动作，以及策略版本是什么。否则同一个问题过几天再查，权限配置已经变化，很难还原现场。

可以先从一个小地方动手：把工具列表从“全部可用”改成按任务发放。写文档的智能体通常不需要生产数据库，代码审查智能体也没必要拥有发布权限。工具少一点，模型选错的机会也会少一点。

弹窗仍然有用，只是别让它扛下整套安全系统。真正让人安心的，是弹窗出现之前，智能体已经被放在一个不容易闯大祸的空间里。
