别只看最终答案-Agent轨迹分析评测

约 2223 字大约 7 分钟

AI智能体

2026-09-01

Agent答错了，到底是哪一步出了问题？本文从一次线上故障出发，介绍为什么传统评测方法对Agent失效，以及如何用轨迹分析定位Agent的真实问题。

上个月我们的客服Agent出了个线上故障：有用户反馈，问"我的退款到账了吗"，Agent回复说"您的退款已原路退回，请查收"，但实际上用户根本没申请过退款。

我们第一反应是模型回答错了，于是去看日志。结果发现模型没答错——它调用了一个叫get_refund_status的工具，工具返回了"已退款"，模型只是如实转述。问题出在工具调用上：Agent把用户ID传错了，查成了另一个人的退款记录。

如果只看最终答案，你会觉得是模型在胡说八道。但看完整执行轨迹，你会发现问题出在工具参数那一步。这就是Agent评测和传统大模型评测最大的区别：Agent的答案是"过程的产物"，只看结果根本定位不了问题。

传统评测为什么对Agent失效

评测普通大模型很简单：准备一批问题和标准答案，让模型回答，然后对比答案对不对。准确率、BLEU、ROUGE这些指标就够用了。

但Agent不一样。Agent的回答不是"直接生成"的，而是经过了"思考→规划→调用工具→获取结果→整理回答"这一长串过程。最终答案错了，可能的原因有很多：

  • 规划错了：该调用A工具，它调用了B工具
  • 参数错了：工具选对了，但参数传错了（就像上面的例子）
  • 工具本身错了：工具返回了错误数据
  • 结果解读错了：工具返回了正确数据，但模型理解错了
  • 最终表达错了：前面都对，最后组织语言时说错了

这五种错误，最终表现都是"答案不对"，但修复方式完全不同。规划错了要改提示词，参数错了要加参数校验，工具错了要修工具代码，解读错了要优化结果格式，表达错了要调输出模板。只看最终答案，你根本不知道该改哪里。

这就是为什么我说：Agent评测的核心不是"答案对不对"，而是"过程对不对"。

怎么看执行轨迹

要做轨迹分析，首先得把Agent的每一步都记录下来。一个完整的轨迹应该包含：

  1. 用户输入：用户说了什么
  2. 思考过程：Agent的推理（如果用了ReAct模式，会有Thought字段）
  3. 工具调用：调用了哪个工具、传了什么参数
  4. 工具返回：工具返回了什么结果
  5. 最终回答：Agent给用户的最终回复

每一步都要有时间戳，这样你还能分析每一步花了多长时间。

我们用LangSmith来做轨迹记录和分析（也可以用LangFuse，开源的）。接入很简单：

pip install langsmith

设置环境变量：

import os
os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_API_KEY"] = "your-api-key"
os.environ["LANGCHAIN_PROJECT"] = "customer-service-agent"

设置好之后，你用LangChain写的Agent每一次运行都会自动记录完整轨迹。在LangSmith的界面里，你能看到像时间线一样的执行过程：哪一步调用了什么工具、传了什么参数、返回了什么、花了多长时间，一目了然。

如果你不用LangChain，也可以自己埋点。核心就是在Agent的每个关键节点打日志：

import json
from datetime import datetime

class TrajectoryLogger:
    def __init__(self):
        self.trace = []
    
    def log(self, step_type, content, metadata=None):
        """记录一步执行"""
        entry = {
            "step": step_type,
            "content": content,
            "metadata": metadata or {},
            "timestamp": datetime.now().isoformat()
        }
        self.trace.append(entry)
        print(f"[{step_type}] {json.dumps(content, ensure_ascii=False)[:200]}")
    
    def get_full_trace(self):
        """获取完整轨迹"""
        return self.trace
    
    def save(self, filepath):
        """保存轨迹到文件"""
        with open(filepath, "w", encoding="utf-8") as f:
            json.dump(self.trace, f, ensure_ascii=False, indent=2)

# 使用示例
logger = TrajectoryLogger()

def agent_run(user_input):
    logger.log("user_input", {"text": user_input})
    
    # 思考阶段
    thought = "用户问退款状态，需要调用get_refund_status工具"
    logger.log("thought", {"text": thought})
    
    # 工具调用阶段
    tool_name = "get_refund_status"
    tool_params = {"user_id": "U12345", "order_id": "O67890"}
    logger.log("tool_call", {"tool": tool_name, "params": tool_params})
    
    # 工具返回
    tool_result = {"status": "已退款", "amount": 99.0, "refund_time": "2026-08-30"}
    logger.log("tool_result", {"result": tool_result})
    
    # 最终回答
    final_answer = "您的退款已原路退回，金额99元，请查收。"
    logger.log("final_answer", {"text": final_answer})
    
    logger.save(f"./traces/{datetime.now().strftime('%Y%m%d%H%M%S')}.json")
    return final_answer

有了完整轨迹，你就能做精准的问题定位了。

轨迹分析的几个实用方法

记录轨迹只是第一步，真正有价值的是从轨迹里发现问题。我常用的几个方法：

按错误类型分类统计。 把所有失败的case拿出来，逐条看轨迹，给每个失败case打上标签：规划错误、参数错误、工具错误、解读错误、表达错误。统计下来你就知道，你的Agent最大的问题出在哪一环。我们统计过，参数错误占了40%，是最大的问题来源——于是我们给所有工具加了参数校验层，错误率直接降了一半。

看工具调用的"浪费"。 有些Agent会调用很多不必要的工具，比如用户只问了个简单问题，它却调用了3个工具才回答。这不仅浪费Token，还增加了出错概率。通过轨迹分析，你能发现哪些工具调用是多余的，然后优化提示词减少冗余调用。我们有个Agent平均每次对话调用2.8个工具，优化后降到了1.5个，成本降了近一半。

追踪"差点错了"的case。 不要只看最终答错的，还要看那些"过程中出了问题但最终蒙对了"的case。比如Agent调用工具时参数传错了，但工具刚好返回了一个不影响结论的结果，最终答案看起来是对的。这种case是定时炸弹——这次蒙对了，下次不一定。通过轨迹分析能把这些"隐形错误"揪出来。

做A/B测试的轨迹对比。 改了提示词之后，不要只看最终准确率有没有提升，还要对比轨迹：工具调用次数有没有减少？错误类型有没有变化？平均响应时间有没有变长？有时候最终准确率提升了，但工具调用次数增加了50%，成本反而更高了，这就不一定是好的优化。

我的一些思考

做Agent评测越久，我越觉得：Agent的质量不是"测"出来的，是"看"出来的。

传统软件测试，你写一堆自动化用例，跑一遍全绿就放心了。但Agent不行——同样的输入，这次对了下次可能错；最终答案对了，过程可能全是问题。你必须一条一条看轨迹，像看监控录像一样，看Agent每一步在干什么、为什么这么干。

这很花时间，但没办法。Agent的行为太复杂了，目前还没有什么自动化指标能替代人工看轨迹。我们团队现在的做法是：每天随机抽20条轨迹人工review，每周做一次错误类型统计，每月做一次全面的轨迹分析报告。这个节奏比较合理，不会太累，但能持续发现问题。

另一个感受是：轨迹分析会反过来指导你的架构设计。比如你通过轨迹发现，参数错误特别多，那你就应该在工具层加参数校验，而不是反复改提示词；如果你发现工具返回结果的格式经常被模型理解错，那你就应该把工具返回格式改得更简单，而不是指望模型"聪明一点"。轨迹分析告诉你的不是"哪里错了"，而是"该在哪里修"。

最后说一句：很多团队做Agent，只关注最终效果，不看过程。这就像考试只看分数，不看错题本——分数可能偶尔很高，但你永远不知道问题在哪。轨迹分析就是Agent的"错题本"，它不会让你的Agent立刻变聪明，但能让你知道它为什么笨、怎么才能不笨。

如果你也在做Agent，建议从今天开始记录每一条执行轨迹。不用搞很复杂，就把每一步的输入输出打日志存下来。然后每周花半小时，随机看几条。相信我，你会发现很多之前完全没意识到的问题。
