AI模型路由，别只按单价切换

约 822 字大约 3 分钟

大模型模型路由AI开发平台

2026-08-10

摘要： 模型路由要看完成一次任务花多少，不能只比较百万 Token 单价。

团队为了省成本，把所有摘要任务切到最便宜的模型。单次调用确实便宜了，客服工单却经常漏掉关键退款原因，只能再让大模型重做。月底一算，Token 费用下降不多，处理时间还变长了。

模型路由听起来像“简单问题用小模型，难问题用大模型”。真正上线后，难点在于系统怎么知道这次问题简单。

先给任务分出可验证的类型

不要让路由器只读用户一句话后凭感觉选模型。可以根据任务类型、输入长度、工具需求和风险做第一层判断。固定分类、字段抽取适合小模型；跨文档推理、高风险写操作使用更强模型，并保留验证。

function route(task: Task) {
  if (task.risk === "high") return "reasoning-model";
  if (task.needsTools || task.inputTokens > 50_000) return "agent-model";
  if (task.kind === "classification") return "small-model";
  return "balanced-model";
}

模型名字会变，路由规则最好依赖能力标签，不要把业务代码写死在某个版本号上。

失败升级要算进成本

小模型第一次失败，再调用大模型，付出的是两次推理和更长等待。真正该比较的是“每个成功任务的成本”。

成功任务成本 = 总模型费用 / 通过质量门槛的任务数

还可以记录升级率。某类任务有一半都会升级，直接使用更强模型可能更省。OpenAI 在 2026 年关于 Agent 时代投入的文章里，也建议按结果和工作流价值看效率，Token 单价只是其中一项。

质量门槛尽量用程序验证。结构化抽取检查 Schema 和业务范围，代码任务运行测试，RAG 回答检查引用。验证失败才升级，路由会比“让另一个模型判断难不难”更稳定一些。

延迟和容量也是路由条件

批量夜间任务可以用异步或低优先级容量，在线客服则更关心首字延迟。模型暂时不可用时要有回退，但回退模型的上下文长度、工具格式和安全能力必须兼容。

我会给每条路由规则留一个原因字段。排查时知道它因为“高风险”进入强模型，还是因为输入太长被迫切换。规则修改后用历史任务回放，看看成本降了多少，质量有没有在某类用户上掉下去。

模型路由的价值不是把每次请求压到最低价。它更像安排工作：简单的事别占用最稀缺的人，复杂的事也别为了省一点时间反复返工。把完成率、延迟和升级次数放在一起，选择才会接近真实成本。
