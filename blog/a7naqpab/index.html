AI应用的可观测性体系-Trace-Metric-Log的设计与实现

约 4465 字大约 15 分钟

AI应用的可观测性体系

2026-09-01

LLM应用出了问题，怎么排查？本文系统拆解AI应用可观测性的三大支柱——Trace（链路追踪）、Metric（指标监控）、Log（日志记录），讲清每个支柱需要采集什么数据、怎么采集、怎么用，并给出可落地的实现方案。

一、为什么AI应用的可观测性更重要

传统应用出了问题，排查路径相对清晰——看错误日志、查数据库、复现请求。但AI应用的问题排查要困难得多，原因有几个：

1. 输出不确定：同样的输入，LLM可能返回不同的输出。用户说"回答不对"，你可能根本复现不出来——因为LLM的输出有随机性，同样的请求再发一次，结果可能就对了。

2. 链路长：一个AI应用的请求，可能经过了API网关、对话服务、RAG检索、Prompt组装、LLM调用、输出后处理等多个环节。任何一个环节出问题，都可能导致最终结果不对。没有完整的链路追踪，根本不知道问题出在哪。

3. 问题类型多：AI应用的问题不只是"报错"，还包括：

  • 回答质量差（答非所问、幻觉、逻辑错误）
  • 延迟高（用户等了很久才出结果）
  • 成本超支（Token消耗异常，费用暴涨）
  • 安全问题（Prompt注入、有害输出）
  • 检索不准（RAG没检索到相关文档）

这些问题不是传统的"错误"，不会抛异常，但用户体验很差。没有完善的可观测性，这些问题根本发现不了。

4. 依赖外部服务：AI应用严重依赖外部LLM API（OpenAI、Anthropic、通义等）。这些外部服务的故障、限流、延迟波动，都会直接影响应用。需要监控外部服务的状态，及时发现和切换。

因为这些特殊性，AI应用的可观测性比传统应用更重要、也更复杂。本文系统拆解AI应用可观测性的设计与实现。

二、可观测性的三大支柱

可观测性（Observability）的概念来自控制论，在软件领域通常指通过系统的外部输出来推断内部状态。三大支柱是：

  • Log（日志）：记录离散的事件，包含详细的上下文信息
  • Metric（指标）：记录可聚合的数值，用于监控趋势和告警
  • Trace（追踪）：记录请求的完整链路，用于排查性能问题和错误定位

三者不是孤立的，而是互相补充、互相联动的。下面逐个拆解。

三、Trace：链路追踪

Trace是AI应用可观测性中最核心的部分。因为AI应用的链路长、环节多，出了问题首先需要知道"请求经过了哪些环节、每个环节花了多久、哪个环节出了问题"。

3.1 Trace的基本概念

Trace（追踪）：一次完整的请求，从用户输入到最终返回的全过程。

Span（跨度）：Trace中的一个操作单元，比如一次RAG检索、一次LLM调用、一次数据库查询。每个Span有开始时间、结束时间、名称、标签。

一个典型的AI应用请求的Trace结构：

Trace: 用户提问"我的订单到哪了"
├── Span: API网关（认证+限流） 2ms
├── Span: 对话服务（处理请求）
│   ├── Span: 检索对话历史 5ms
│   ├── Span: RAG检索
│   │   ├── Span: 向量检索 80ms
│   │   ├── Span: 重排序 120ms
│   │   └── Span: 上下文组装 5ms
│   ├── Span: Prompt组装 3ms
│   ├── Span: LLM调用
│   │   ├── Span: 首Token延迟 800ms
│   │   └── Span: 完整生成 2500ms
│   └── Span: 输出后处理 10ms
└── Span: 返回响应 1ms

通过这个Trace，你能清楚地看到：

  • 总耗时是多少
  • 每个环节花了多久（瓶颈在哪）
  • RAG检索花了205ms，LLM调用花了2500ms（LLM是主要瓶颈）
  • 如果出错了，是哪个Span报的错

3.2 AI应用需要记录的关键Span

不是所有操作都需要记录成Span，重点记录以下关键环节：

1. LLM调用Span：这是最重要的Span，需要记录：

  • 模型名称（gpt-4o、qwen-max等）
  • 输入Token数、输出Token数、总Token数
  • 首Token延迟（Time to First Token, TTFT）
  • 完整生成耗时
  • 温度（temperature）、top_p等参数
  • 输入内容（Prompt）和输出内容（Completion）
  • 错误信息（如果失败）
  • 费用估算

2. RAG检索Span：记录：

  • 检索方式（向量检索、关键词检索、混合检索）
  • 检索到的文档数量和相似度分数
  • 重排序后的Top-K文档
  • 检索耗时
  • 检索的查询文本

3. 工具调用Span（Agent场景）：记录：

  • 工具名称
  • 工具参数
  • 工具返回结果
  • 工具执行耗时
  • 工具调用是否成功

4. Prompt组装Span：记录：

  • 使用的Prompt模板名称和版本
  • 注入的变量
  • 最终组装的完整Prompt
  • 上下文长度（Token数）

5. 对话历史Span：记录：

  • 检索到的历史轮数
  • 历史压缩方式（如果做了压缩）
  • 压缩后的Token数

3.3 Trace的实现方案

主流的实现方案是OpenTelemetry + Jaeger/Tempo。

OpenTelemetry（OTel）是一个开放的可观测性标准，提供了统一的API和SDK来采集Trace、Metric、Log。Jaeger和Tempo是Trace的后端存储和可视化工具。

Python实现示例（用OpenTelemetry + LangChain的自动instrumentation）：

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.instrumentation.langchain import LangChainInstrumentor

# 初始化Trace Provider
trace.set_tracer_provider(TracerProvider())
tracer_provider = trace.get_tracer_provider()

# 配置OTLP导出器（导出到Jaeger/Tempo）
otlp_exporter = OTLPSpanExporter(endpoint="http://jaeger:4317")
tracer_provider.add_span_processor(BatchSpanProcessor(otlp_exporter))

# 自动instrument LangChain（自动记录LLM调用、Chain、Tool等Span）
LangChainInstrumentor().instrument()

# 自定义Span示例
tracer = trace.get_tracer(__name__)

def process_user_query(query):
    with tracer.start_as_current_span("process_user_query") as span:
        span.set_attribute("user.query", query)
        
        # RAG检索
        with tracer.start_as_current_span("rag_retrieval") as rag_span:
            docs = retrieve_documents(query)
            rag_span.set_attribute("rag.doc_count", len(docs))
            rag_span.set_attribute("rag.top_score", docs[0].score if docs else 0)
        
        # LLM调用
        with tracer.start_as_current_span("llm_call") as llm_span:
            response = call_llm(query, docs)
            llm_span.set_attribute("llm.model", "gpt-4o")
            llm_span.set_attribute("llm.input_tokens", response.usage.prompt_tokens)
            llm_span.set_attribute("llm.output_tokens", response.usage.completion_tokens)
            llm_span.set_attribute("llm.total_tokens", response.usage.total_tokens)
            llm_span.set_attribute("llm.cost", estimate_cost(response.usage))
        
        return response

LangChain和LlamaIndex都有OpenTelemetry的自动instrumentation，能自动记录LLM调用、Chain执行、工具调用等Span，不需要手动写太多代码。

3.4 Trace的使用场景

有了Trace，你能做什么？

1. 性能瓶颈定位：看哪个Span耗时最长，针对性优化。比如发现LLM调用占了80%的时间，就可以考虑用更快的模型、加缓存、优化Prompt长度。

2. 错误定位：请求失败了，看Trace里哪个Span报错，错误信息是什么。比如发现是RAG检索的向量数据库超时了，就知道问题不在LLM而在向量库。

3. 质量排查：用户说回答不对，找到对应的Trace，看Prompt是什么、检索到了什么文档、LLM返回了什么。能完整复现用户的请求，排查问题。

4. 成本分析：看每个请求的Token消耗和费用，找出成本最高的请求类型，针对性优化（比如缩短Prompt、用更便宜的模型、加缓存）。

四、Metric：指标监控

Trace记录的是每次请求的详细信息，适合排查具体问题。但你不可能每次都一条条看Trace——需要聚合的指标来监控整体趋势、发现异常、设置告警。这就是Metric的作用。

4.1 AI应用需要监控的关键指标

AI应用的指标可以分为几类：

1. 流量指标

  • 请求量（QPS/RPM）：每分钟/每秒请求数
  • 并发用户数
  • 按模型、按功能、按用户分群的请求量

2. 延迟指标

  • 总延迟（端到端）：P50、P95、P99
  • LLM首Token延迟（TTFT）：P50、P95、P99
  • LLM完整生成延迟：P50、P95、P99
  • RAG检索延迟：P50、P95、P99
  • 各环节延迟占比

3. 质量指标

  • 成功率（HTTP 2xx占比）
  • 错误率（按错误类型分：超时、限流、模型错误、系统错误）
  • 回答质量评分（如果有用户反馈或自动评估）
  • 幻觉率（如果有自动检测）
  • 检索命中率（RAG检索到相关文档的比例）

4. 成本指标

  • Token消耗总量（输入/输出/总计）
  • 费用总量（按模型、按功能、按用户分群）
  • 单次请求平均费用
  • 缓存命中率（命中缓存能省多少钱）
  • 预算使用率（当前费用/月度预算）

5. 模型指标

  • 各模型的调用量占比
  • 各模型的延迟对比
  • 各模型的错误率对比
  • 模型切换次数（故障转移的次数）

6. 业务指标

  • 日活/月活用户数
  • 用户留存率
  • 平均对话轮数
  • 用户满意度（点赞/点踩比例）
  • 功能使用率（各功能模块的使用占比）

4.2 Metric的实现方案

主流方案是Prometheus + Grafana。

Prometheus是时序数据库，用来存储和查询指标。Grafana是可视化工具，用来做Dashboard和告警。

Python实现示例（用Prometheus客户端）：

from prometheus_client import Counter, Histogram, Gauge, start_http_server
import time

# 定义指标
REQUEST_COUNT = Counter(
    'ai_app_requests_total',
    'Total number of requests',
    ['model', 'feature', 'status']
)

REQUEST_LATENCY = Histogram(
    'ai_app_request_duration_seconds',
    'Request duration in seconds',
    ['model', 'feature'],
    buckets=(0.1, 0.5, 1, 2, 5, 10, 30, 60)
)

LLM_TOKEN_USAGE = Counter(
    'ai_app_llm_tokens_total',
    'Total LLM token usage',
    ['model', 'token_type']  # token_type: input/output
)

LLM_COST = Counter(
    'ai_app_llm_cost_total',
    'Total LLM cost in USD',
    ['model']
)

CACHE_HIT = Counter(
    'ai_app_cache_hits_total',
    'Total cache hits',
    ['cache_type']  # cache_type: prompt/semantic/rag
)

# 启动Prometheus metrics server（默认9090端口）
start_http_server(9090)

# 在请求处理中记录指标
def process_request(query, model="gpt-4o"):
    start_time = time.time()
    try:
        # ... 处理逻辑 ...
        response = call_llm(query, model)
        
        # 记录指标
        REQUEST_COUNT.labels(model=model, feature="chat", status="success").inc()
        REQUEST_LATENCY.labels(model=model, feature="chat").observe(time.time() - start_time)
        LLM_TOKEN_USAGE.labels(model=model, token_type="input").inc(response.usage.prompt_tokens)
        LLM_TOKEN_USAGE.labels(model=model, token_type="output").inc(response.usage.completion_tokens)
        LLM_COST.labels(model=model).inc(estimate_cost(model, response.usage))
        
        return response
    except Exception as e:
        REQUEST_COUNT.labels(model=model, feature="chat", status="error").inc()
        raise

4.3 告警规则

有了指标，就要设置告警，在异常发生时及时通知。关键的告警规则：

延迟告警：

  • P99延迟超过阈值（比如总延迟>30s，TTFT>5s）
  • 延迟突然升高（比上周同期高50%以上）

错误告警：

  • 错误率超过阈值（比如5分钟内错误率>10%）
  • 某个模型的错误率突然升高（可能是模型服务故障）
  • 限流错误增多（可能是API配额不够）

成本告警：

  • 日费用超过预算的1/30（日均预算）
  • 单次请求费用异常高（比如超过$1）
  • Token消耗突然飙升（可能是死循环或异常请求）

质量告警：

  • 用户点踩率突然升高
  • 检索命中率下降
  • 幻觉率升高（如果有自动检测）

资源告警：

  • GPU/CPU使用率过高
  • 内存不足
  • 向量数据库查询延迟升高

告警通道可以用邮件、短信、飞书/钉钉/企业微信机器人、PagerDuty等。

五、Log：日志记录

Log是最基础、最详细的可观测性手段。Trace和Metric都是聚合或结构化的，而Log可以记录任意详细的信息，是排查具体问题的"最后一道防线"。

5.1 AI应用需要记录的关键日志

1. 请求日志：每次请求的完整信息

  • 请求ID（Trace ID，用于关联Trace和Log）
  • 用户ID、会话ID
  • 用户输入
  • 时间戳
  • 客户端信息（IP、User-Agent）

2. LLM调用日志：

  • 模型名称、参数（temperature、top_p、max_tokens等）
  • 完整的Prompt（包括系统提示词、用户输入、检索到的上下文）
  • 完整的输出（Completion）
  • Token消耗（输入/输出/总计）
  • 耗时（TTFT、总耗时）
  • 费用
  • 错误信息（如果失败）

3. RAG检索日志：

  • 检索查询文本
  • 检索到的文档列表（文档ID、标题、相似度分数、内容摘要）
  • 重排序后的结果
  • 检索耗时

4. 工具调用日志（Agent场景）：

  • 工具名称、参数
  • 工具返回结果
  • 执行耗时
  • 错误信息

5. 系统日志：

  • 服务启动/停止
  • 配置变更
  • 模型切换
  • 缓存命中/未命中
  • 限流触发
  • 熔断触发

5.2 日志的最佳实践

1. 结构化日志：用JSON格式记录日志，而不是纯文本。结构化日志方便检索、过滤、分析。

import logging
import json
from pythonjsonlogger import jsonlogger

# 配置结构化日志
logger = logging.getLogger()
handler = logging.StreamHandler()
formatter = jsonlogger.JsonFormatter(
    "%(asctime)s %(levelname)s %(trace_id)s %(user_id)s %(message)s"
)
handler.setFormatter(formatter)
logger.addHandler(handler)

# 记录日志
logger.info(
    "LLM call completed",
    extra={
        "trace_id": trace_id,
        "user_id": user_id,
        "model": "gpt-4o",
        "input_tokens": 1500,
        "output_tokens": 300,
        "duration_ms": 2500,
        "cost_usd": 0.0045
    }
)

2. 日志级别：合理使用DEBUG、INFO、WARN、ERROR级别。

  • DEBUG：详细的调试信息（完整的Prompt和输出），生产环境默认关闭，需要时打开
  • INFO：正常的请求记录（请求ID、模型、Token数、耗时）
  • WARN：需要注意但不影响服务的问题（重试、降级、缓存未命中）
  • ERROR：错误（调用失败、异常、超时）

3. 日志脱敏：日志中可能包含用户的敏感信息（个人信息、商业机密、API Key）。需要做脱敏处理，避免敏感信息泄露。

  • 用户姓名、手机号、邮箱、身份证号等个人信息脱敏
  • API Key、密码、Token等密钥脱敏
  • 商业机密内容（如果有）需要加密或不记录

4. 日志采样：如果请求量很大，记录所有请求的完整日志（尤其是完整的Prompt和输出）会占用大量存储空间。可以做采样——比如10%的请求记录完整日志，其他只记录摘要。错误请求100%记录。

5. 日志关联：每条日志都要带上Trace ID，这样可以把Log和Trace关联起来——在Trace里看到某个Span出错，就能用Trace ID搜到对应的详细日志。

5.3 日志的存储和检索

日志量很大，需要专门的日志存储和检索系统。主流方案：

ELK Stack：Elasticsearch（存储+检索）+ Logstash（采集+处理）+ Kibana（可视化）。功能强大，生态成熟。

Loki + Grafana：Loki是轻量级的日志存储，和Grafana集成好，成本比ELK低。适合中小规模。

云服务：AWS CloudWatch、阿里云SLS、腾讯云CLS等云厂商的日志服务，开箱即用，不需要自己运维。

六、三大支柱的联动

Log、Metric、Trace不是孤立的，最好的实践是三者联动：

用户反馈"回答不对"
    ↓
Metric看板：发现该时段点踩率升高、某模型错误率升高
    ↓
用时间范围和用户ID筛选Trace：找到对应的请求Trace
    ↓
看Trace：发现RAG检索的文档相似度很低（检索不准）
    ↓
用Trace ID搜Log：看到完整的检索查询、检索到的文档、Prompt、LLM输出
    ↓
定位问题：用户的问题用了专业术语，文档里用的是另一种表述，检索没命中
    ↓
修复：优化检索策略（加同义词、调整切分方式）

这个流程就是三大支柱联动的典型场景：Metric发现异常→Trace定位环节→Log查看细节→修复问题。

七、落地建议

AI应用的可观测性体系建设，建议分阶段进行：

第一阶段：基础可观测性（1-2周）

  • 接入OpenTelemetry，自动记录LLM调用的Trace
  • 记录基本的Metric（请求量、延迟、错误率、Token消耗）
  • 结构化日志（请求ID、模型、Token数、耗时）
  • 搭一个基础的Grafana看板

第二阶段：完善可观测性（2-4周）

  • 完善Trace（RAG检索、工具调用、Prompt组装等Span）
  • 完善Metric（成本、质量、模型对比、业务指标）
  • 设置关键告警（延迟、错误率、成本）
  • 日志脱敏和采样
  • Trace和Log的关联

第三阶段：高级可观测性（持续迭代）

  • 自动评估（定期评估回答质量，自动检测幻觉）
  • 用户反馈闭环（点赞/点踩和Trace关联）
  • 异常检测（用AI自动分析日志和Trace，发现异常模式）
  • 成本优化建议（基于Metric数据，自动给出成本优化建议）
  • 全链路压测（模拟高并发，监控各环节的性能瓶颈）

八、总结

AI应用的可观测性，比传统应用更重要也更复杂。三大支柱各有侧重：

  • Trace：记录每次请求的完整链路，用于定位性能瓶颈和错误环节
  • Metric：聚合的指标数据，用于监控趋势、发现异常、设置告警
  • Log：详细的事件记录，用于排查具体问题的最后一道防线

三者联动，才能形成完整的可观测性闭环：Metric发现异常→Trace定位环节→Log查看细节→修复问题。

几个关键原则：

  1. 可观测性先行：在应用开发的早期就接入可观测性，不要等出了问题才补。没有可观测性，AI应用就是"黑盒"，出了问题根本不知道在哪。
  2. LLM调用是重点：LLM调用是AI应用的核心和瓶颈，Trace、Metric、Log都要重点记录LLM调用的详细信息（模型、Token、耗时、费用、完整的输入输出）。
  3. 成本可观测性不可少：LLM调用是按Token计费的，成本控制很重要。要详细记录Token消耗和费用，设置预算告警，避免"账单惊喜"。
  4. 质量可观测性是难点：回答质量是AI应用的核心指标，但很难自动量化。需要结合用户反馈（点赞/点踩）、自动评估（用LLM评估LLM）、人工抽检等多种方式。
  5. 隐私和安全：日志中可能包含用户的敏感信息，必须做脱敏处理。Trace和Log的访问权限也要控制，避免敏感信息泄露。

可观测性不是一次性的工作，而是持续迭代的过程。随着应用的功能越来越复杂、用户量越来越大，可观测性体系也要不断完善。但只要打好基础（三大支柱+联动），后续的迭代就会很顺畅。
