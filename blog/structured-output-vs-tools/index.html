结构化输出和工具调用，别混用

约 789 字大约 3 分钟

大模型Function Calling模型工具

2026-08-10

摘要： 要一份稳定 JSON 用结构化输出，要执行外部动作才用工具调用。

从发票里提取金额，模型返回了一次工具调用：save_invoice。应用还没来得及确认字段，工具已经准备写数据库。开发者原本只是想要一份格式稳定的 JSON，却把“生成数据”和“执行动作”绑在了一起。

结构化输出与 Function Calling 都会写 JSON Schema，代码看起来很像，确实容易混。

先问模型需不需要外部世界

如果答案只依赖当前输入，例如抽取合同字段、给工单分类、生成页面配置，结构化输出就够了。模型按 Schema 返回数据，应用验证后再决定怎么使用。

const invoiceSchema = {
  type: "object",
  properties: {
    invoiceNo: { type: "string" },
    amount: { type: "number" },
    currency: { type: "string", enum: ["CNY", "USD", "EUR"] },
  },
  required: ["invoiceNo", "amount", "currency"],
};

工具调用处理的是另一件事：模型发现自己需要查订单、发邮件或更新系统，于是请求应用执行一个函数。工具结果还可能回到模型，继续下一轮。

const getOrderTool = {
  name: "get_order",
  description: "按订单号读取订单，不修改数据",
  parameters: {
    type: "object",
    properties: { orderId: { type: "string" } },
    required: ["orderId"],
  },
};

一个是答案合同，一个是行动接口。Google Gemini 最新文档也明确区分了这两种用途。

Schema 正确，内容仍可能错

结构化输出能保证 JSON 形状，不会保证发票金额识别正确。金额需要范围检查，订单号可以到业务系统里核对。枚举、整数和必填项尽量写清楚，嵌套层级别太深。

if (invoice.amount <= 0 || invoice.amount > 1_000_000) {
  return { status: "needs_review", reason: "金额超出自动处理范围" };
}

这一层业务校验不能交给 Schema 代劳。

工具调用则要多看权限和副作用。get_order 与 refund_order 不应混成一个 manage_order。名称具体一点，模型更容易选对，网关也能为写操作单独审批。

两者可以在同一段流程里配合

客服智能体可以先调用工具读取订单，再用结构化输出生成一份退款建议。应用校验金额和政策后，用户确认了，才开放真正的退款工具。这样每一步目的都比较清楚。

我遇到这类设计时，会先画出数据什么时候进入系统、什么时候产生副作用。只要出现“模型一返回 JSON 就执行写入”，就值得停一下。中间加一层验证并不复杂，却能把很多含糊的错误挡在动作之前。

两种能力都很好用，名字也会随着平台变化。记住一个朴素判断就够了：想让模型把答案装进固定盒子，用结构化输出；需要它伸手去拿外部东西，再给工具。
