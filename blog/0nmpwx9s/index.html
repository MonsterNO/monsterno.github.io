LLM应用架构设计-从单体到微服务的演进路径

约 3490 字大约 12 分钟

LLM应用架构设计

2026-09-01

一个生产级的LLM应用，后端架构应该怎么设计？本文从最简单的单体架构讲起，逐层拆解LLM应用的核心组件——API网关、模型路由、Prompt管理、RAG引擎、Agent编排、可观测性，并给出从单体到微服务的演进路径和各阶段的技术选型。

一、LLM应用的架构特殊性

LLM（大语言模型）应用和传统的Web应用有很大的不同，这些不同决定了它的架构设计也有特殊性：

1. 计算密集型，延迟高：一次LLM调用可能需要几百毫秒到几十秒，比传统的数据库查询（几毫秒）慢得多。这意味着应用的响应时间主要由LLM调用决定，架构设计需要围绕"减少LLM调用次数"和"优化LLM调用效率"来展开。

2. 输出不确定：同样的输入，LLM可能返回不同的输出。而且输出可能包含错误、幻觉、格式问题。这意味着架构需要有"输出校验"、"重试"、"降级"等机制。

3. 上下文有限：LLM的上下文窗口是有限的（4K-128K），不可能把所有信息都塞进去。这意味着需要有"上下文管理"、"RAG检索"、"摘要压缩"等组件。

4. 成本高：LLM调用是按Token计费的，一次调用可能几分钱到几块钱。高并发下成本会迅速攀升。这意味着架构需要有"成本控制"、"缓存"、"模型分级"等机制。

5. 快速迭代：LLM应用的核心是Prompt和模型，这些需要频繁迭代和实验。这意味着架构需要有"Prompt版本管理"、"A/B测试"、"快速回滚"等能力。

理解了这些特殊性，才能设计出合理的LLM应用架构。

二、第一阶段：单体架构（MVP阶段）

最开始做LLM应用，不要一上来就搞微服务。单体架构足够了，而且开发速度快、运维简单。

2.1 单体架构的组成

一个最简单的LLM应用单体架构，包含以下组件：

用户 → 前端 → API后端 → LLM API（OpenAI/通义/DeepSeek）
                        ↓
                    数据库（PostgreSQL）

API后端是核心，它负责：

  • 接收用户请求
  • 构建Prompt
  • 调用LLM API
  • 处理LLM返回结果
  • 保存对话历史到数据库
  • 返回给前端

这个阶段，所有逻辑都写在一个服务里。Prompt硬编码在代码里，对话历史存在数据库里，直接调用LLM API。

2.2 技术选型

  • 后端框架：FastAPI（Python）或 Express（Node.js）。FastAPI因为Python生态好（LLM相关库多），是最常用的选择。
  • 数据库：PostgreSQL，存用户信息、对话历史。
  • LLM SDK：直接用官方SDK（openai、dashscope等）。
  • 部署：Docker + 一台云服务器。

2.3 单体架构的适用场景

单体架构适合：

  • MVP验证阶段，快速验证想法
  • 用户量小（日活<1000）
  • 功能简单（单轮对话、简单RAG）
  • 团队小（1-3人）

单体架构的开发速度最快，能在几天内上线一个可用的版本。不要过早优化，先把产品跑起来，验证用户需求，再考虑架构升级。

三、第二阶段：模块化单体（增长阶段）

当用户量增长、功能变多，单体架构会变得越来越臃肿——所有逻辑混在一起，改一个地方可能影响其他地方，部署一次要等很久。这时候需要进入第二阶段：模块化单体。

模块化单体的核心思想是：还是一个服务，但内部按模块划分，模块之间通过清晰的接口通信。

3.1 核心模块划分

一个LLM应用的模块化单体，通常包含以下模块：

┌─────────────────────────────────────┐
│            API Layer（API层）         │
│  接收请求、参数校验、返回响应          │
├─────────────────────────────────────┤
│         Service Layer（服务层）        │
│  ┌─────────┬──────────┬──────────┐  │
│  │ Prompt  │   RAG    │  Agent   │  │
│  │ Manager │ Engine   │ Orchestr.│  │
│  └─────────┴──────────┴──────────┘  │
│  ┌─────────┬──────────┬──────────┐  │
│  │  Model  │ Conversation │ Cost  │  │
│  │ Router  │  Manager    │ Track.│  │
│  └─────────┴──────────┴──────────┘  │
├─────────────────────────────────────┤
│        Infrastructure Layer（基础设施层）│
│  数据库、向量库、缓存、LLM客户端       │
└─────────────────────────────────────┘

下面逐个模块讲。

Prompt Manager（Prompt管理）：把Prompt从代码中抽离出来，统一管理。支持版本控制、变量注入、A/B测试。

class PromptManager:
    def __init__(self, storage):
        self.storage = storage  # 可以是数据库、配置中心、Git
    
    def get_prompt(self, name: str, version: str = None, **kwargs) -> str:
        """获取指定名称和版本的Prompt，注入变量"""
        template = self.storage.get(name, version)
        return template.format(**kwargs)
    
    def list_versions(self, name: str) -> list:
        """列出某个Prompt的所有版本"""
        return self.storage.list_versions(name)

Model Router（模型路由）：根据任务类型、成本、延迟要求，选择合适的模型。简单任务用便宜的小模型，复杂任务用贵的大模型。

class ModelRouter:
    def __init__(self, models_config):
        self.models = models_config  # 模型配置列表
    
    def route(self, task_type: str, priority: str = "balanced") -> str:
        """根据任务类型和优先级选择模型"""
        if priority == "cost":
            return self.cheapest_model(task_type)
        elif priority == "quality":
            return self.best_model(task_type)
        else:  # balanced
            return self.balanced_model(task_type)

RAG Engine（RAG引擎）：负责文档处理、向量检索、重排序、上下文组装。这是LLM应用中最复杂的模块之一。

Agent Orchestrator（Agent编排）：负责任务规划、工具调用、多步骤执行。如果应用有Agent能力，需要这个模块。

Conversation Manager（对话管理）：负责对话历史的存储、检索、压缩。长对话需要压缩历史，避免超出上下文窗口。

Cost Tracker（成本追踪）：记录每次LLM调用的Token消耗和费用，做成本统计和预算控制。

3.2 模块化单体的优势

  • 开发速度仍然快（一个服务部署）
  • 代码结构清晰，模块之间职责明确
  • 便于后续拆分成微服务（模块边界就是未来的服务边界）
  • 适合中等规模的团队和应用

3.3 什么时候需要升级到微服务

当出现以下情况时，就该考虑微服务了：

  • 某个模块（比如RAG引擎）需要独立扩展（它的负载比其他模块高很多）
  • 团队变大，多个团队同时开发，单体的代码冲突和部署冲突越来越多
  • 不同模块有不同的技术栈需求（比如RAG引擎想用Go，Agent编排想用Python）
  • 需要更严格的故障隔离（一个模块挂了不影响其他模块）

四、第三阶段：微服务架构（规模化阶段）

当应用规模进一步增长，就需要微服务架构。微服务的核心思想是：把模块化单体中的每个模块，拆成独立的服务，独立部署、独立扩展、独立迭代。

4.1 微服务架构的组成

一个典型的LLM应用微服务架构，包含以下服务：

                    ┌─────────────┐
                    │   API网关    │
                    │ （认证/限流/路由）│
                    └──────┬──────┘
                           │
        ┌──────────┬───────┼───────┬──────────┐
        ↓          ↓       ↓       ↓          ↓
   ┌─────────┐ ┌──────┐ ┌─────┐ ┌──────┐ ┌────────┐
   │对话服务  │ │RAG服务│ │Agent│ │Prompt│ │模型服务 │
   │Conversation│ │Engine│ │服务 │ │服务  │ │Router  │
   └────┬────┘ └──┬───┘ └──┬──┘ └──┬───┘ └───┬────┘
        │         │        │       │         │
        └─────────┴────────┴───────┴─────────┘
                           │
                    ┌──────┴──────┐
                    │  消息队列      │
                    │（Kafka/RabbitMQ）│
                    └──────┬──────┘
                           │
        ┌──────────┬───────┼───────┬──────────┐
        ↓          ↓       ↓       ↓          ↓
   ┌─────────┐ ┌──────┐ ┌─────┐ ┌──────┐ ┌────────┐
   │  成本服务 │ │评估服务│ │缓存 │ │日志服务│ │通知服务 │
   │  Cost   │ │Eval  │ │Cache│ │Logging│ │Notify  │
   └─────────┘ └──────┘ └─────┘ └──────┘ └────────┘

4.2 核心服务详解

API网关：所有请求的入口，负责认证、鉴权、限流、路由、协议转换。常用技术：Kong、APISIX、Nginx。

对话服务（Conversation Service）：管理对话历史、用户会话、消息记录。是最核心的业务服务。

RAG服务（RAG Service）：负责文档上传、切分、向量化、检索、重排序。独立部署，可以单独优化性能和扩展。

Agent服务（Agent Service）：负责任务规划、工具调用、多步骤执行。Agent的执行时间长，独立部署避免阻塞其他服务。

Prompt服务（Prompt Service）：管理所有Prompt的版本、变量、A/B测试。独立部署后，产品经理可以自己改Prompt，不需要开发介入。

模型路由服务（Model Router Service）：统一管理所有LLM的接入（OpenAI、Anthropic、通义、DeepSeek、本地模型），做负载均衡、故障转移、成本优化。

成本服务（Cost Service）：异步消费LLM调用的事件，统计Token消耗和费用，做预算控制和告警。

评估服务（Evaluation Service）：定期评估模型和Prompt的效果，做回归测试和质量监控。

4.3 服务间通信

微服务之间的通信有两种模式：

同步通信（HTTP/gRPC）：用于需要立即返回结果的调用。比如对话服务调用RAG服务检索文档，需要等检索结果返回才能继续。gRPC比HTTP性能更好，适合内部服务间通信。

异步通信（消息队列）：用于不需要立即返回结果的调用。比如LLM调用完成后，发一个事件到消息队列，成本服务和日志服务异步消费。常用技术：Kafka、RabbitMQ、Pulsar。

异步通信的好处是解耦——对话服务不需要知道有多少个下游服务在消费事件，新增服务也不需要改对话服务的代码。

4.4 数据存储

微服务架构下，每个服务有自己的数据库（Database per Service），避免服务间直接访问对方的数据库。

常用的存储：

  • 关系型数据库：PostgreSQL，存用户、对话、配置等结构化数据
  • 向量数据库：Pinecone、Milvus、Qdrant、Weaviate，存文档向量
  • 缓存：Redis，存热点数据、会话状态、限流计数
  • 对象存储：S3、MinIO，存上传的文档、生成的文件
  • 搜索引擎：Elasticsearch，存日志、做全文检索

五、横切关注点：所有架构都需要的组件

不管是单体还是微服务，有一些组件是所有架构都需要的，这些叫"横切关注点"。

5.1 可观测性（Observability）

LLM应用的可观测性比传统应用更重要，因为LLM的输出不确定，出了问题很难排查。

可观测性的三大支柱：

日志（Logging）：记录每次请求的详细信息——用户输入、Prompt、LLM参数、LLM输出、Token消耗、耗时、错误信息。结构化日志（JSON格式），方便检索和分析。

指标（Metrics）：统计关键指标——请求量、延迟（P50/P95/P99）、成功率、Token消耗、成本、缓存命中率。用Prometheus+Grafana做监控和告警。

追踪（Tracing）：分布式链路追踪，记录一次请求经过了哪些服务、每个服务的耗时。用OpenTelemetry+Jaeger做追踪。LLM调用要作为一个span记录，包含模型名称、Token数、耗时。

5.2 安全（Security）

  • 认证鉴权：JWT/OAuth2，确保只有合法用户能访问
  • 输入过滤：防止Prompt注入攻击（用户输入中包含恶意指令）
  • 输出过滤：防止LLM生成有害内容（暴力、色情、违法）
  • 数据加密：传输加密（HTTPS）、存储加密（敏感数据加密存储）
  • 密钥管理：LLM API Key等密钥存在密钥管理服务（AWS KMS、HashiCorp Vault），不要硬编码

5.3 缓存（Caching）

缓存是降低LLM应用成本和延迟的关键手段。

  • Prompt缓存：相同的Prompt和输入，缓存LLM的输出。命中率高的话能省很多成本。
  • 语义缓存：不是精确匹配，而是语义相似就命中（用向量相似度判断）。比精确缓存命中率高很多。
  • RAG缓存：缓存文档的向量和检索结果，避免重复计算。

5.4 限流与降级（Rate Limiting & Circuit Breaker）

  • 限流：限制每个用户/每个IP的请求频率，防止滥用和过载。用Redis做分布式限流。
  • 熔断：当LLM API故障率超过阈值时，自动熔断，返回降级结果（比如缓存的结果或"服务暂时不可用"），避免级联失败。
  • 降级：主模型不可用时，自动切换到备用模型（比如从GPT-4切换到GPT-3.5），保证服务可用。

六、架构演进的原则

从单体到微服务，不是一步到位的，而是渐进式演进。几个原则：

1. 不要过早微服务化：单体能解决的问题，不要拆微服务。微服务增加了运维复杂度和开发成本，只有当规模真的需要时才拆。

2. 先模块化，再微服务：在单体内部先把模块边界划清楚，等模块稳定了，再把需要独立扩展的模块拆成服务。不要一上来就拆十几个服务。

3. 拆服务的依据是"变化频率"和"负载特征"：变化频率高的模块（比如Prompt管理）适合独立部署，方便快速迭代；负载特征不同的模块（比如RAG引擎是计算密集型，对话服务是IO密集型）适合独立扩展。

4. 保持服务间的契约稳定：微服务之间通过API通信，API契约（接口定义）要保持稳定，避免频繁变更导致下游服务出问题。用API版本管理（v1、v2）来处理不兼容的变更。

5. 可观测性先行：在拆微服务之前，先把日志、指标、追踪做好。没有可观测性，微服务出了问题根本不知道在哪。

七、总结

LLM应用的架构演进，和传统应用类似，但有自己的特殊性——围绕LLM调用的延迟、成本、不确定性来设计。

三个阶段的总结：

阶段架构适用规模核心优势
MVP单体日活<1000开发快、运维简单
增长模块化单体日活1000-10万结构清晰、便于拆分
规模化微服务日活>10万独立扩展、故障隔离

不管哪个阶段，横切关注点（可观测性、安全、缓存、限流降级）都是必须的。尤其是可观测性，对LLM应用来说比传统应用更重要。

最后一句话：架构是为业务服务的，不是为了炫技。 选择适合当前业务规模的架构，比选择"最先进"的架构重要得多。随着业务增长，渐进式演进，才是最稳妥的路径。
