Agent架构深度解析-从ReAct到Plan-and-Execute

约 3293 字大约 11 分钟

Agent架构深度解析

2026-09-01

Agent的核心不是"用了什么模型"，而是"用什么架构组织模型的推理和行动"。本文从最基础的ReAct模式讲起，逐层拆解Reflexion、Tree of Thoughts、Plan-and-Execute等主流Agent架构的原理、适用场景和工程实现细节。

一、为什么Agent需要架构

大模型本身是一个"单步推理器"——给它一个输入，它输出一个结果。但真实世界的任务往往是多步骤的：你需要先理解问题，然后规划步骤，再逐步执行，过程中还要根据反馈调整。

直接把一个复杂任务丢给大模型，效果往往不好。原因有三个：

  1. 上下文窗口有限：复杂任务的中间结果太多，全塞进去会爆窗口
  2. 单步推理容易出错：一步错步步错，没有纠错机制
  3. 无法与外部环境交互：模型只能"说"，不能"做"——不能查数据库、不能调API、不能执行代码

Agent架构就是为了解决这些问题。它本质上是一套"组织大模型推理过程"的框架，决定了模型在什么时刻思考什么、如何调用工具、如何处理错误、何时停止。

二、ReAct：最基础的Agent架构

ReAct（Reasoning + Acting）是目前最主流、最基础的Agent架构，2022年由普林斯顿大学和Google Research联合提出。它的核心思想很简单：让模型交替进行"思考"和"行动"。

2.1 核心循环

ReAct的每一轮循环包含三个步骤：

Thought（思考）→ Action（行动）→ Observation（观察）
  • Thought：模型分析当前状态，决定下一步该做什么
  • Action：模型调用一个工具（比如搜索、代码执行、数据库查询）
  • Observation：工具返回结果，作为下一轮Thought的输入

这个循环不断重复，直到模型认为任务完成，输出最终答案。

2.2 工程实现

ReAct的实现并不复杂，核心是一个循环：

def react_agent(query, tools, max_steps=10):
    """ReAct Agent的核心实现"""
    # 系统提示词：定义Thought/Action/Observation格式
    system_prompt = """你是一个智能助手，通过思考和行动来解决问题。

可用工具：
{tools_description}

每轮按以下格式输出：
Thought: 你的思考过程，分析当前状态和下一步计划
Action: 工具名(参数)
Observation: 工具返回结果（由系统填充）

当你认为任务完成时，输出：
Final Answer: 最终答案
"""
    
    messages = [
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": query}
    ]
    
    for step in range(max_steps):
        # 1. 模型思考并决定行动
        response = llm.chat(messages)
        messages.append({"role": "assistant", "content": response})
        
        # 2. 检查是否输出了Final Answer
        if "Final Answer:" in response:
            return extract_final_answer(response)
        
        # 3. 解析Action，调用工具
        action_name, action_params = parse_action(response)
        tool = tools[action_name]
        observation = tool(**action_params)
        
        # 4. 将Observation加入上下文
        messages.append({
            "role": "user",
            "content": f"Observation: {observation}"
        })
    
    return "达到最大步数限制，任务未完成"

2.3 ReAct的优缺点

优点：

  • 实现简单，逻辑清晰
  • 每一步都有明确的Thought，可解释性强
  • 工具调用和推理交替进行，能处理多步骤任务

缺点：

  • 线性推理，没有回溯：一步走错了，后面很难纠正
  • 没有反思机制：模型不会回头检查自己的推理是否正确
  • 复杂任务容易陷入循环：模型可能在几个步骤之间来回打转

ReAct适合中等复杂度的任务，比如"查资料→整理→回答"这种线性流程。但对于需要深度推理、多路径探索的任务，ReAct就不够用了。

三、Reflexion：给Agent加反思能力

Reflexion是2023年提出的架构，核心思想是：让Agent在完成任务后，对自己的表现进行反思，然后基于反思重新尝试。

3.1 核心机制

Reflexion在ReAct的基础上，增加了一个"反思"步骤：

执行任务（ReAct循环）→ 评估结果 → 反思失败原因 → 基于反思重新执行

关键在于，反思的结果会被保存为"经验记忆"，在下一轮执行时注入到提示词中，让模型"记住"上次的教训。

3.2 实现要点

Reflexion的实现有两个核心组件：

评估器（Evaluator）：判断任务是否成功完成。可以是规则判断（比如检查输出是否包含特定内容），也可以用另一个大模型来评估。

反思生成器（Reflector）：如果任务失败，让模型基于失败的轨迹生成反思，总结失败原因和改进建议。

def reflexion_agent(query, tools, max_trials=3):
    """Reflexion Agent的核心实现"""
    reflections = []  # 保存历史反思
    
    for trial in range(max_trials):
        # 1. 执行任务（注入历史反思）
        result, trajectory = react_with_reflections(query, tools, reflections)
        
        # 2. 评估结果
        is_success = evaluate(result, query)
        
        if is_success:
            return result
        
        # 3. 生成反思
        reflection = generate_reflection(query, trajectory, result)
        reflections.append(reflection)
        
        print(f"第{trial+1}轮失败，反思：{reflection}")
    
    return result  # 返回最后一轮的结果

3.3 适用场景

Reflexion特别适合有明确成功标准的任务：

  • 编程任务（测试是否通过）
  • 数学题（答案是否正确）
  • 有明确输出格式要求的任务

实验表明，Reflexion在编程任务上比纯ReAct的成功率提升了30%以上。但它的代价是执行时间更长（可能要跑好几轮），而且需要有可靠的评估机制。

四、Tree of Thoughts：多路径探索

Tree of Thoughts（ToT）是2023年由普林斯顿和Google DeepMind联合提出的架构，核心思想是：让模型同时探索多条推理路径，然后选择最优的一条。

4.1 核心机制

ToT把推理过程组织成一棵树：

  • 节点（Node）：一个中间推理状态
  • 分支（Branch）：从当前状态出发，模型生成多个可能的下一步
  • 评估（Evaluate）：对每个节点的"前景"进行打分
  • 搜索（Search）：用BFS或DFS探索树，找到最优路径

和ReAct的线性推理不同，ToT允许模型"并行思考"多个可能性，然后选择最有希望的方向继续深入。

4.2 实现框架

ToT的实现比ReAct复杂得多，核心是四个函数：

class TreeOfThoughts:
    def __init__(self, llm, problem_solver):
        self.llm = llm
        self.problem_solver = problem_solver
    
    def thought_decomposition(self, problem):
        """将问题分解为多个思考步骤"""
        # 比如24点游戏分解为：选两个数→计算→选下一个数→计算
        pass
    
    def thought_generator(self, state, step):
        """从当前状态生成多个可能的下一步思考"""
        prompt = f"问题：{state['problem']}\n当前状态：{state}\n请给出3个可能的下一步："
        response = self.llm.generate(prompt)
        return parse_thoughts(response)  # 返回多个候选思考
    
    def state_evaluator(self, state):
        """评估当前状态的前景，返回分数（0-1）"""
        prompt = f"问题：{state['problem']}\n当前状态：{state}\n请评估这个状态最终能解决问题的可能性（0-10分）："
        score = self.llm.generate(prompt)
        return normalize_score(score)
    
    def search(self, problem, algorithm="BFS", beam_width=3):
        """用BFS或DFS搜索最优解"""
        initial_state = {"problem": problem, "steps": [], "value": None}
        frontier = [initial_state]
        
        for step in range(max_steps):
            # 1. 对每个前沿节点生成多个候选下一步
            all_candidates = []
            for state in frontier:
                candidates = self.thought_generator(state, step)
                for candidate in candidates:
                    new_state = apply_thought(state, candidate)
                    new_state["value"] = self.state_evaluator(new_state)
                    all_candidates.append(new_state)
            
            # 2. 按评估分数排序，保留beam_width个最优节点
            all_candidates.sort(key=lambda x: x["value"], reverse=True)
            frontier = all_candidates[:beam_width]
            
            # 3. 检查是否有节点达到终止状态
            for state in frontier:
                if is_terminal(state):
                    return state
        
        return frontier[0]  # 返回最优节点

4.3 适用场景与局限

ToT适合需要多路径探索的任务：

  • 数学推理（24点游戏、方程求解）
  • 创意写作（探索多个故事线）
  • 策略规划（国际象棋、游戏AI）

但ToT的局限性也很明显：

  • 计算成本高：每个节点都要调用大模型，一棵树可能要调用几十次
  • 评估函数难设计：怎么评估一个中间状态的"前景"，本身就是个难题
  • 不适合工具调用：ToT主要用于纯推理任务，和外部工具交互的场景不太适配

五、Plan-and-Execute：先规划后执行

Plan-and-Execute是2023年由LangChain团队提出的架构，核心思想是：先让模型制定完整的执行计划，然后按计划逐步执行。

5.1 核心机制

Plan-and-Execute分为两个阶段：

规划阶段（Planning）：模型分析任务，制定一个多步骤的执行计划。每个步骤是一个具体的子任务。

执行阶段（Execution）：按计划逐步执行每个子任务。执行过程中可以根据实际情况动态调整计划（Re-Planning）。

用户输入 → 规划器生成步骤列表 → 逐步执行每个步骤 → 整合结果 → 最终答案
                ↑                        ↓
                └──── 动态重规划 ←──────┘

5.2 实现细节

Plan-and-Execute的核心是两个模块：规划器和执行器。

class PlanAndExecuteAgent:
    def __init__(self, llm, tools):
        self.llm = llm
        self.tools = tools
        self.planner = self._create_planner()
        self.executor = self._create_executor()
    
    def _create_planner(self):
        """创建规划器：将任务分解为步骤列表"""
        planner_prompt = """你是一个任务规划专家。请将用户的任务分解为具体的执行步骤。

要求：
1. 每个步骤是一个可独立执行的子任务
2. 步骤之间有明确的依赖关系
3. 步骤数量控制在3-7步
4. 用编号列表输出

用户任务：{query}
执行计划："""
        return planner_prompt
    
    def _create_executor(self):
        """创建执行器：执行单个步骤（可以用ReAct）"""
        return ReActAgent(self.llm, self.tools)
    
    def run(self, query):
        # 1. 规划阶段
        plan = self.llm.generate(self.planner.format(query=query))
        steps = parse_plan(plan)
        print(f"执行计划：{steps}")
        
        # 2. 执行阶段
        step_results = []
        for i, step in enumerate(steps):
            print(f"执行步骤{i+1}/{len(steps)}：{step}")
            
            # 将之前的步骤结果注入上下文
            context = self._build_context(query, steps[:i], step_results)
            
            # 执行当前步骤
            result = self.executor.run(step, context)
            step_results.append(result)
            
            # 3. 动态重规划：检查是否需要调整计划
            if self._should_replan(step, result, steps[i+1:]):
                print("检测到计划需要调整，重新规划...")
                remaining_steps = self._replan(query, steps[:i+1], step_results)
                steps = steps[:i+1] + remaining_steps
        
        # 4. 整合所有步骤结果，生成最终答案
        final_answer = self._synthesize(query, step_results)
        return final_answer

5.3 Plan-and-Execute vs ReAct

维度ReActPlan-and-Execute
推理方式边想边做，线性推进先想后做，整体规划
上下文使用每轮都带完整历史规划和执行分离，上下文更精简
复杂任务容易迷失方向有明确计划，不容易跑偏
灵活性高，随时可以调整中等，需要重规划机制
实现复杂度低中高
适合场景中等复杂度、线性任务高复杂度、多步骤任务

Plan-and-Execute的最大优势是任务分解能力。对于"做一份市场调研报告"这种复杂任务，ReAct可能做到一半就忘了最初的目标，而Plan-and-Execute因为有明确的计划，能始终围绕目标推进。

六、架构选型建议

了解了这么多架构，实际项目中该怎么选？我的建议是：

从ReAct起步。大多数场景下，ReAct已经够用了。它实现简单、调试方便、可解释性强。先把ReAct跑通，看看效果瓶颈在哪里，再考虑升级。

需要纠错能力时加Reflexion。如果你的任务有明确的成功标准（比如编程、数学），而且ReAct的成功率不够，加上Reflexion的反思机制，通常能提升20-30%的成功率。

需要深度推理时用ToT。如果你的任务是纯推理类（数学、逻辑、策略），而且需要探索多个可能性，ToT是更好的选择。但要注意控制计算成本。

复杂任务用Plan-and-Execute。如果你的任务步骤多、复杂度高、需要整体规划，直接上Plan-and-Execute。它的规划-执行分离架构，是目前处理复杂任务最可靠的方式。

生产环境的最佳实践：大多数生产级Agent，实际上是混合架构。比如用Plan-and-Execute做整体规划，每个步骤的执行用ReAct，关键步骤加Reflexion反思，纯推理子任务用ToT。根据任务的不同阶段，灵活组合不同的架构模式。

七、总结

Agent架构的演进，本质上是在解决一个核心矛盾：大模型的单步推理能力 vs 真实任务的多步骤复杂性。

从ReAct的"边想边做"，到Reflexion的"做完反思"，到ToT的"多路探索"，再到Plan-and-Execute的"先想后做"，每一种架构都在尝试用不同的方式组织大模型的推理过程，让它能更好地处理复杂任务。

没有哪种架构是"最好的"，只有"最适合当前场景的"。理解每种架构的原理和适用场景，根据任务特点灵活选择甚至组合，才是工程上的正确做法。

未来Agent架构的演进方向，我认为有两个：一是更精细的任务分解，让规划器能把任务拆得更细、更合理；二是更高效的记忆系统，让Agent能在长任务中保持上下文一致性，不会"做到一半忘了目标"。这两个方向的突破，会让Agent的能力再上一个台阶。
