智能体出错后，日志该记什么

约 838 字大约 3 分钟

AI智能体可观测性AI开发平台

2026-08-10

摘要： 智能体日志要回答发生了什么，也要让人看懂它为何停在这里。

客服智能体创建了两张重复退款单。排查时，模型日志里只有一句“退款申请已提交”。工具服务说两个请求都合法，网关也各自返回了 200。每一段单独看都没错，放在一起却解释不了为什么执行了两次。

智能体的故障经常跨过模型、工具、权限和业务系统。日志还按服务各记各的，最后只能靠时间戳猜。

给一次任务一个共同编号

最先要补的是贯穿全程的 traceId。用户请求进入宿主应用时生成，后面的模型调用、工具调用、审批和下游 API 都沿用它。一次工具重试再分配单独的 spanId。

const trace = {
  traceId: crypto.randomUUID(),
  runId: "refund-run-1842",
  userId: hashUserId(user.id),
  agentVersion: "refund-agent@2.6.1",
  policyVersion: "refund-policy@8",
};

用户身份不必明文落日志。能关联权限边界，又不把敏感信息到处复制，通常更合适。

工具调用要记意图和结果

只记“调用了 create_refund”还不够。需要保存经过脱敏的参数、令牌所属租户、幂等键、耗时和返回状态。如果参数太大，可以存摘要与原始记录的位置。

模型侧也别只存完整提示词。生产环境里，提示词可能带客户数据，长期保存反而增加风险。更有用的是模型版本、上下文来源、工具目录版本、Token 用量和停止原因。确实需要复盘文本时，再进入受控审计存储。

{
  "event": "tool_call",
  "tool": "create_refund",
  "idempotencyKey": "order-7319-refund",
  "tenant": "tenant-hash-2fd1",
  "attempt": 2,
  "durationMs": 438,
  "result": "success"
}

这条记录一眼就能提醒人：第二次尝试为什么仍执行成功，业务接口是否真的处理了幂等键。

轨迹需要能看，也要能报警

追踪页面适合复盘，线上问题还需要指标。工具失败率突然升高、平均调用步数变长、人工接管增多，都可能是模型或工具变化的信号。成本也可以按任务统计，别只看整个月的 Token 总额。

OpenAI 的 Agents 工具和安全实践都强调 tracing 与 agent-native telemetry。背后的道理不复杂：智能体会自己选择路径，平台就得保留足够的信息解释这条路径。

我不太赞成把模型的每段内部推理都当成可观测性的核心。它未必稳定，也可能带来额外风险。真正能落地排查的，往往是输入来源、工具动作、外部状态变化和验证结果。

可以先从一次最难查的历史故障开始，问问现有日志还缺哪三个字段。把它们补上，再故意制造一次重试。如果重复退款能在一条轨迹里被看见，这套日志才算从“有记录”往“能解释”走了一步。
