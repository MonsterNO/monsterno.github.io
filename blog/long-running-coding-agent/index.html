代码智能体跑久了，怎么续上

约 1002 字大约 3 分钟

AI编程AI智能体Agent工程

2026-08-10

摘要： 代码智能体跑得越久，越需要检查点、任务账本和可重复执行的步骤。

午饭前给代码智能体一个任务：“把旧鉴权模块迁到新接口，顺便补上测试。”回来一看，它已经改了二十多个文件。终端里最后一行停在安装依赖，前面的推理被压缩过，测试也没跑完。

这时候，重试按钮就在眼前。更让人犹豫的是，它会不会把已经做对的部分再改坏。

代码智能体正在从几分钟的小修补，走向需要几个小时的迁移、重构和排查。OpenAI 在 2026 年公布的使用研究里也提到，长时任务已经很常见。任务变长以后，模型能力当然重要，可恢复能力很快会变成更现实的问题。

聊天记录不能当进度条

不少智能体把“当前做到哪”放在对话历史里。运行时间一长，历史会被压缩，工具输出也可能被截断。即使上下文还在，里面也混着尝试、失败和已经过期的判断，很难直接当作可靠状态。

比较稳的做法，是给任务留一份机器可读的账本。它不需要写得很复杂，但要能回答三个问题：哪些步骤已经完成，当前产物在哪里，下一次从什么条件开始。

{
  "taskId": "auth-migration-42",
  "goal": "迁移鉴权模块并补测试",
  "checkpoint": "tests-added",
  "completed": [
    "inventory-old-api",
    "replace-token-parser",
    "add-unit-tests"
  ],
  "next": "run-integration-tests",
  "artifacts": ["src/auth", "tests/auth"]
}

这份文件和给人看的工作日志不一样。人可以写“鉴权差不多改完了”，程序需要知道哪个检查已经通过、哪些文件可以继续复用。

每一步都要允许重新来一次

中断恢复最怕副作用。智能体第一次执行数据库迁移成功了，结果响应丢失；恢复后又执行一次，数据就可能重复写入。创建分支、提交工单、发布包也有类似问题。

我越来越觉得，长任务没必要追求永远不停。每个步骤经得起再跑一次，反倒更实在。能先查询状态就别直接创建；有副作用的接口带上幂等键；文件修改前记录基线哈希。恢复时先核对现场，再决定继续还是回滚。

async function ensureIssue(input: IssueInput) {
  const key = `migration:${input.repo}:${input.module}`;
  const existing = await findIssueByKey(key);
  if (existing) return existing;
  return createIssue({ ...input, idempotencyKey: key });
}

这段代码看着很普通，却比一句“不要重复创建工单”的提示词可靠得多。

给智能体一个重新进门的入口

任务恢复时，不要把整段旧对话原封不动塞回去。可以让智能体先读取目标、检查点、最新测试结果和 Git 差异，再重新规划剩余工作。旧日志留着审计，需要时再查。

还有个小细节很有用：检查点最好放在完成验证之后。代码写完但测试没过，只能算“已修改”，还不能算“已完成”。这条界线如果模糊，任务账本很快就会变成另一份自我安慰式的进度表。

真正适合长跑的代码智能体，未必一次都不出错。它只是停下来以后，能看懂桌面上留下的东西，然后从一个可信的位置继续。准备接入长时任务时，可以先拿一次最简单的故障做测试：运行到一半关掉执行器，再看看它能不能不重复、不漏步地完成。
