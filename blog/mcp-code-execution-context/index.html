MCP工具太多，代码执行更省上下文

约 837 字大约 3 分钟

MCPAI智能体模型工具

2026-08-10

摘要： 几十个 MCP 工具直接暴露给模型，Token 和选择错误都会一起增加。

一个数据分析智能体连接了工单、网盘、数据库和监控平台。刚开始每边只有三四个工具，调用挺顺。后来工具涨到八十多个，模型还没开始回答，光定义就占了一大段上下文。

更麻烦的是，查一份工单详情要返回几千行 JSON。模型真正需要的可能只是严重级别和创建时间，其余内容都跟着进入下一轮。

工具定义也有成本

直接工具调用很直观，数量少时完全够用。工具一多，名称相似、参数重复，模型选错的概率会上升。每次请求还要重复传完整 Schema。

一种办法是先暴露简短目录，按需加载具体工具。另一种正在变热的做法，是给智能体一个受控代码执行环境，让它在代码里调用 MCP 工具，并在结果进入模型前完成筛选。

issues = mcp.call("tickets.search", {
    "query": "payment incident",
    "limit": 100
})

summary = [
    {"id": x["id"], "severity": x["severity"], "created": x["createdAt"]}
    for x in issues
    if x["severity"] in ("P0", "P1")
]

print(summary)

模型只看到过滤后的十几行，不必吞下原始的一百张工单。

代码适合做组合和过滤

连续调用五个工具时，普通 Agent Loop 会经历“模型决定—调用—把结果送回模型”五轮。代码可以把稳定的组合逻辑一次写完，排序、去重和字段转换交给运行时。Anthropic 的 MCP 代码执行文章把这点讲得很清楚。

当然，代码执行也不是免费午餐。运行环境要隔离文件和网络，MCP 工具仍按最小权限发放，执行时间和内存要有限制。模型写出的代码不能因为放进沙箱，就自动变成可信代码。

sandbox:
  timeoutSeconds: 20
  memoryMb: 256
  network: deny
  mcpTools:
    - tickets.search
    - metrics.query

这个环境只能通过两项 MCP 工具接触外部系统，不能自行访问任意网址。

别为了省 Token 把审计弄丢

代码把多个工具调用包在一起以后，平台仍要记录每次调用的工具名、参数摘要和权限身份。否则表面上只看到执行了一段 Python，里面查过什么完全不清楚。

我会先找返回值特别大、组合步骤固定的任务尝试这种方式，例如批量筛工单或汇总监控指标。单次删除、发布这种高风险动作，保留清楚的独立工具调用和审批，反而更好理解。

是否值得改，可以用实际数据判断：比较两种实现的输入 Token、模型轮数、工具误选率和总耗时。代码执行通常能让长结果安静下来，但系统也多了一个需要维护的沙箱。省下来的上下文，得足够覆盖这份复杂度才划算。
