从零搭生产级RAG系统-召回率92延迟180ms

约 2736 字大约 9 分钟

大模型

2026-09-01

RAG系统看起来简单，做起来全是细节。本文从文档切分到检索策略，从重排序到Prompt工程，手把手搭一个召回率92%、P99延迟180ms的生产级RAG系统。

很多人觉得RAG很简单：不就是"文档切块→向量化→存起来→查询时检索→塞给大模型"吗？照着教程写个Demo，半小时就能跑通。

我一开始也是这么想的。直到我们的RAG系统上线，用户反馈"答非所问"、"找不到相关内容"、"响应太慢"，我才意识到：Demo和生产系统之间，隔着一百个细节。

后来我们花了两个月优化，把召回率从65%提到了92%，P99延迟从800ms降到了180ms。今天就把整个过程和关键细节写出来。

RAG系统的完整架构

一个生产级RAG系统，不是简单的"检索+生成"，而是包含多个环节的流水线：

用户提问 → 查询改写 → 混合检索（关键词+向量） → 重排序 → 上下文组装 → 大模型生成 → 答案

每个环节都有优化空间。下面我们一步步来实现。

第一步：文档处理与切分

文档切分是RAG的基础，也是最容易被忽视的环节。切得太大，检索不精准；切得太小，上下文不完整。

我们试过固定长度切分（比如每500字一块），效果很差——经常把一个完整的段落从中间切开，导致语义断裂。后来改用了"语义切分+重叠"的策略，效果好了很多。

from langchain.text_splitter import RecursiveCharacterTextSplitter

def split_document(text):
    """语义递归切分，按段落→句子→词的优先级切分"""
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=500,        # 每块最大500字符
        chunk_overlap=100,     # 相邻块重叠100字符，保证上下文连续
        separators=["\n\n", "\n", "。", "！", "？", "，", " ", ""],
        length_function=len
    )
    chunks = splitter.split_text(text)
    
    # 给每个块加上下文元数据
    chunked_docs = []
    for i, chunk in enumerate(chunks):
        chunked_docs.append({
            "id": f"chunk_{i}",
            "content": chunk,
            "chunk_index": i,
            "total_chunks": len(chunks)
        })
    return chunked_docs

几个关键细节：

  • chunk_size=500是我们的经验值。太小了语义不完整，太大了检索不精准。500字符（约300-400个中文字）刚好是一个完整的小段落。
  • chunk_overlap=100保证相邻块有重叠，避免关键信息被切在边界上。
  • 递归分隔符按"段落→换行→句号→逗号→空格"的优先级切分，尽量在语义边界处切，而不是硬切。

第二步：向量化与存储

切分之后，要把每个文本块转成向量，存到向量数据库里。

embedding模型的选择很关键。我们试过OpenAI的text-embedding-3-small和BGE-large-zh，在中文场景下BGE-large-zh的召回率明显更高（大概高8-10个百分点）。

from sentence_transformers import SentenceTransformer
import chromadb

# 加载中文embedding模型
model = SentenceTransformer('BAAI/bge-large-zh-v1.5')

# 初始化向量数据库（生产环境用Milvus或Qdrant，这里用Chroma演示）
client = chromadb.PersistentClient(path="./rag_db")
collection = client.get_or_create_collection(
    name="knowledge_base",
    metadata={"hnsw:space": "cosine"}
)

def embed_and_store(docs):
    """向量化并存储"""
    texts = [doc["content"] for doc in docs]
    ids = [doc["id"] for doc in docs]
    metadatas = [{"chunk_index": doc["chunk_index"]} for doc in docs]
    
    # 生成向量
    embeddings = model.encode(texts, normalize_embeddings=True)
    
    # 存入向量数据库
    collection.add(
        ids=ids,
        embeddings=embeddings.tolist(),
        documents=texts,
        metadatas=metadatas
    )

第三步：混合检索

这是提升召回率最关键的一步。

很多人做RAG只用向量检索（语义相似度），但向量检索有个致命问题：它对"专有名词"、"数字"、"缩写"的检索效果很差。比如用户问"VPN连不上怎么办"，向量检索可能会把"网络连接故障"的内容检索出来，但漏掉了标题里明确写着"VPN"的内容。

我们的解决方案是混合检索：同时用关键词检索（BM25）和向量检索，然后合并结果。

import rank_bm25
import numpy as np

class HybridRetriever:
    def __init__(self, collection, embedding_model):
        self.collection = collection
        self.model = embedding_model
        # 加载所有文档用于BM25
        all_docs = collection.get()
        self.documents = all_docs["documents"]
        self.doc_ids = all_docs["ids"]
        # 初始化BM25
        tokenized_docs = [doc.split() for doc in self.documents]
        self.bm25 = rank_bm25.BM25Okapi(tokenized_docs)
    
    def vector_search(self, query, top_k=20):
        """向量检索"""
        query_embedding = self.model.encode([query], normalize_embeddings=True)
        results = self.collection.query(
            query_embeddings=query_embedding.tolist(),
            n_results=top_k
        )
        return results["ids"][0], results["documents"][0], results["distances"][0]
    
    def keyword_search(self, query, top_k=20):
        """关键词检索（BM25）"""
        tokenized_query = query.split()
        scores = self.bm25.get_scores(tokenized_query)
        top_indices = np.argsort(scores)[::-1][:top_k]
        ids = [self.doc_ids[i] for i in top_indices]
        docs = [self.documents[i] for i in top_indices]
        scores = [scores[i] for i in top_indices]
        return ids, docs, scores
    
    def hybrid_search(self, query, top_k=20):
        """混合检索：向量+关键词，取并集"""
        vec_ids, vec_docs, vec_scores = self.vector_search(query, top_k)
        kw_ids, kw_docs, kw_scores = self.keyword_search(query, top_k)
        
        # 合并结果，去重
        merged = {}
        for doc_id, doc, score in zip(vec_ids, vec_docs, vec_scores):
            merged[doc_id] = {"doc": doc, "vec_score": 1 - score}  # cosine距离转相似度
        
        for doc_id, doc, score in zip(kw_ids, kw_docs, kw_scores):
            if doc_id in merged:
                merged[doc_id]["kw_score"] = score
            else:
                merged[doc_id] = {"doc": doc, "kw_score": score}
        
        return merged

混合检索之后，我们的召回率从78%提到了88%。因为向量检索漏掉的专有名词，关键词检索能补上；关键词检索漏掉的语义相关内容，向量检索能补上。两者互补。

第四步：重排序（Rerank）

混合检索返回了20个候选结果，但这20个不是都相关。我们需要一个"重排序模型"，把这20个结果按和问题的相关性重新排序，取最相关的前5个。

重排序是提升准确率的关键。我们用的是BGE-reranker-large，专门做中文的重排序。

from sentence_transformers import CrossEncoder

# 加载重排序模型
reranker = CrossEncoder('BAAI/bge-reranker-large')

def rerank(query, candidates, top_k=5):
    """对检索结果重排序"""
    # 构造(查询, 文档)对
    pairs = [(query, candidate["doc"]) for candidate in candidates.values()]
    
    # 计算相关性分数
    scores = reranker.predict(pairs)
    
    # 按分数排序
    scored = []
    for candidate, score in zip(candidates.values(), scores):
        scored.append((candidate["doc"], score))
    
    scored.sort(key=lambda x: x[1], reverse=True)
    
    # 返回top_k
    return [doc for doc, score in scored[:top_k]]

重排序之后，我们的Top-5准确率从88%提到了92%。因为混合检索保证了"相关内容在候选里"，重排序保证了"相关内容排在前面"。

第五步：查询改写

这是一个容易被忽视但效果明显的优化。

用户的提问往往是口语化的、模糊的，直接拿去检索效果不好。比如用户问"那个东西怎么弄"，你根本不知道他在问什么。但如果结合对话历史，把用户的问题改写成一个完整、清晰的查询，检索效果就会好很多。

我们用大模型做查询改写：

def rewrite_query(user_query, conversation_history):
    """结合对话历史，改写用户查询"""
    history_text = ""
    for msg in conversation_history[-5:]:  # 只取最近5轮
        history_text += f"{msg['role']}: {msg['content']}\n"
    
    prompt = f"""请根据对话历史，将用户的当前问题改写为一个完整、清晰、适合检索的查询。
    要求：
    1. 补全省略的指代（如"这个"、"那个"）
    2. 补充必要的上下文
    3. 只输出改写后的查询，不要解释

    对话历史：
    {history_text}

    当前问题：{user_query}

    改写后的查询："""
    
    response = client.chat.completions.create(
        model="gpt-4o-mini",  # 用便宜的模型就行
        messages=[{"role": "user", "content": prompt}],
        temperature=0
    )
    return response.choices[0].message.content.strip()

查询改写虽然多了一次大模型调用，但用的是便宜的小模型，延迟只增加了50ms左右，却能让检索准确率提升5-8个百分点。性价比很高。

第六步：Prompt工程

最后一步，把检索到的上下文组装成Prompt，让大模型回答。

这一步的关键是：明确告诉模型"只基于上下文回答，不知道就说不知道"，减少幻觉。

def generate_answer(query, contexts):
    """基于检索上下文生成答案"""
    context_text = ""
    for i, ctx in enumerate(contexts):
        context_text += f"【参考资料{i+1}】\n{ctx}\n\n"
    
    prompt = f"""你是一个专业的知识库问答助手。请严格基于以下参考资料回答用户的问题。

    规则：
    1. 只使用参考资料中的信息，不要使用你自己的知识
    2. 如果参考资料中没有相关信息，直接回答"根据现有资料无法回答这个问题"
    3. 回答要简洁准确，不要编造内容
    4. 如果参考资料中有矛盾，以最新的资料为准，并指出矛盾

    参考资料：
    {context_text}

    用户问题：{query}

    回答："""
    
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        temperature=0.1
    )
    return response.choices[0].message.content

性能优化：延迟从800ms到180ms

上面的流程跑通之后，我们测了一下延迟，P99是800ms，太慢了。用户体验很差。于是我们做了一系列优化：

  1. embedding缓存：把常用查询的embedding缓存起来，避免重复计算。命中率大概40%，省了一次embedding计算（约50ms）。
  2. 检索并行化：向量检索和关键词检索并行执行，而不是串行。省了约100ms。
  3. 重排序批量计算：20个候选一次性送入重排序模型，而不是一个个算。省了约150ms。
  4. 大模型流式输出：答案用流式输出，用户不需要等完整答案生成，首字延迟从600ms降到了200ms。
  5. 查询改写和检索并行：查询改写的同时，用原始查询先做一次检索，改写后再做一次，取并集。虽然多了一次检索，但省了查询改写的等待时间。

优化之后，P99延迟降到了180ms（不含大模型生成时间），用户体验好了很多。

我的一些思考

做RAG系统最大的感受是：细节决定成败。

RAG的原理很简单，谁都能写个Demo。但从Demo到生产系统，中间有无数个细节：切分大小、重叠比例、embedding模型选择、检索策略、重排序、查询改写、Prompt工程、性能优化……每一个细节都影响最终效果。

我们团队有一句话："RAG是一门工程艺术，不是算法科学。"因为它没有什么高深的算法，全是工程上的细节和取舍。你需要根据自己的场景，不断地试错、调参、优化。

另一个感受是：不要迷信单一技术。 最开始我们只用向量检索，觉得语义检索最先进。后来发现关键词检索虽然"老派"，但在专有名词和数字检索上效果更好。混合检索才是王道。重排序也是，最开始我们觉得没必要，后来加上之后准确率提升明显。

最后说一句：RAG系统没有"最好的配置"，只有"最适合你场景的配置"。本文的参数（chunk_size=500、top_k=20、重排序取5个）是我们场景下的最优值，放到你的场景可能就不对了。一定要用自己的数据做测试，找到最适合自己的配置。

RAG这条路没有捷径，就是不断地试、不断地调。但当你看到召回率从65%一点点爬到92%的时候，你会觉得一切都值得。
