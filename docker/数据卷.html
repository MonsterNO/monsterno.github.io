数据卷 ​

概念 ​

一句话：数据卷是容器的 “外接硬盘”——Docker 在容器之外单独管理的存储目录，挂进容器里当普通目录用。

四个名词先分清：

  • 命名卷（named volume）：Docker 创建并管理，有自己的名字（如 mydata），落在宿主机 /var/lib/docker/volumes/ 下。
  • 绑定挂载（bind mount）：直接把宿主机某个目录挂进容器，容器内外的改动是同一份文件。
  • 匿名卷（anonymous volume）：没有名字的卷，Docker 随机起 64 位 hash 名；docker run -v /data、Dockerfile 里的 VOLUME 都会生成它。
  • tmpfs：挂到内存的临时存储，容器一停就消失。

卷和容器是 “外挂” 关系：数据不写在容器的可写层里，所以容器删了、换了、升级了，数据还在。

有什么用 ​

没有卷，容器的可写层就是数据的唯一下落，于是：

  • 容器 docker rm 之后，里面写过的文件全没了；
  • 可写层基于镜像分层，每次写文件都要走 Copy-on-Write 拷贝，数据库这种频繁写的场景表现很差；
  • 多个容器之间没法共享同一批文件；
  • 换台机器部署，数据只能手工搬过去。

卷把这些一个个接过去：

场景解决什么
数据持久化容器删除、重建、升级镜像，数据仍在：MySQL 容器换三遍，库还在
解耦容器回归 “无状态、可随时销毁”，有状态的东西交给卷
容器间共享一个卷可以同时挂给多个容器，比如 web 与定时任务共用上传目录
迁移与备份卷和宿主机目录两边一挂，tar 打包就能搬到另一台机器
性能绕过 CoW，直接读写宿主机磁盘，数据库、日志类 IO 更合适
注入配置宿主机上的配置文件、初始化 SQL 直接挂进去（这类更适合绑定挂载）

三种挂载方式 ​

方式语法存储位置典型场景
命名卷 named volume-v mydata:/data 或 --mount type=volume,src=mydata,dst=/dataDocker 管理（Linux 下 /var/lib/docker/volumes/<卷名>/_data）数据库数据、需要持久化并由 Docker 管理的内容
绑定挂载 bind mount-v /host/path:/data 或 --mount type=bind,src=/host/path,dst=/data宿主机任意目录配置文件、代码热更新、宿主机已有数据
临时挂载 tmpfs--mount type=tmpfs,dst=/tmp宿主机内存敏感临时文件、不需要持久化的高性能读写

所以：要 “Docker 帮我管着” 就用命名卷；要 “我直接改宿主机文件” 就用绑定挂载；只是临时数据，用 tmpfs。

命名卷与匿名卷 ​

  • 命名卷：docker rm 删容器不会删卷，必须 docker volume rm 显式删除。这是它最大的价值：容器随便重建，数据在。
  • 匿名卷：docker rm 默认保留，docker rm -v 才删；docker run --rm 会在容器退出时连带删掉匿名卷。
  • 匿名卷的问题是 难追踪：docker volume ls 里一堆 hash 名，久了不知道哪个能删。所以生产环境一律显式命名。

-v 与 --mount 该用哪个 ​

优先用 --mount，它的行为更可预测：

  • -v 遇到宿主机路径不存在会自动创建目录——这是 “文件被挂成目录” 这类事故的根源。
  • --mount type=bind 源路径不存在直接报错，问题当场暴露。
  • -v 的简写后缀：:ro（只读）、:z / :Z（SELinux 标签）、:cached / :delegated（Docker Desktop for Mac 的一致性模式）；--mount 用逗号参数表达同样含义。
bash
docker run -d \
  --mount type=bind,src=/etc/app/config.yml,dst=/app/config.yml,readonly \
  myapp

Dockerfile 的 VOLUME ​

dockerfile
VOLUME /var/lib/mysql
1

这行声明一个匿名卷：每个容器创建时，Docker 自动给该目录挂一个匿名卷。

  • 好处：提醒使用者这个目录要持久化，不写 -v 时数据也不会随可写层销毁。
  • 坏处：匿名卷悄悄堆积；构建阶段对 VOLUME 目录的写入也不会进镜像。

所以更推荐不在 Dockerfile 里写 VOLUME，持久化交给运行时的 -v / --mount 显式决定。

权限问题 ​

最常见报错：容器内进程写卷时 Permission denied。原因是容器里的进程用某个 UID 写文件（mysql 常是 999、nginx 常是 101），而卷根目录属于 root，两边对不上。

bash
# 先看卷里文件的属主
docker run --rm -v mydata:/data alpine ls -ln /
1
2
场景做法
绑定挂载（宿主机目录）在宿主机 sudo chown -R 1000:1000 ./data，UID 按镜像文档要求
命名卷一次性容器改属主：docker run --rm -v mydata:/data alpine chown -R 1000:1000 /data
linuxserver 系镜像直接给环境变量：-e PUID=1000 -e PGID=1000
多容器协作（NAS、家庭机）统一约定一个 UID / GID，所有容器都按它跑

UID 一定要查出来再写：docker run --rm nginx:1.27-alpine id nginx、docker run --rm mysql:8.4 id mysql，别背数字。

跨主机与网络存储 ​

卷共享给多个容器：

bash
docker run -d --name web --volumes-from db myapp # 复用 db 容器的所有卷
1

更推荐多个容器直接挂同一个命名卷，来源明确、可读性好。

挂 NFS 等网络存储：

bash
docker volume create --driver local \
  --opt type=nfs \
  --opt o=addr=192.168.1.10,rw,nfsvers=4.1 \
  --opt device=:/export/data \
  nfs-data

docker run -d -v nfs-data:/data myapp

备份与恢复 ​

思路：用一个临时容器，同时挂上 “卷” 和 “宿主机输出目录”，把数据搬出去或搬回来。

bash
# 备份
docker run --rm \
  -v db-data:/data \
  -v /backup:/backup \
  alpine tar czf /backup/db-data-$(date +%F).tar.gz -C /data .

# 恢复：先清空再解包
docker run --rm \
  -v db-data:/data \
  -v /backup:/backup \
  alpine sh -c "rm -rf /data/* && tar xzf /backup/db-data-2026-11-17.tar.gz -C /data"

# 数据量小，直接复制到宿主机
docker run --rm -v db-data:/data -v "$PWD":/out alpine cp -a /data /out/

注意事项 ​

  1. 空目录盖住镜像内容 —— 现象：容器起来后 /app 里的代码或配置 “消失”。原因：绑定挂载一个空目录，会把镜像里该路径的内容整层遮住。解法：只在开发环境挂源码目录，生产别用空目录覆盖镜像自带的内容。
  2. 文件被挂成目录 —— 现象：nginx 启动失败，报 open() "/etc/nginx/nginx.conf" failed (21: Is a directory)。原因：-v ./nginx.conf:/etc/nginx/nginx.conf 而宿主机文件不存在时，-v 自动建了一个同名目录。解法：改用 --mount type=bind（源不存在会直接报错），或先创建文件。
  3. compose down -v 把库删了 —— 现象：重启后数据库空了。原因：-v 表示连卷一起删。解法：日常只 down；需要删卷时单独执行并二次确认。
  4. 写入报 Permission denied —— 现象：mysql 报 Can't create/write to file，nginx 上传 500。原因：容器内进程 UID 与卷根属主不一致。解法：一次性容器 chown，linuxserver 系用 PUID / PGID。
  5. prune 误删卷 —— 现象：docker volume ls 里某个卷不见了。原因：volume prune / system prune --volumes 会删掉所有没有容器引用的卷。解法：执行前先 ls 核对，重要卷保持至少一个容器引用。
  6. 数据库放绑定挂载 —— 现象：Docker Desktop 上启动慢，NFS 上报锁错误。原因：跨文件系统同步和锁语义问题。解法：数据库用本地命名卷，别跨文件系统。
  7. 匿名卷越积越多 —— 现象：volume ls 里一堆 64 位 hash。原因：Dockerfile 的 VOLUME 或 -v /path 只写了容器路径。解法：运行时显式命名，清理前先看清哪些被引用。

实战案例 ​

目标：给博客站把数据落稳——上传目录和 MySQL 数据都不随容器消失，同时配置可改、能备份。

compose.yaml：

yaml
services:
  web:
    image: nginx:1.27-alpine
    ports:
      - "80:80"
    volumes:
      - ./conf/default.conf:/etc/nginx/conf.d/default.conf:ro
      - web-uploads:/var/www/uploads
  db:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: "${DB_PASSWORD:?必须在 .env 里设置}"
    volumes:
      - db-data:/var/lib/mysql

volumes:
  web-uploads:
  db-data:

总结 ​

  • 数据库、上传文件 → 命名卷；配置和代码 → 绑定挂载 + :ro；临时敏感数据 → tmpfs。
  • 命名卷删容器不删，down -v 和 volume prune 才会删，执行前先 ls 核对。
  • 首选 --mount 写法：路径不存在会报错，不会偷偷建目录。
  • 属主问题先 id 查 UID 再 chown，别背数字。
  • 改动前先备份，备份先停容器：tar + 临时容器，两步就够。
