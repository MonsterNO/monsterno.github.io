自定义镜像 ​

概念 ​

自定义镜像 = 以某个基础镜像为起点，用 Dockerfile 把「运行环境 + 你的代码 / 依赖」按层写进去，构建出一个属于自己项目的镜像。

四个名词先记住：

  • Dockerfile：构建脚本，一行一个指令，从上到下按顺序执行。
  • 构建上下文（build context）：docker build 时发给 Docker 守护进程的那个目录，默认是当前目录。
  • 层（layer）：会产生文件变化的指令（RUN、COPY、ADD）各生成一层，层只读、可复用、按顺序叠加。
  • 基础镜像：FROM 后面那个镜像，决定运行环境（node:20-alpine、nginx:1.27-alpine、ubuntu:24.04）。

类比：基础镜像是毛坯房，Dockerfile 是装修方案，构建出来的镜像是成品房——拿成品房的人不需要知道装修过程。

有什么用 ​

不自定义镜像，交付最终会退化成「在我机器上是好的」：

  • 开发机 Node 18、服务器 Node 16，同一份代码跑出不同结果；
  • 每次部署手动 apt install、npm install，漏一步就起不来；
  • 出问题要回滚，只能凭记忆重新操作一遍，没有可执行的“标准件”。

自定义镜像把这三件事一次解决：

场景解决什么
环境固化运行时、系统库、依赖版本写死在镜像里，哪台机器拉下来都一样
交付一致本地、测试、线上跑的是同一个镜像（同一个 digest）
可回滚每次构建打不同 tag，出问题切回上一个 tag 即可
可复用一个镜像能起任意多个容器，也能被别的 Dockerfile 当基础镜像用
构建提速层缓存让「依赖没变」时跳过重装，CI 从几分钟降到几十秒
安全可控基础镜像、非 root 运行、体积裁剪，全由你决定

Dockerfile 的基本结构 ​

dockerfile
# 1. 基础镜像（必须第一条）
FROM node:20-alpine

# 2. 元信息与工作目录
LABEL maintainer="you@example.com"
WORKDIR /app

# 3. 先拷依赖清单，再装依赖（顺序影响缓存，见下文）
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

# 4. 再拷源码
COPY src ./src

# 5. 运行时配置
ENV NODE_ENV=production
EXPOSE 3000

# 6. 启动命令（数组形式）
CMD ["node", "src/index.js"]

常用指令速览：

指令作用常见写法要点
FROM指定基础镜像写死 tag，别用 latest
WORKDIR之后所有指令的工作目录不要用 RUN cd 代替
COPY复制文件进镜像COPY 源 目标，支持 --from=阶段名
ADD同 COPY，另外能解压、能拉 URL一般用 COPY 就够，ADD 语义模糊
RUN构建期执行命令多条命令用 && 串一层，末尾清理缓存
ENV / ARG运行时环境变量 / 构建期参数ARG 不进最终容器环境
EXPOSE声明端口（仅文档作用）真正的映射在 docker run -p
USER切换后续指令与运行时的用户生产镜像建议切到非 root
CMD容器默认启动命令数组形式，可被 docker run 后面的命令覆盖
ENTRYPOINT容器入口，CMD 作为其默认参数数组形式，配 CMD 一起用
HEALTHCHECK容器健康检查与 Compose 的 healthcheck 是同一套机制
VOLUME声明匿名卷已在「数据卷」那篇说明，一般不在 Dockerfile 里写

所以：Dockerfile 的结构就是「基础镜像 → 装依赖 → 拷代码 → 配运行参数 → 定启动命令」，顺序基本固定。

构建上下文与 .dockerignore ​

docker build 并不是把文件逐个拷进去，而是先把整个上下文目录打包送给守护进程。上下文越大，构建越慢，泄露风险也越大。

bash
docker build -t demo-web:1.0.0 .        # . 就是上下文目录

用 .dockerignore 把它裁到最小：

text
node_modules
dist
.git
.env*
*.log
Dockerfile
docker-compose*.yaml
  • 不写的话，node_modules、.git 会被一起发过去，几十 MB 起步。
  • .env 被送进上下文，就存在被打进镜像层的风险。
  • 上下文里只保留构建真正需要的文件，是最省事的优化手段。

分层与构建缓存 ​

每条 RUN、COPY 生成一层，Docker 逐层比对：某一层的内容和上次一样，就直接用缓存；一旦某层变了，它之后的所有层都要重建。

这决定了两个写法：

dockerfile
# 推荐：依赖清单单独一层，改代码不影响装依赖
COPY package.json package-lock.json ./
RUN npm ci
COPY src ./src
dockerfile
# 不推荐：源码和依赖混在一层，改一行代码就要重装全部依赖
COPY . .
RUN npm ci
  • 顺序原则：变化频率低的放前面，变化频率高的放后面。
  • 想强制不用缓存：docker build --no-cache。
  • 缓存打不中时，日志里会看到 CACHED 消失，从那一层开始重新执行。

多阶段构建 ​

编译类项目（前端、Go、Java）需要一个“带编译器”的镜像来构建，但运行时并不需要这些工具。多阶段构建让它们待在同一个 Dockerfile 里，最终镜像只留运行所需。

dockerfile
# 阶段一：构建
FROM node:20-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

# 阶段二：运行
FROM nginx:1.27-alpine
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
  • AS builder 给阶段起名，COPY --from=builder 从上一阶段取文件。
  • 也可以用外部镜像：COPY --from=nginx:1.27-alpine /usr/share/nginx/html/index.html ./。
  • 只想构建到某个阶段做调试：docker build --target builder -t demo-web:debug .。
  • node_modules、源码、构建工具都不会出现在最终镜像里，体积从几百 MB 压到几十 MB 是常态。

tag、推送与仓库 ​

bash
docker build -t demo-web:1.0.0 .
docker tag demo-web:1.0.0 registry.example.com/app/demo-web:1.0.0
docker push registry.example.com/app/demo-web:1.0.0
  • 镜像名格式：仓库地址/命名空间/名字:tag，省略仓库地址时默认 docker.io。
  • tag 用语义化版本或 git commit 短哈希，别指望 latest 能回滚。
  • 一个镜像可以有多个 tag，指向同一个 digest：docker tag demo-web:1.0.0 demo-web:stable。
  • 私有仓库要 docker login registry.example.com，内网 HTTP 仓库还得在 daemon.json 里加 insecure-registries。
  • 清理本机：docker image prune 删悬空镜像，docker rmi 删指定 tag。

镜像瘦身与安全 ​

做法说明
选精简基础镜像-alpine、-slim 比完整发行版小数倍；追求极致用 distroless
合并 RUN 并清理apt-get install ... && rm -rf /var/lib/apt/lists/* 写在同一层
多阶段构建只把产物拷进运行阶段，编译工具不入镜像
非 root 运行建用户后 USER app，容器被拿下时损失更小
不把密钥写进 Dockerfile密码、token 用 BuildKit secret 或运行时挂载
固定基础镜像版本tag 固定 + 定期更新，避免构建结果漂移

镜像瘦身不是为了好看：体积小 → 拉取快、启动快、攻击面小、漏洞扫描噪声少。

构建参数与跨平台 ​

dockerfile
ARG NODE_VERSION=20
FROM node:${NODE_VERSION}-alpine

ARG BUILD_ENV=production
ENV APP_ENV=${BUILD_ENV}
bash
docker build --build-arg NODE_VERSION=18 -t demo-web:1.0.0 .
  • ARG 只在构建期有效，ENV 会留在镜像里；两者都不适合放密码（docker history 能看到）。
  • 构建期密钥用 BuildKit 的 RUN --mount=type=secret，或干脆在运行时注入。
  • 跨平台构建（Apple 芯片给 amd64 服务器打镜像）：
bash
docker buildx build --platform linux/amd64,linux/arm64 \
  -t registry.example.com/app/demo-web:1.0.0 --push .

单平台本地验证用 --platform linux/amd64 即可，注意别把平台相关二进制混进同一层缓存。

注意事项 ​

  1. COPY . . 放在 npm ci 前面 —— 现象：改一行代码，构建时依赖全部重装。原因：源码层变了，往后的层缓存全部失效。解法：先 COPY package*.json 再装依赖，最后 COPY 源码。
  2. 不写 .dockerignore —— 现象：构建耗时突然变长、镜像里出现 node_modules 或 .env。原因：整个目录被当作上下文发过去。解法：把 node_modules、.git、.env*、dist 排除，并且确认 Dockerfile 没 COPY .env。
  3. CMD 用了 shell 形式 —— 现象：docker stop 要等 10 秒才杀掉，进程收不到 SIGTERM，日志刷 graceful shutdown timeout。原因：CMD node app.js 会被 /bin/sh -c 包一层，信号到不了 node。解法：写 CMD ["node", "app.js"]。
  4. 镜像里以 root 运行 —— 现象：容器内的进程能改系统文件，安全扫描报警。原因：基础镜像默认 root，且没写 USER。解法：创建普通用户并在 CMD 前 USER app，同时把挂载目录属主改成这个 UID。
  5. 用 ARG 传密码 —— 现象：docker history --no-trunc 能直接看到密码。原因：ARG 会写进构建历史。解法：BuildKit secret 或运行时环境变量，构建完再把凭据轮换。
  6. latest 当发布版本 —— 现象：某天 docker pull 拿到不一样的镜像，问题无法复现。原因：latest 被覆盖。解法：每次构建打版本 tag + commit 短哈希，保留至少两个历史版本。
  7. alpine 上编译产物跑不起来 —— 现象：Error loading shared library、not found。原因：alpine 用 musl libc，node-gyp 编译的模块或某些预编译二进制依赖 glibc。解法：builder 与运行阶段统一用同一个基础镜像，或改用 -slim。

实战案例 ​

目标：把一个 Vite 静态站点打成 nginx 镜像，要求体积小、改代码不重装依赖、能按 tag 回滚。结构就是上文那张多阶段构建图。

目录：

text
hopeisle/
├─ Dockerfile
├─ .dockerignore
├─ package.json
├─ package-lock.json
├─ nginx.conf
└─ src/

Dockerfile：

dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80

.dockerignore：

text
node_modules
dist
.git
.env*
*.log

nginx.conf：

nginx
server {
  listen 80;
  root /usr/share/nginx/html;
  index index.html;

  location / {
    try_files $uri $uri/ /index.html;
  }
}

构建与验证：

bash
docker build -t hopeisle-web:1.0.0 .

docker run -d --name web -p 8080:80 hopeisle-web:1.0.0
curl -I http://localhost:8080            # 期望 200

docker images hopeisle-web                # 对比体积：几十 MB 量级
docker history hopeisle-web:1.0.0         # 确认没有 node_modules、没有源码

# 第二次构建只改 src/ 里的文件，观察缓存
time docker build -t hopeisle-web:1.0.1 .

验证点：

  • 第二次构建时 npm ci 那层显示 CACHED，只有 COPY . . 之后的层重建——说明缓存顺序写对了。
  • docker run 起来后页面正常、刷新子路由不 404（try_files 兜底生效）。
  • docker history 里看不到 node 相关层，说明多阶段生效。

总结 ​

  • 结构固定：FROM → 装依赖 → 拷代码 → 配运行参数 → 定启动命令。
  • 缓存靠顺序：变化频率低的层放前面，package*.json 先于源码。
  • 上下文要瘦：.dockerignore 必写，别把 node_modules、.git、.env 发过去。
  • 编译类项目用多阶段：builder 留构建工具，运行阶段只留产物。
  • tag 别用 latest：版本号 + commit 短哈希，才谈得上回滚。
  • 生产镜像三件套：非 root、精简基础镜像、密钥不进 Dockerfile。
