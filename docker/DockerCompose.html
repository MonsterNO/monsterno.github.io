DockerCompose ​

概念 ​

Compose 是 Docker 官方提供的一套单机多容器编排工具：用一个 compose.yaml 文件声明「要跑哪些服务、每个服务怎么配、彼此怎么连」，再用 docker compose 这一条命令把它们统一启动、停止、重建。

几个基本名词：

  • 服务（service）：一个容器实例的定义，比如 web、db。同一个服务可以通过 --scale 起多个实例。
  • 项目（project）：一组服务的集合，文件名/目录名默认就是项目名，所有资源（容器、网络、卷）都带这个前缀。
  • Compose Specification：字段规范的名字。网上说的「Compose v2 / v3」指的就是不同时期的这套规范。

一句话记：Compose 把「一堆 docker run」变成「一份 yaml + 一条命令」。它管的是单机上的协作，跨机器的集群调度是 Swarm / Kubernetes 的事。

有什么用 ​

场景Compose 帮你解决什么
本地开发一条命令起全套依赖（db、redis、mq），不用一个个 docker run 记参数
单机部署网络、卷、重启策略、资源限制、日志轮转都写进文件，换台机器复制过去就能跑
环境切换compose.override.yaml 或多 -f 文件，本地和线上共用一份基础配置
团队协作yaml 进 Git，新人 clone 后 docker compose up -d 就有完整环境
问题复现环境能完整复述出来，不用口述「我敲了哪些命令」

它具体解决了哪些麻烦：不起 Compose 时，拉一个 web + db 要这么干——

bash
docker network create app-net
docker volume create db-data
docker run -d --name db --network app-net -v db-data:/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=xxx mysql:8.4
docker run -d --name web --network app-net -p 8080:80 myapp:latest

命令长、参数散、换台机器要重敲、改一项容易漏一项、顺序全靠脑子记。写成 yaml 之后，这些全变成文件里的一行，改完 docker compose up -d 就生效。

两个版本别再混用 ​

版本命令说明
v1docker-composePython 写的独立二进制，2023 年起不再发新版，停止维护
v2docker composeGo 写的 Docker CLI 插件，随 Docker Engine 一起装，现在统一用这个
  • v2 里 version: 字段已经废弃，写了会警告 the attribute version is obsolete，删掉即可。
  • 旧教程里的 version: "3.8" 属于过时写法，字段以 Compose Specification 为准。

文件结构与顶层字段 ​

yaml
name: hopeisle # 项目名，决定容器/网络/卷名前缀
services: # 必填，每个 key 是一个服务
  web:
    image: nginx:1.27-alpine
networks: # 可选，自定义网络
  app:
volumes: # 可选，命名卷
  web-data:

项目名影响资源命名：默认取所在目录名，容器叫 <项目>-<服务>-1，默认网络叫 <项目>_default，命名卷叫 <项目>_<卷名>。不显式写 name 时，换个目录启动就变成另一套资源，现象就是“数据不见了”。

services 常用字段 ​

字段作用备注
image使用镜像tag 写死，别用 latest
build本地构建：context / dockerfile / args / target与 image 同时写时，image 作为构建产物的名字
command / entrypoint覆盖镜像的启动命令容器内要用的变量要写 $$
environment / env_file环境变量数组或 map 两种写法
ports发布到宿主机："8080:80"只写容器端口则随机映射
expose只在容器网络内暴露不发布到宿主机
volumes挂载详见「数据卷」那篇
depends_on启动顺序不等于对方已就绪
healthcheck健康检查配合 condition: service_healthy 才真的等
restartno / always / on-failure / unless-stopped常驻服务用 unless-stopped
networks加入哪些网络，可配 aliases不写就进默认网络
container_name固定容器名会导致无法 --scale，一般不写
user / working_dir运行身份、工作目录处理属主问题时常用来对齐 UID
initinit: true 处理 PID 1 信号建议常开，免得收不到 SIGTERM
profiles按需启动调试工具、一次性任务用
mem_limit / cpus资源限制也可用 deploy.resources.limits
logging日志驱动与轮转不配轮转迟早写满磁盘
stop_grace_period停止前的优雅退出时间默认 10s，数据库类可放宽

命令速查 ​

命令作用
docker compose up -d后台起全套；--build 重新构建，--pull always 重新拉镜像
docker compose up --wait等所有服务 healthy 才返回，脚本里比 sleep 稳
docker compose ps看服务状态与健康状态
docker compose logs -f --tail=100 web跟日志
docker compose exec -it web sh进运行中的容器
docker compose run --rm web sh起一次性临时容器，跑完即删
docker compose config校验语法并打印插值后的最终配置
docker compose config --quiet只校验，CI 里用
docker compose build / pull只构建 / 只拉镜像
docker compose restart web重启单个服务
docker compose down停并删容器、网络；-v 连卷删，--rmi local 连镜像删
docker compose up --scale web=3横向扩到 3 个实例（不能写 container_name、不能固定端口）
docker compose cp web:/etc/nginx/nginx.conf ./容器与宿主机之间拷文件
docker compose watchv2.17+，监听代码变化自动同步或重建

网络 ​

yaml
services:
  web:
    networks:
      - app
  db:
    networks:
      - app
networks:
  app:
    driver: bridge
    # internal: true   # 这个网络没有外网出口
    # external: true   # 引用外部已存在的网络
  • 不写 networks 时所有服务都进 <项目>_default，服务名就是 DNS 名：web 里直接连 db:3306。
  • ports 只决定宿主机能否访问，与服务之间互通无关。
  • aliases 给服务加额外域名；internal: true 断开外网；external: true 复用已存在的网络。
  • 两个不同 Compose 项目要互通：用 external: true 的网络，或显式写同一个 name。

依赖与启动顺序 ​

depends_on 只保证启动顺序，不保证对方已经可用。db 容器起来了、初始化没跑完，web 照样连不上然后退出。

正确做法是给被依赖的服务配健康检查：

yaml
services:
  db:
    image: mysql:8.4
    healthcheck:
      test:
        ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-uroot", "-p$$MYSQL_ROOT_PASSWORD"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
  web:
    depends_on:
      db:
        condition: service_healthy
  • condition 三种取值：service_started（默认，仅顺序）、service_healthy（等健康）、service_completed_successfully（等一次性任务跑完，适合数据库迁移、初始化脚本）。
  • start_period 很关键：MySQL 首次初始化可能要几十秒，不给这个窗口就会一直判失败。
  • 循环依赖会直接报错。

环境变量与 .env ​

优先级：shell 环境变量 > .env（或 --env-file 指定的文件）> compose 里写的默认值。

yaml
services:
  db:
    image: mysql:${MYSQL_VERSION:-8.4}
    environment:
      MYSQL_ROOT_PASSWORD: "${DB_PASSWORD:?必须在 .env 里设置}"
  • ${VAR:-默认值}：没设置就用默认。
  • ${VAR:?报错信息}：没设置直接中止，适合密码这类不能默默跑空的变量。
  • .env 放 compose 文件同目录会自动加载；docker compose --env-file ./prod.env up -d 可换一份。
  • environment 里想用容器内的变量，$ 要写成 $$，否则会被 Compose 先在宿主机替换掉——最高频的一条坑。

profiles：按需启动 ​

yaml
services:
  phpmyadmin:
    image: phpmyadmin
    profiles: ["debug"]
  • 声明了 profiles 的服务，普通 docker compose up -d 不会启动它。
  • 要起就 docker compose --profile debug up -d。
  • 常见用法：调试面板、一次性迁移任务、备份容器塞进 profile，生产环境一条 up -d 不会带上它们。

多文件与 override ​

  • compose.yaml 旁边放 compose.override.yaml 会自动合并。本地开发把端口、代码挂载、调试开关写进 override，compose.yaml 保持干净。
  • 手动指定：docker compose -f compose.yaml -f compose.prod.yaml up -d，后面的覆盖前面的。
  • 合并规则：标量字段覆盖（image、command）、映射按键合并、ports / expose 这类列表是追加不是替换。
  • 需要「清空再覆盖」时用 v2.24+ 的标签：ports: !reset []、image: !override xxx。
yaml
# compose.yaml —— 两边共用的部分
services:
  web:
    build: .
    ports: ["8080:80"]

# compose.override.yaml —— 本地开发，自动合并进来
services:
  web:
    volumes:
      - ./src:/app/src
    environment:
      DEBUG: "1"

本地 docker compose up -d 会把两份合并；线上用 -f compose.yaml -f compose.prod.yaml 指定时，compose.override.yaml 不会再自动加载，避免把本地调试配置带上生产。

资源限制与日志轮转 ​

yaml
services:
  api:
    mem_limit: 512m
    cpus: 1.0
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
  • deploy.resources.limits 在 Compose v2 里同样生效，与 mem_limit / cpus 等价；只用 docker compose 时后者更直白。
  • 不配日志轮转，json-file 会一直追加，小型服务器上最常见的磁盘告警就是这么来的。

常见坑 ​

  1. 写死 container_name：不能 --scale，多个项目还会撞名。除非被别的脚本按名字引用，否则不要写。
  2. down -v：连卷一起删，数据库直接没。删之前确认命令里没有 -v。
  3. 端口冲突：宿主机 80 被占会在 up 时报 bind 失败，改 ports: "8080:80"，或把端口放进 .env。
  4. 把 depends_on 当就绪：只有配了 healthcheck 的条件才真的等。
  5. $ 没转义：command: sh -c "echo $HOME" 里的 $HOME 会被 Compose 在宿主机替换成空，要容器内展开就写 $$HOME。
  6. restart: always 掩盖问题：容器反复重启、日志刷屏，先看 ps 状态和 logs --tail，别用重启策略盖住症状。
  7. 改配置不生效：up -d 只重建配置变化过的容器；换 image tag 用 up -d --pull always，改 Dockerfile 用 up -d --build。
  8. version: 字段：v2 下已废弃，留着只有警告，建议删干净。
  9. Windows 路径：./data:/data 没问题，E:\data:/data 要写成 E:/data。

实战案例 ​

只挑一个案例：web 容器 + MySQL。它把三条最常用的知识串在一起——服务之间靠服务名通信、depends_on 配合健康检查、数据落在命名卷里。

案例：web 容器 + MySQL ​

运行关系

启动流程

项目结构：

text
demo/
├─ compose.yaml      # 服务定义（进 Git）
├─ .env              # DB_PASSWORD=...（不进 Git）
├─ Dockerfile        # web 的构建文件
└─ （没有 db-data/）  # 命名卷由 Docker 管理，不会出现在项目目录里

下面是两份文件的完整内容。

compose.yaml：

yaml
name: demo
services:
  web:
    build: .
    ports:
      - "8080:80"
    environment:
      DB_HOST: db
      DB_PASSWORD: "${DB_PASSWORD:?必须在 .env 里设置}"
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped
  db:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: "${DB_PASSWORD}"
      MYSQL_DATABASE: app
    volumes:
      - db-data:/var/lib/mysql
    healthcheck:
      test:
        ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-uroot", "-p$$MYSQL_ROOT_PASSWORD"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    restart: unless-stopped
volumes:
  db-data:

.env：

bash
DB_PASSWORD=change-me

跑起来：

bash
docker compose config      # 先校验语法，看清插值结果
docker compose up -d --build
docker compose ps          # web 和 db 都是 running / healthy
docker compose logs -f web # 确认能连上库

验证「数据真的留住了」：改一行代码 → docker compose up -d --build → 库里的数据还在，因为它在 demo_db-data 这个命名卷里。

总结 ​

  • 用 docker compose（v2），把 version: 删掉。
  • 显式写 name，容器 / 网络 / 卷的命名才稳定。
  • 依赖就绪靠 healthcheck + condition: service_healthy，别指望 depends_on 单独扛。
  • 数据库必须挂命名卷，down -v 之前先想清楚。
  • 环境变量走 .env 加 ${VAR:?}，容器内的变量记得 $$。
  • 配置改动没生效，先想清楚是 --build、--pull always 还是 --force-recreate 的问题。
